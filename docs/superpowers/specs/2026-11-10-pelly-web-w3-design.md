## 1. 왜 하는가

백오피스 요청은 화면 하나에서 끝나지 않는 경우가 많다. 이 문서는 그중 세 가지를 푼다.

1. **JS·CSS 수정을 명세에 넣을 수 없다.** 지금 명세 작업 종류는 `cs`·`sql`·`asp`뿐이다. 「주문 검색에 상태 조건을 더한다」가 SP, ASP, 공용 JS를 함께 고쳐야 하면, JS 부분만 `pelly js`로 따로 돌려야 한다. 그러면 그룹으로 함께 되돌릴 수 없다.
2. **JS 함수의 이름이나 매개변수를 바꿀 수 없다.** 지금 `pelly js`는 대상 함수의 이름·매개변수가 바뀌면 막는다(`JsChecks.ShapeViolation`, 「이름을 바꾸지 마십시오」). 부르는 곳을 함께 고칠 방법이 없어서 그렇게 정했다. 그런데 「검색 함수에 페이지 번호 인수를 더한다」 같은 요청은 흔하다(Claude 짐작). 그 함수를 부르는 곳은 다른 `.js`, 페이지 `<script>`, `onclick="fnSearch(…)"` 같은 HTML 속성, VBScript가 쓰는 HTML 문자열에 흩어져 있다.
3. **폼 필드 이름이 어긋나도 모른다.** 저장 페이지는 `Request.Form("custNo")`로 읽는데, 화면의 입력란 이름은 `custId`로 고쳐진 경우다. 실행해 보기 전에는 드러나지 않고, 값이 빈 채로 저장된다. JS·CSS 설계 §4.9는 이것을 「백오피스 요청에서 가장 자주 빠지는 짝」으로 짐작했다.

## 2. 목표 / 비목표 / 실패 조건

**목표**
1. 명세 작업 줄에 `js`·`css` 종류를 더한다. 대상은 W1·W2의 `pelly js`·`pelly css` 대상과 같다(§3).
2. `spec check`가 js·css 작업을 검사하고, `pelly apply`가 W1·W2 파이프라인으로 실행한다. 그룹 규칙은 A2와 같다. 함께 되돌리고, C# 빌드는 cs 작업에만 한다.
3. **명세 안에서는 JS 함수 서명 변경을 허용한다.** 명세의 js 작업은 대상 함수의 이름·매개변수를 바꿀 수 있다(§4.2). 단독 `pelly js`는 `--signature`를 줄 때만 허용한다.
4. **JS 호출 색인과 영향 탐색:** 사이트 전체에서 「어느 파일 어느 줄이 어떤 JS 함수를 부르는가」를 찾는다(§4.3). `spec check --impact`는 js 작업 대상 함수를 부르는 곳 중 명세에 없는 곳을 경고한다(§4.4).
5. **적용 뒤 확인:** js 작업이 대상 함수의 이름이나 매개변수를 실제로 바꿨으면, 고치지 않은 호출을 경고한다(§4.5). 이름을 바꾼 경우에는 옛 이름으로 남은 호출을 경고한다.
6. **바뀐 서명 전달:** 같은 apply에서 앞선 js 작업이 서명을 바꾼 함수를, 뒤의 js·asp 작업이 부르면 모델 입력에 바뀐 서명을 보인다(§4.6). A2 §4.4와 같은 생각이다.
7. **폼 필드 이름 짝 검사(경고):** 편집 때문에 「서버 페이지가 읽는 필드 이름」과 「그 페이지로 보내는 폼·ajax의 필드 이름」이 새로 어긋나면 경고한다(§5). `pelly asp`·`pelly js`의 검증 행으로 넣고, apply 끝에 적용된 파일 전체로 한 번 더 본다.
8. `apply.json`·`summary.json`·`pelly report`·README·`deploy/usage.md`·PRD·`deploy/field-results.md`에 반영한다.

**비목표**
- **부르는 곳의 기계식 자동 치환.** 「함께 고치기」는 명세 안의 작업으로 한다. 부르는 곳마다 사람이 작업 줄을 쓰고, 영향 탐색과 적용 뒤 확인이 빠진 곳을 알려 준다(Claude 결정). 이유는 두 가지다. 인수를 더하면 넘길 값을 정해야 하는데 이건 문자열 치환으로 정할 수 없다. 또 pelly의 원칙이 「모델이 고치고 코드가 판정하고 사람이 승인」이다.
- **CSS 선택자 변경과 쓰는 곳 찾기.** `pelly css`는 지금 선택자 변경을 막는다(W1). 이 문서도 그대로 둔다. 선택자 이름 바꾸기 요청이 현장에서 나오면 따로 정한다.
- `spec draft`가 js·css 작업을 제안하는 것. A2와 같다. 사람이 쓴 js·css 줄은 검사·적용된다.
- 브라우저 실행 검증. JS·CSS 설계와 같다.
- 객체 메서드의 동적 호출(`obj[name]()`, `window["fn" + kind]()`), `eval` 문자열 안의 호출, 다른 창의 함수(`opener.fnX()`, `parent.fnX()`). 찾지 않는다(요소 검사와 같은 판단).
- 쿼리 문자열 링크(`<a href="view.asp?no=1">`)와 `Request.QueryString`의 짝. 이번에는 폼과 ajax만 본다(§5.1).
- 서버 쪽 JScript.

**실패 조건 (기술적으로 돌아가도 실패로 본다)**
- 함수 이름을 바꾸는 작업이 끝났는데 옛 이름으로 부르는 곳이 남았고, 아무 경고도 없다.
- 모델이 명세 밖 단독 `pelly js`에서 몰래 함수 이름을 바꿔도 통과한다. 단독 실행은 지금처럼 막아야 한다.
- 함수 본문만 고쳤는데 `apply`가 부르는 곳 수십 개를 경고해서 확인을 묻는다. 사람이 경고를 무시하는 버릇이 생긴다(§4.4).
- 폼 필드 검사가 보내는 쪽을 다 알 수 없는 페이지(`serialize()`, 동적 필드 이름)에서 틀린 경고를 쏟아낸다.
- 편집 전부터 어긋나 있던 필드를 편집할 때마다 다시 경고한다.

## 3. 명세 문법

### 3.1 작업 줄

```
- [ ] T1 js js/order.js#fnSearch 페이지 번호 매개변수 page를 끝에 더한다 [G1]
- [ ] T2 js admin/order/list.asp#goPage T1의 fnSearch에 페이지 번호를 넘긴다 [G1]
- [ ] T3 asp admin/order/list.asp#L88-90 검색 버튼 onclick의 fnSearch 호출에 1을 넘긴다 [G1]
- [ ] T4 css css/admin.css#.search-box 상태 선택 칸 너비를 넓힌다
- [ ] T5 css admin/order/list.asp#L12-30 페이지 안 style 블록의 표 간격을 줄인다
```

- **종류 낱말 `js`·`css`:** 파서의 `cs|sql|asp` 세 곳(작업 줄, 작업 모양 줄, 체크박스 줄)에 더한다. A2와 같다.
  - 지금 정규식은 종류 낱말 뒤에 공백·낱말 경계를 요구하므로 `cs`와 `css`가 섞이지 않는다. 테스트로만 고정한다.
- **파일 확장자:**
  - `js`: `.js`, 그리고 `asp.extensions`와 `.htm`·`.html`(W2 페이지 블록).
  - `css`: `.css`, 그리고 같은 페이지 확장자.
  - 맞지 않으면 기존 `KindMismatch`다.
- **대상:**
  - `js`: `#이름`은 함수 하나다. `Obj.method`·`Obj.prototype.m` 같은 이름도 받는다(W1 `--function`과 같음). `#L시작-끝`은 줄 범위다.
  - `css`: `#선택자`는 공백 없는 선택자 하나다(`#.search-box`, `#td.num`). id 선택자는 `##main`처럼 쓴다. 공백이 있는 선택자(`.grid td`)는 작업 줄 문법상 쓸 수 없으니 `#L`을 쓴다(Claude 결정). `#L시작-끝`은 줄 범위다.
  - 대상이 없으면 오류다(`AspTargetRequired`와 같은 이유로 `WebTargetRequired`).
- **페이지 파일 대상:** `#이름`·`#선택자`는 페이지의 클라이언트 블록 안에서 찾는다(W2와 같음). `#L` 범위는 클라이언트 블록 하나 안에 완전히 들어 있어야 한다. 걸치면 `spec check` 오류이고, 문구는 「asp 작업으로 쓰십시오」다(W2 「`pelly asp --lines`를 쓰십시오」와 같음).

### 3.2 같은 파일의 줄 범위 작업

A2 §3.2 규칙을 종류와 상관없이 넓힌다.
- 같은 파일을 고치는 작업이 둘 이상이고, 그중 첫 작업이 아닌 작업이 `#L` 대상이면 오류다.
- 종류는 따지지 않는다. 같은 `.asp`를 asp 작업과 js 작업이 함께 고치는 경우가 흔하기 때문이다(목표 예의 T2·T3).
- 문제 코드는 기존 `AspLinesAfterEdit`를 일반 이름 `LinesAfterEdit`로 바꿀지, asp에만 두고 새 코드를 더할지 빌더가 정한다(§9).
- 위 예에서 T3(`#L`)은 같은 파일의 T2 뒤라서 오류가 된다. 그래서 예에서는 T3을 T2보다 앞에 두거나, T2를 `#L` 없이 둔다. README 예는 규칙에 맞게 쓴다.

### 3.3 `spec check`가 js·css 작업에 하는 검사

| 검사 | 문제 코드 | 수준 |
|---|---|---|
| 확장자가 맞지 않음 | `KindMismatch`(기존, 문구에 js·css 추가) | 오류 |
| 대상 없음 | `WebTargetRequired` | 오류 |
| `#이름` 함수·`#선택자` 규칙이 없음·여럿 | `SymbolNotFound`·`SymbolAmbiguous`(기존 코드 재사용) | 오류 |
| `#L` 범위가 파일 밖이거나 거꾸로 됨 | `LinesOutOfFile`(기존) | 오류 |
| 페이지 `#L`이 클라이언트 블록 하나에 들어 있지 않음 | `LinesOutsideBlock` | 오류 |
| 압축·라이브러리 파일(W1 판정) | `WebVendorFile` | 오류 |
| §3.2 | (§3.2 참고) | 오류 |
| 파일을 읽을 수 없음(인코딩) | `AspEncoding`와 같은 판정, 코드는 `WebEncoding` | 오류 |

`#L`을 `cs`·`sql`에 쓰면 지금처럼 `LinesNotSupported`다. js·css에서는 받는다.

문법·문법 수준·안전 같은 W1 판정은 `spec check`에서 하지 않는다. 적용할 때 파이프라인이 한다(A2와 같음).

## 4. JS 함수 서명 변경과 부르는 곳

### 4.1 apply가 js·css 작업을 실행하는 방식

- `FsmTaskExecutor`에 js·css 갈래를 더한다.
  - `RunRequest`에는 `Kind = EditKind.Js`·`Css`를 넣는다.
  - 대상은 W1 `--function`·`--selector`·`--lines`와 같은 값으로 넣는다.
- 파이프라인은 `FsmOrchestratorFactory`의 Js·Css 파이프라인을 그대로 쓴다. W2 블록 판정과 요소 검사도 포함된다.
- 그룹 규칙, 되돌리기, 결과 표시, 「그룹 없이 앞 작업만 적용됨」 경고는 A2 §4.1과 같다.
  - A2의 어긋남 경고는 sql + asp만 본다. W3에서는 서명을 바꾼 js 작업이 적용되고 뒤의 작업이 실패하면 같은 경고를 낸다. 문구는 「T1(js)은 적용됐고 T2는 실패했습니다. 함수와 부르는 곳이 어긋나 있을 수 있습니다」다.
- `apply.json` 작업 항목에는 `kind: "js"`·`"css"`와 대상(`function`·`selector`·`lines`)이 들어간다.

### 4.2 서명 변경 허용

- **명세의 js 작업**은 대상 함수(`#이름`)의 이름과 매개변수를 바꿀 수 있다(Claude 결정).
  - 그대로 막는 것: 함수 밖의 새 최상위 선언, 대상 함수가 사라지거나 둘로 늘어나는 것.
  - 다만 **대상 함수의 새 이름은 새 최상위 선언으로 치지 않는다.** 지금 `JsChecks.ShapeViolation`의 `TopLevelNames` 비교는 최상위 함수의 이름 변경을 늘 막으므로 예외를 둔다(빌더 확인 반영).
  - 바뀐 함수는 원래 대상과 **같은 자리**에서 찾는다. 같은 블록·파일 안에서 원래 대상과 같은 순번의 함수다. 이름이 같은 함수가 여럿인 경우는 지금 `Occurrence` 규칙을 따른다.
  - 대상을 이름으로 다시 찾는 곳은 모두 이 규칙을 따라야 한다. 지금은 `WebSlicePhase.RefindFunction`(재시도 때 대상 다시 찾기)과 `JsChecks.ShapeViolation`이 있다. 검증 단계 중 대상 함수 이름을 쓰는 곳이 더 있으면 함께 바꾼다. 목록은 계획에서 확정한다(빌더 확인 반영).
- **단독 `pelly js`**는 지금처럼 막는다. `--signature`를 주면 같은 규칙으로 허용한다. 막을 때 문구에 「부르는 곳도 고쳐야 하면 명세(js 작업)로 하거나 `--signature`를 쓰십시오」를 덧붙인다.
- 줄 범위 대상(`#L`)은 지금처럼 서명 검사를 하지 않는다. 다만 적용 뒤 확인(§4.5)은 범위 안의 함수 선언이 바뀌었는지 본다.
- **모델에게 알리기:** 서명 변경이 허용되면, JS 시스템 프롬프트의 「이름·매개변수를 바꾸지 마십시오」 줄을 「요청이 요구할 때만 바꾸십시오. 부르는 곳은 다른 작업이 고칩니다」로 바꾼 판을 쓴다. 프롬프트는 `system.js.txt`와 `system.js-page.txt` 둘이고, 각각 fewshot 판 번호와 맞춰야 한다(`PromptResources`, 빌더 확인 반영).
- **같은 명세의 뒤 작업이 옛 이름을 가리키는 경우 (Claude 결정, 빌더 확인 반영):** T1이 `js/order.js#fnSearch`를 `fnFind`로 바꾸고 T5가 다시 `js/order.js#fnSearch`를 대상으로 하는 경우다.
  - apply는 같은 파일의 옛 이름 대상을 새 이름으로 따라간다.
  - 결과에는 「T5의 대상 fnSearch는 T1이 바꾼 fnFind로 찾음」을 남긴다.
  - `spec check`는 이름이 바뀔지 미리 알 수 없으므로 막지 않는다.
- **asp 작업이 페이지 `<script>` 안 함수의 서명을 바꾸는 경우 (Claude 결정, 빌더 확인 반영):** 지금 asp 작업은 클라이언트 블록의 JS 모양을 검사하지 않으므로, 이미 이름을 바꿀 수 있다.
  - 막지는 않는다. W2 동작을 그대로 둔다.
  - §4.5 적용 뒤 확인을 asp 작업에도 적용한다. 편집 범위가 걸친 클라이언트 블록의 함수 선언을 편집 전후로 순서대로 짝지어 비교한다.
  - 단독 `pelly asp`에서는 검증 행 `JsSignature`(경고)로 「함수 서명 변경: … 부르는 곳 N곳」을 보인다.
- **결과 기록:** 서명이 바뀌면 `summary.json`에 `signatureChange: { before: "fnSearch(f)", after: "fnSearch(f, page)" }`를 남긴다. 검토 화면에는 「함수 서명 변경: …」 줄을 보인다.

### 4.3 사이트의 JS 호출 색인

W2 사이트 색인(`WebSiteIndex`, `.pelly/cache/`)에 JS 호출 항목을 더한다. SP 호출을 담은 것과 같은 방식이고, 캐시 판을 올린다(지금 3).

- **한 항목:** `(상대 경로, 줄, 함수 이름, 인수 개수 또는 모름, 출처)`. 출처는 셋 중 하나다.
  - `Js`: `.js` 파일의 호출.
  - `PageScript`: 페이지 클라이언트 `<script>` 블록 안의 호출.
  - `Attribute`: HTML 이벤트 속성(`on…="…"`)과 `href="javascript:…"` 안의 호출. VBScript 문자열 안의 HTML(`Response.Write "<a onclick=""fnX()"">"`)도 포함한다.
- **찾는 법:**
  - JS 코드는 `JsTokenScan.Mask`로 문자열·주석을 가린 뒤 `이름(`을 찾는다. 앞에 `.`이 붙은 것(`a.fnX(`)은 `Obj.method` 대상일 때만 그 전체 이름(`Common.fnX(`)으로 맞춘다.
  - 페이지 블록은 W2의 `PageBlockView`로 연다. `<% … %>` 문장이 섞인 블록도 자리 표시 뒤 문자열 수준으로 찾는다.
  - 호출 없이 이름만 넘기는 참조(`setTimeout(fnX, 100)`, `btn.onclick = fnX`, `$(…).click(fnX)`)는 인수 개수를 「참조」로 남긴다. 이름 바꾸기의 영향에는 들어가고, 인수 개수 비교에서는 뺀다.
  - 선언 자체(`function fnX(`)는 호출로 세지 않는다.
- **인수 개수:** 괄호 짝을 맞춰 최상위 쉼표로 센다. 인수 안에 `<%= %>` 자리 표시가 있어도 센다. 짝이 맞지 않으면 「모름」이다.
- **범위:** `asp.siteRoot` 아래의 `.js`와 페이지 확장자 파일이다. W1의 라이브러리·압축 파일(`web.vendorPaths`)은 뺀다. 파일 수 상한은 지금 색인과 같이 2000이다.
  - 지금 `spec check`의 색인은 설정의 `web.vendorPaths`를 쓰지 않고 기본값을 쓴다(`SpecChecker`가 `new WebOptions()`를 씀). `AspImpactRequest`에 `WebOptions`를 넘기도록 고친다(빌더 확인 반영).
- **`<script src>` 관계:** 지금 색인에는 없고, `PageScripts`가 그때그때 푼다(빌더 확인 반영).
  - 페이지(와 include)가 부르는 `.js` 상대 경로 목록을 색인 항목에 더한다.
  - §4.3의 「이 페이지는 … 부르지 않음」과 W3b의 ajax 주소 풀기(§5.1)가 함께 쓴다. 그래서 W3a에서 만든다.
- **이름 기준의 한계:** 이름이 같은 다른 함수(서로 다른 페이지에 같은 이름의 지역 함수가 있는 경우)도 함께 찾힌다. C#의 이름 기준 영향 탐색과 같이 받아들이는 틀린 맞음이다.
  - 다만 페이지 블록 안의 호출은, 그 페이지(와 include)가 같은 이름을 직접 선언하면 그 선언에 묶인 것으로 보고 다른 파일의 함수 영향에서 뺀다(Claude 결정).
  - 페이지가 그 이름을 선언하지 않으면, 그 페이지가 `<script src>`로 부르는 `.js` 중에 대상 파일이 있는지 본다. 없으면 「(이 페이지는 js/order.js를 부르지 않음)」을 붙여 경고한다. 빼지는 않는다. `<script src>`를 include가 넣는 경우가 흔하기 때문이다.

### 4.4 `spec check --impact`의 JS 영향 탐색

- **씨앗:** 완료되지 않은 js 작업 중 `#이름` 대상의 함수다. `#L` 대상은 씨앗이 아니다. 범위 안에 함수 선언이 있으면 「줄 범위 대상이라 부르는 곳을 찾지 않았습니다」를 경고 한 줄로 보인다.
- **찾는 것:** §4.3 색인에서 이름이 같은 호출.
- **명세에 있는지 판정:** A2 §4.3과 같다.
  - 같은 파일의 작업(js·asp 종류 모두) 대상 안에 있으면 「명세에 있음」이다. 함수 대상이면 그 함수 안, 줄 범위면 그 범위 안이다.
  - `Attribute` 호출은 그 줄을 덮는 asp 작업(`#L` 또는 그 줄을 감싼 프로시저)이 있을 때만 「명세에 있음」이다.
- **경고 문구:** 「작업 T1의 영향 대상이 명세에 없습니다: admin/order/view.asp:88 (fnSearch 호출, 인수 1개, onclick)」.
- **상한:** 함수 하나당 10개까지 보이고 나머지는 「외 N곳」이다. 전체 목록은 `.pelly/impact/<명세>-js.json`에 쓴다.
- **`pelly apply`의 사전 영향 탐색에는 넣지 않는다(Claude 결정).** apply는 이 경고로 확인을 묻지 않는다. 함수 본문만 고치는 작업이 더 흔하고, 그때 부르는 곳 경고는 쓸모가 없다(§2 실패 조건). apply에서는 실제로 서명이 바뀐 경우만 §4.5에서 경고한다.
  - A2의 SP 영향은 apply가 확인을 묻는다. 이 점이 다르다는 것을 README에 적는다.

### 4.5 적용 뒤 확인 — 서명이 바뀐 함수

- **비교:** js 작업이 「적용됨」이 되면, 그 작업 실행 전 백업과 바뀐 파일에서 대상 함수의 이름과 매개변수 목록을 비교한다(§4.2의 「같은 자리」 규칙). `#L` 작업과 asp 작업(§4.2)은 범위가 걸친 블록의 함수 선언을 순서대로 짝지어 비교한다.
  - `--resume`으로 이미 완료된 작업은 비교하지 않는다(A2 §4.5와 같음).
- **apply가 끝난 뒤 남은 호출을 찾는다:** 모든 작업이 끝난 뒤의 파일로 색인을 다시 읽는다. 캐시는 파일 해시로 갱신된다.
  - **이름이 바뀐 경우:** 옛 이름의 호출·참조가 남아 있으면 경고한다. 사이트 어딘가에 옛 이름의 선언이 아직 있으면, 「(다른 선언이 있음: js/old.js:12)」를 덧붙인다.
  - **매개변수 개수가 바뀐 경우 (Claude 결정, 빌더 확인 반영):** apply가 끝난 뒤의 파일에서, 그 함수의 호출 중 인수 개수가 새 매개변수 수와 다른 것을 경고한다.
    - 「참조」와 「모름」은 뺀다.
    - 명세가 덮었는지는 보지 않는다. 덮은 작업이 고치지 못한 호출도 알려야 하기 때문이다. 또 편집 뒤에는 줄 번호가 밀려 대상 범위로 판정하기 어렵다.
  - 매개변수를 끝에만 더했으면 「기존 호출은 새 인수가 undefined로 동작함」을 덧붙인다. 막지는 않는다.
  - **개수는 같고 이름·순서만 바뀐 경우:** 인수 개수로는 판정할 수 없다. 「fnSearch의 매개변수 순서·이름이 바뀌었습니다. 부르는 곳 N곳을 확인하십시오」와 호출 목록(상한 10)을 보인다.
- **문구:** 「fnSearch의 서명이 바뀌었습니다: fnSearch(f) → fnSearch(f, page). 고치지 않은 호출: admin/order/view.asp:88 외 2곳」.
- **기록:** `apply.json`에 `jsCallersNotUpdated`, `pelly report`에 「JS 서명 변경 뒤 고치지 않은 호출 N곳」.
- 이 경고는 종료 코드를 바꾸지 않는다(A2 §4.5와 같음).
- 색인이 상한 2000에서 잘렸으면 「사이트 파일이 많아 일부 호출을 보지 못했을 수 있습니다」를 덧붙인다.

### 4.6 뒤 작업의 모델 입력에 바뀐 서명

- 같은 apply에서 앞선 js 작업이 서명을 바꿨고 뒤의 js·asp 작업 대상이 옛 이름이나 새 이름을 부르면, 모델 입력의 READ-ONLY 영역에 한 줄을 보인다. 「T1이 바꾼 함수: fnSearch(f, page) (원래 fnSearch(f))」.
- 전달은 A2의 `ChangedProcedures`처럼 `TaskRunOptions`에 바뀐 서명 목록을 더해서 한다.
- js 작업은 지금 「대상이 부르는 함수의 선언 줄」을 이미 보인다(`WebSlicePhase`). 바뀐 서명 줄은 그 앞에 둔다.
- asp 작업은 JS 선언을 보이지 않는다. 대상 범위 안에 그 이름이 있을 때만 위 한 줄을 더한다.
- JS 이름 검사(`JsNamesStep`)는 색인을 파일에서 다시 읽으므로, 이름을 바꾼 뒤의 새 이름을 이미 안다. 바꿀 것이 없다(확인만).

## 5. 폼 필드 이름 짝 검사

### 5.1 무엇을 짝짓는가

- **판단 기준 (Claude 결정, 빌더 확인 반영):** 확실히 아는 짝만 경고한다. 모르면 「열림」이나 「주소 모름」으로 두고 경고하지 않는다. 틀린 경고가 놓침보다 해롭다(§2 실패 조건).
- **읽는 쪽(서버 페이지 P):** P와 P가 include하는 파일의 서버 코드에서 다음 셋을 읽는다. 키는 문자열 리터럴일 때만 센다.
  - `Request.Form("k")` — 폼 값.
  - `Request("k")` — 폼 또는 쿼리 문자열.
  - `Request.QueryString("k")` — 짝 검사에 쓰지 않는다(비목표). 다만 GET 폼이 보내는 값이면 맞는 것으로 친다.
  - `For Each k In Request.Form`처럼 키를 모르게 읽으면 P는 「모두 읽음」으로 보고, P를 대상으로 하는 「보내지 않음」 경고는 내지 않는다.
- **보내는 쪽(P로 보내는 것):**
  - `<form action="P">` 안의 `<input>`·`<select>`·`<textarea>`·`<button>`의 `name`. `method`가 없으면 GET이다.
  - **action을 JS가 정하는 폼 (Claude 결정, 빌더 확인 반영):** 백오피스에서는 `<form name="frm" method="post">`에 action을 두지 않고 `frm.action = "save.asp"; frm.submit()`으로 보내는 일이 흔하다(Claude 짐작). `document.frm.action = …`이나 `$("#frm").attr("action", …)`도 쓴다.
    - 같은 페이지의 JS(페이지 블록과 그 페이지가 부르는 `.js`)에서, 그 폼의 이름·id에 리터럴 action을 대입하는 곳을 찾는다. 찾은 주소마다 보내는 쪽 하나로 센다.
    - `"save.asp?mode=" + m`처럼 쿼리 부분만 이어 붙이면 쿼리를 떼고 리터럴로 본다. 주소가 변수이거나 `<%`가 섞이면 그 폼은 「주소 모름」이고 짝짓지 않는다.
    - action 속성도 JS 대입도 없으면 그 페이지 자신으로 본다(HTML 규칙).
  - **서버 코드가 쓰는 필드 (Claude 결정, 빌더 확인 반영):**
    - 폼 안의 VBScript 문자열에 리터럴로 들어 있는 이름은 센다. `<% Response.Write "<input name=""k"">" %>`가 그 예이고, 요소 검사의 `""` 규칙과 같다.
    - `<% If %>`로 감싼 필드도 센다. 분기 합집합이다.
    - 다음 경우에는 그 폼이 「열림」이다. 이름이 문자열 리터럴이 아니다(VBScript `&`로 이어 붙인 이름). 또는 폼 안의 서버 코드가 다른 함수를 불러 HTML을 쓴다.
  - jQuery ajax: `$.ajax({ url: "P", data: { k: … } })`, `$.post("P", { k: … })`, `$.get("P", { … })`. `data`가 객체 리터럴이고 키가 리터럴일 때만 필드를 안다.
  - 위의 `<form>` 안에 들어간 필드라도 이름에 `<%`가 있으면 접두로 본다(요소 검사의 `row*` 규칙과 같음).
- **필드를 다 알 수 없는 보내는 쪽은 「열림」이다:** `data: $(f).serialize()`, `new FormData(…)`, 변수, 함수 호출 결과, 그리고 JS가 필드를 더하는 폼이 해당한다. JS가 필드를 더하는 폼이란, 그 폼에 `append`·`appendChild`·`.html(`·`.innerHTML`을 쓰는 코드가 같은 페이지에 있는 경우다(Claude 결정 — 문자열 수준의 짐작).
- **주소 맞추기:**
  - `/`로 시작하면 사이트 루트에서, 아니면 그 폼이 있는 페이지의 폴더에서 찾는다.
  - `.inc` 안의 폼은 그 `.inc`를 include하는 각 페이지의 폴더에서 찾는다.
  - `.js` 안의 ajax 주소는 그 `.js`를 `<script src>`로 부르는 각 페이지의 폴더에서 찾는다. 브라우저가 페이지 주소를 기준으로 풀기 때문이다.
  - 쿼리 문자열·`#`은 떼고, 대소문자는 무시한다(IIS).
  - `http://`·`https://`·`//`로 시작하는 주소, `<%`가 섞인 주소, 사이트에 없는 파일은 짝짓지 않는다.

### 5.2 경고 규칙 — 편집이 새로 만든 어긋남만

요소 검사와 같이, 편집 전과 편집 후의 어긋남 개수를 (종류, 페이지, 키)별로 비교해 **늘어난 것만** 경고한다.

- **한 저장 페이지를 여러 폼이 쓰는 경우 (Claude 결정, 빌더 확인 반영):** 등록·삭제처럼 모드마다 다른 폼이 같은 P로 보내는 일이 흔하다. 그래서 「보내는 쪽마다」 세지 않고 아래 두 규칙으로 센다.
- **「보내지 않음」 — 보내는 쪽이 바뀐 경우만 센다:** 편집된 보내는 쪽 S가 편집 전에는 키 k를 보냈는데 편집 뒤에는 보내지 않고, P는 k를 `Request.Form`이나 `Request`로 읽는다.
  - S가 「열림」이 아니고 P가 「모두 읽음」이 아닐 때만 센다.
  - 원래부터 S가 보내지 않던 키는 세지 않는다. 다른 모드의 키일 수 있기 때문이다.
  - 문구: 「admin/order/save.asp가 읽는 custNo(줄 14)를 list.asp의 폼(줄 40)이 보내지 않음, 보내는 비슷한 이름: custId」. 「비슷한 이름」은 대소문자만 다르거나, 그 보내는 쪽에만 있고 P가 읽지 않는 이름이 하나뿐일 때 보인다.
- **「아무도 보내지 않음」 — 읽는 쪽이 바뀐 경우:** P가 새로 읽기 시작한 키 k(이름을 바꾼 키 포함)를 어떤 보내는 쪽도 보내지 않는다.
  - 한 곳이라도 보내면 통과다.
  - P로 보내는 쪽이 하나 이상 있고, 그 보내는 쪽이 모두 「열림」이 아닐 때만 센다.
  - 보내는 쪽이 하나도 없는 페이지는 경고하지 않는다. 다른 사이트나 바깥 시스템이 보내는 페이지일 수 있기 때문이다.
- 보내기만 하고 읽지 않는 필드는 경고하지 않는다. 남는 필드는 해가 없다.
- **보는 범위:** 편집된 파일이 읽는 쪽이면 그 페이지로 보내는 쪽 전체(색인)를 본다. 편집된 파일이 보내는 쪽이면 그 파일이 보내는 대상 페이지들을 본다. 둘 다일 수 있다.

### 5.3 어디서 보이는가

- **검증 행(경고만):** `pelly asp`에는 `FormFields`, `pelly js`에는 `Fields`를 더한다. 표시 이름은 둘 다 「폼 필드」다.
  - 실행 조건: 읽는 쪽·보내는 쪽 어느 것도 편집 전후에 없으면 행을 만들지 않는다. `pelly js`가 `.js`를 고치는 경우도 ajax가 있으면 행을 만든다.
  - 색인을 읽지 못하면 「건너뜀(사이트 색인을 읽지 못함)」이다(요소 검사와 같음).
  - 사이트 색인 Lazy는 요소 검사·클라이언트 경고와 함께 쓴다.
- **apply 끝:** 같은 apply 안에서 앞 작업이 서버 페이지의 키를 바꾸고 뒤 작업이 폼을 고치면, 앞 작업의 검증 행에 잠시 경고가 생긴다. 그래서 apply가 끝난 뒤 한 번 더 본다.
  - 「이번 apply에서 적용된 파일 전체의 편집 전(백업) 대 편집 후」로 §5.2를 다시 계산한다.
  - 남은 경고만 결과 끝과 `apply.json`의 `formFieldMismatches`에 보인다.
  - 작업별 검증 행의 경고는 그대로 둔다. 기록이기 때문이다.
  - 결과 끝에 「작업 중 경고 N건 중 M건은 뒤 작업이 해결함」을 한 줄 보인다(Claude 결정).
- 종료 코드는 바꾸지 않는다.

### 5.4 색인

W2 색인 파일 항목에 다음 둘을 더한다. 캐시 판은 §4.3과 함께 한 번만 올린다.

- **읽음:** `(키, 출처 Form|Any|QueryString, 줄)`, 그리고 「모두 읽음」 표시.
- **보냄:** `(원문 주소 또는 주소 모름, 방식 GET|POST, 필드 목록 또는 열림, 줄, 종류 form|ajax, 폼 이름·id)`.
- **JS의 action 대입:** `(폼 이름·id, 원문 주소, 줄)`. 폼과의 짝짓기는 색인을 읽을 때 한다.

캐시 판은 W3a 판에서 한 번 더 올린다. 주소 풀기(§5.1)는 색인을 읽을 때 한다. include·`<script src>` 관계가 다른 파일에 달려 있어서 파일별 캐시에 넣을 수 없기 때문이다.

## 8. 검증 (pelly 자체 테스트)

- **파서:** `js`·`css` 줄, `cs`와 `css`가 섞이지 않음, `#Obj.method`, `##id` 선택자, `#L`, 그룹·완료 표시와 함께.
- **spec check:** §3.3 표의 각 줄, 페이지 `#L`이 블록 밖이면 오류, §3.2가 종류를 가리지 않음.
- **apply:**
  - js·css 작업 실행, 그룹 안 sql·asp·js 섞기, 그룹에서 js 실패 시 모두 원래 바이트로 복원.
  - 서명을 바꾼 js 작업 뒤 실패하면 어긋남 경고.
- **서명 변경:**
  - 명세 js 작업에서 이름·매개변수 변경은 통과하고, 새 최상위 선언은 거절한다.
  - 단독 `pelly js`는 거절하고 안내 문구를 보인다. `--signature`면 통과한다.
  - 이름이 같은 함수 둘 중 하나를 바꿔도 「같은 자리」로 찾는다.
  - 최상위 함수의 이름을 바꿔도 「새 최상위 선언」으로 막히지 않는다. 재시도 때 대상을 다시 찾을 때도 같다.
  - 같은 명세의 뒤 작업이 옛 이름을 가리키면 새 이름으로 따라가고, 결과에 그 사실을 남긴다.
  - asp 작업이 블록 안 함수 서명을 바꾸면 `JsSignature` 경고 행이 생기고, apply 뒤 확인에도 들어간다.
- **호출 색인:**
  - `.js`, 페이지 블록, `onclick`, `href="javascript:"`, VBScript 문자열 안 속성, 참조(`setTimeout(fnX)`), 주석·문자열 안은 뺌, 선언은 뺌.
  - `Common.fnX(` 이름, 인수 개수(중첩 괄호·`<%= %>`), 짝이 맞지 않으면 모름.
  - 같은 이름을 직접 선언한 페이지는 뺌.
- **영향 탐색:** 명세 안/밖 판정(함수 대상, 줄 범위, onclick과 asp `#L`), 상한 10과 「외 N곳」, 전체 목록 파일, apply 사전 탐색에서는 경고 없음.
- **적용 뒤 확인:**
  - 이름 변경 후 옛 이름이 남으면 경고하고, 다른 곳에 옛 이름 선언이 있으면 덧붙임.
  - 매개변수 추가 후 고치지 않은 호출을 경고하되, 인수 개수가 맞는 호출은 뺌. 끝에 더한 경우 덧붙임 문구.
  - 서명이 그대로면 경고 없음.
- **바뀐 서명 전달:** 뒤 js 작업과 asp 작업의 모델 입력에 바뀐 서명 줄이 보임. 단독 실행에는 없음.
- **폼 필드(W3b):**
  - 읽음 세 가지와 「모두 읽음」. 보냄 form·ajax와 「열림」(serialize·변수·JS로 필드 추가).
  - JS의 action 대입 세 모양(`frm.action =`, `document.frm.action =`, `.attr("action", …)`), 쿼리를 이어 붙인 주소, 「주소 모름」.
  - VBScript 문자열 안 필드, `<% If %>` 안 필드, 이어 붙인 이름이면 「열림」.
  - 등록·삭제 두 폼이 같은 저장 페이지로 보낼 때, 한쪽만 보내는 키를 새로 읽어도 경고하지 않음.
  - 주소 풀기: 상대·루트·`.inc`·`.js`·외부·`<%`.
  - 새 어긋남만 경고하고, 이미 있던 어긋남은 다시 경고하지 않음. 「비슷한 이름」 힌트.
  - 보내는 쪽이 없는 페이지는 경고하지 않음. apply 끝 재계산으로 뒤 작업이 해결한 경고가 빠짐.
- **단독 실행:** W1·W2의 `pelly js`·`pelly css`·`pelly asp` 결과가 바뀌지 않음. 새 행 말고는 기존 테스트 그대로다.
- **게이트:** `dotnet build -warnaserror` 종료 0, `dotnet test` 실패 0.
- **예비 측정:**
  - W3a: `eval/benchmark/web/`에 명세 사례 3건(js 서명 변경 + 부르는 js·asp 작업 그룹, 매개변수 추가인데 부르는 곳 하나를 명세에서 뺌, css 작업 하나). 기록은 `docs/web-premeasure.md` W3 절.
  - W3b: 기존 asp·web 벤치마크를 다시 돌려 「폼 필드」 틀린 경고가 0인지 보고, 필드 이름을 어긋나게 고치는 사례 2건을 더한다.

## 9. 빌더에게 맡기는 것

- `SpecTask`에 css 선택자 대상을 담는 방식(`Symbol` 재사용 여부).
- §3.2 문제 코드 이름(`AspLinesAfterEdit` 일반화 또는 새 코드). 기존 출력·테스트가 깨지지 않게 한다.
- 색인 항목 자료형, 캐시 판 번호, JS 호출 찾기를 `JsTokenScan` 위에 둘지 Acornima 해석 결과로 할지. 해석에 실패한 파일도 마스크 방식으로는 찾을 수 있어야 한다.
- 「같은 자리」 함수 짝짓기의 정확한 규칙(§4.2).
- js 시스템 프롬프트의 서명 변경 판을 파일 하나로 둘지, 한 줄을 끼워 넣을지.
- 폼 필드 경고 문구의 세부와 「비슷한 이름」 판정.
- 코퍼스(`eval/corpus/Asp/`)에 더할 페이지: 같은 JS 함수를 부르는 `.js`·페이지·`onclick` 세 곳, 저장 페이지와 그 폼 페이지 한 쌍, ajax 저장 한 쌍.

## 10. 사람이 확인할 것

**결정 (아래 Claude 결정 중 바꾸고 싶은 것)**
1. 「부르는 곳 함께 고치기」는 명세 작업 + 영향 경고로 한다. 기계식 자동 치환은 하지 않는다(§2 비목표).
2. 명세의 js 작업은 서명 변경을 늘 허용한다. 단독 `pelly js`는 `--signature`를 줄 때만 허용한다(§4.2).
3. JS 영향 경고는 `spec check --impact`에서만 보인다. apply는 사전 영향으로 확인을 묻지 않고, 실제로 서명이 바뀐 뒤에만 경고한다(§4.4·§4.5).
4. CSS 선택자 변경은 이번에도 막는다(§2 비목표).
5. 폼 필드 검사는 폼과 jQuery ajax만 본다. 쿼리 문자열 링크는 보지 않는다(§5.1).
6. W3a·W3b 두 계획으로 나눈다(§7).
7. 매개변수 개수가 바뀌면, 명세가 덮었는지와 상관없이 인수 개수가 맞지 않는 호출을 모두 경고한다(§4.5).
8. asp 작업이 페이지 안 JS 함수 서명을 바꾸는 것은 막지 않고 경고만 한다(§4.2).
9. 한 저장 페이지를 여러 폼이 쓰면, 「한 곳이라도 보내면 통과」로 센다. 보내는 쪽 경고는 그 보내는 쪽이 원래 보내던 키를 뺄 때만 낸다(§5.2).

**현장 (`deploy/field-results.md` 17절에 더함)**
- 공용 JS 함수를 몇 곳에서 부르는가, `onclick` 속성으로 부르는 비율.

- 실제 요청 1건을 js + asp 명세로 돌린 결과.
