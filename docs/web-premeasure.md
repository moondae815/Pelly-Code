# pelly js·pelly css 예비 측정

> **예비 — 현장 측정 별도.** 에이전트가 개발 맥(macOS)의 로컬 Ollama로 잰 값이다. 사례 12건 × 3회, 표본이 작고 코퍼스 파일이 짧아(최대 54줄) 비율보다 **판정이 무엇을 잡고 무엇을 놓치는지**를 읽는 자료다. KPI 판정에는 쓰지 않는다(설계 §9). 브라우저에서 실행해 본 결과는 없다(pelly도 실행하지 않는다). 현장 확인은 `deploy/field-results.md` 17절에 사람이 적는다.

설계: [docs/superpowers/specs/2026-11-04-pelly-js-css-design.md](superpowers/specs/2026-11-04-pelly-js-css-design.md) §9 · 사례와 실행기: `eval/benchmark/web/`

## 1. 요약

- **36/36** 실행 모두 종료 코드 0(성공)이고, 모두 **첫 시도**에 통과했다(재시도 0회). 예상 문자열 판정(`mustContain`·`mustKeep`·`mustNotContain`)도 36/36 맞았다. 사례마다 `mustContain`에 원본에 없는 문자열이 하나 이상 있어, 요청한 변경이 실제로 들어갔는지를 본다(2절 「사례 검사」).
- 편집 영역 밖 바이트는 36/36 원본과 같았다(CP949 한글 파일, CRLF·LF가 섞인 순수 ASCII `edit.js` 포함). 검사 실패(패치·인코딩·문법·문법 수준·대상 모양·안전·구조)와 경고(이름·API·속성·덮어쓰기)는 한 번도 나지 않았다.
- **ES5 수준 함정 사례(js-007·008) 2건에서 모델은 최신 문법을 한 번도 쓰지 않았다.** 요청이 화살표 함수·템플릿 문자열·`const`를 허락하거나 시켜도 `var`와 보통 문자열로 썼다. 그래서 **문법 수준 거절은 0회**이고, 수준 거절 → 피드백 → 재시도 경로는 이번 측정에서 실제 모델로 재지 못했다(가짜 모델 테스트로만 확인됨). 모델 입력 [READ-ONLY: env]의 「ES5 — let/const/화살표 함수/… 금지」가 먹힌 것으로 본다.
- 사람이 diff를 읽고 틀렸다고 본 결과는 **없다.** 다만 js-008 사례는 요청의 일부(`const`·템플릿 문자열)를 말없이 따르지 않았고(관찰 1), jQuery를 쓰지 않던 `common.js`에 `$` 호출이 새로 들어간 결과가 있었다(관찰 2).
- 전체 걸린 시간 **95초**(실행당 평균 2.4초, 모델 생성 평균 1.5초). 생각 토큰은 0(생각 모드 `retry`, 재시도가 없음).

## 5. 관찰 (결과 diff를 읽고)

기록 원본(사례별 `console.log`, `summary.json`, 결과 파일, `run/attempt-*/`)은 로컬 임시 폴더에 두었고 저장소에 포함하지 않는다.

1. **js-008: 최신 문법 요청을 말없이 따르지 않음(3/3).** 「변수는 `const`로, 알림 문구는 템플릿 문자열로」를 시켰지만 모델은 `var`(2회 `trimmedName`, 1회 `name`)와 보통 문자열을 썼다(ES5 파일이라 맞는 선택). 공백 제거는 정규식 `replace` 2회, `$.trim` 1회였다. 요청과 결과가 다른데 검토 화면에는 이유가 나오지 않는다. 사람이 diff를 보고 판단해야 한다. 순수 ASCII 파일에 한글 알림을 넣어 검토에 「이 파일은 ASCII였고 CP949로 저장했습니다」가 3/3 나왔고, 줄 끝이 섞인 파일의 범위 밖 바이트도 그대로였다.
2. **jQuery를 쓰지 않던 공용 파일에 `$`가 들어감.** js-001 사례는 `$.isArray(v)`로 배열을 가렸고(3/3), js-004 사례는 `$("#dateError").text(…)`를 썼다(3/3). `common.js` 원본은 jQuery 없이 쓰인 파일이다. 사이트에서 jQuery를 찾았으므로 이름 검사는 `$`를 아는 이름으로 보고 경고하지 않았고, `$.isArray`(1.3 버전부터)도 1.8.3 기준 API 표에 걸리지 않는다. 결과는 맞지만, 이 공용 파일을 jQuery 없이 부르는 페이지가 있으면 그 페이지에서 오류가 난다. 파일 하나로는 부르는 페이지를 알 수 없는 W1 단계의 한계이고(W2 단계에서 페이지 기준으로 보완), 사람이 diff에서 확인할 부분이다.
3. **js-007: 최신 문법 허락에도 ES5.** 3/3 모두 `if (isNaN(n)) return "";` 한 줄을 함수 첫 줄에 더했다. 큰따옴표도 원본 모양을 따랐다.
4. **이름 검사가 사이트 색인을 썼다.** js-002 사례는 다른 파일(`common.js`)의 `isEmpty`를 불렀고 경고가 없었다(사이트 색인). js-006 사례는 `$(this)`만 썼다. `web.globals`의 `gfnOpenPopup`을 새로 쓴 사례는 없었다.
5. **CSS IE 핵은 기준선으로 통과했다.** css-002(`*zoom: 1` 같은 줄)와 css-004(`filter: progid:DXImageTransform…`, `color: red\9` 선언이 있는 규칙)에서 구조 검사·속성 경고가 하나도 나지 않았고 모델도 핵 줄을 건드리지 않았다(css-004 보존 확인 3/3). css-003 사례는 `@media print` 안에 새 규칙 `.btn_blue { display: none; }`을 더했다(줄 범위 대상이라 허용, 덮어쓰기 알림 없음).
6. **너무 쉬운 사례일 수 있다.** 파일이 짧고 요청이 한두 줄 변경이라 첫 시도 100%는 일반 성공률이 아니다. 재시도·검사 실패 분포, 문법 수준 거절, 이름·API·속성 경고는 이번에 보지 못했다.

## 6. 의미와 한계

- 표본이 작고(12건 × 3회) 같은 입력에 모델 출력이 거의 같았다. 3회 반복은 분산보다 재현성을 보여 준다.
- **문법 수준 판정의 실제 효과는 재지 못했다.** 이 모델은 [READ-ONLY: env]의 수준 힌트만으로 ES5 문법을 지켰다. 수준 검사는 힌트를 어긴 경우의 마지막 방어선이고, 그 경로(거절 → 영어 피드백 「arrow functions」 등 → 재시도)는 테스트로만 확인했다. 현장 요청이 길거나 파일이 클 때 다를 수 있다.
- **예상 문자열 판정과 pelly 판정은 「요청한 것이 들어갔는가」만 본다.** 요청 일부를 따르지 않은 수정(관찰 1), 공용 파일에 새 의존을 들인 수정(관찰 2) 모두 사람이 diff를 읽어야 보인다. 브라우저에서 실행하지 않으므로 화면 동작은 확인하지 않았다. 검토 화면의 고정 문구가 이 한계를 알린다.
- 사례 위치는 `eval/benchmark/web/`이다(설계 §9 원문은 `eval/benchmark/tasks/`. 전용 실행기 `run.sh`와 함께 둠, 기존 벤치마크 50건 집합에 섞지 않음 — ASP와 같은 결정).
- 개선 후보: (1) 더 큰 JS 파일(수백 줄 `ready` 함수), jQuery 기준 버전에서 없어진 API(`.live`·`$.browser` 등)를 부르기 쉬운 요청, 원본이 해석되지 않는 `legacy/broken.js` 사례로 보강, (2) 요청과 수준 규칙이 부딪칠 때(관찰 1) 검토에 「요청한 최신 문법을 쓰지 않았습니다」 같은 알림을 줄지 검토, (3) 원본이 쓰지 않던 `$`·`jQuery`를 새로 쓰면(관찰 2) 이름 경고로 알릴지 검토.

## W2-5. 관찰

기록 원본(사례별 `console.log`, `summary.json`, 결과 파일, `run/`)은 로컬 임시 폴더에 두었고 저장소에 포함하지 않는다.

1. **page-004: 판정은 통과했으나 대상 요소를 잘못 짚음(3/3).** 모델은 `$("#custId").focus()`를 썼는데 페이지의 입력칸은 `name="custId"`만 있고 `id`가 없다. 문법·이름·API 검사와 예상 문자열은 이를 잡지 못한다(셀렉터 문자열은 검사 대상이 아니다). 브라우저에서 실행하면 포커스가 가지 않는다. 사람이 diff에서 확인할 부분이다.
2. **page-003: 서버 코드가 섞인 블록은 낮춘 판정이다.** `<% If %>`로 갈라진 함수라 문법·수준·이름·API 검사가 건너뛰어졌다(`skipped`). 이번 요청은 문구 하나만 바꿔 문제가 없었지만, 이런 블록에서 문법 오류를 만들어도 pelly가 잡지 못한다는 뜻이다. 검토 화면의 고정 문구가 이를 알린다.
3. **서버 코드 자리는 한 번도 건드리지 않았다.** `<%= %>`가 든 줄(page-006, page-008)과 `<% If %>` 줄(page-003)을 모델이 그대로 두었고 `WebServerCodeChanged` 거절은 나지 않았다. 이 거절 경로는 이번에도 가짜 모델 테스트로만 확인됨.
4. **ES5 유지.** page-007 사례는 최신 문법을 허락했지만 모델은 문자열 한 곳만 바꿨다. page-005는 `className` 한 줄을 삼항식으로 더했다(ES5).
5. **너무 쉬운 사례일 수 있다.** 파일이 짧고 요청이 한두 줄 변경이라 첫 시도 100%는 일반 성공률이 아니다. 재시도·거절 경로와 `WebBlockChanged`·`WebOutsideBlock`는 이번에 보지 못했다. 페이지 기준 jQuery 버전(`inc/header.inc`가 부르는 `lib/jquery-1.8.3.min.js`)이 이름 검사에 반영되는지도 이 사례들로는 가려내지 못했다.

|---|---|---|
| page-001·002·003·005·006·007 (JS) | 18/18 종료 0, 첫 시도 | 18회 모두 통과(새 경고 없음) |

1. **관찰 1(page-004)이 이제 검토 화면에 보인다.** 모델은 세 번 모두 `$("#custId").focus()`를 썼다. 막지는 않으므로 실행은 여전히 성공(종료 0)이지만, 검토 줄의 「요소 경고」와 name 힌트로 사람이 diff를 보기 전에 알 수 있다.
2. **다른 사례에서 틀린 경고는 없었다.** page-003(`<% If %>`가 섞인 블록)과 page-006·008(`<%= %>` 자리)도 경고가 없었다.
3. **한계:** 사례가 작고, 모델이 요소를 새로 찾는 수정은 page-004 하나뿐이다. include·includer에만 있는 입력 칸, 서버 코드로 만든 id는 가짜 모델 테스트로만 확인했다.
