# pelly 페이지 요소 검사 (id·name) 설계

- 날짜: 2026-11-09
- 단계: V2-7 W2 뒤의 작은 추가. W3(명세에 js·css 작업) 앞에 한다.
- 관련: W2 설계 `docs/superpowers/specs/2026-11-06-pelly-web-w2-design.md`, 예비 측정 `docs/web-premeasure.md` W2 절 관찰 1(page-004)
- 사람 결정: 「질문 없이 바로 설계」(2026-11-09). 아래의 결정은 따로 표시하지 않으면 모두 Claude 결정이다.

## 1. 왜

W2 예비 측정 page-004에서 모델이 `$("#custId").focus()`를 썼다. 그런데 페이지의 입력 칸에는 `name="custId"`만 있고 `id`가 없었다. 문법·이름·API 검사를 모두 통과했지만 브라우저에서는 포커스가 가지 않는 틀린 수정이었고, 지금은 사람이 diff를 읽어야만 알 수 있다.

현장 답(2026-11-06)에 따르면 JS 수정은 대부분 페이지 안에서 일어난다. 페이지 JS는 같은 페이지의 입력 칸·폼을 id나 name으로 찾는 일이 많아서, 이런 실수를 경고 한 줄로 알려 주는 효과가 크다.

## 2. 목표

1. 편집 때문에 **새로** 생긴 「페이지에 없는 id·name을 가리키는 JS 참조」를 경고 행 `JsElements`로 알린다. 막지는 않는다.
2. `pelly js`(페이지 대상)와 `pelly asp`(페이지) 두 경로 모두에서 같은 규칙으로 판정한다. `pelly asp --lines`가 HTML에서 id를 지우는 바람에 기존 JS 참조가 끊기는 경우도 같은 규칙으로 잡는다.
3. 경고 문구에는 무엇이 없는지와, 비슷한 것이 있으면 그것을 적는다. 예: 「`#custId` — id 없음, name="custId"는 있음(줄 98)」.

## 3. 목표가 아닌 것

- 막는 검사로 만들지 않는다. id는 서버 코드·include·런타임 JS가 만들 수 있어서 틀린 경고가 생길 수 있다.
- 따로 있는 `.js` 파일(W1)은 검사하지 않는다. 어느 페이지에서 쓰이는지 알 수 없다. 행은 `Skipped`(「페이지가 아님」)로 둔다.
- 속성 접근으로 폼 필드를 찾는 경우(`f.custId`, `document.form1.custId`, `document.forms[0].x`)는 보지 않는다. 변수 별칭을 따라가야 해서 틀린 경고가 많아진다. 이건 W3의 폼 필드 이름 검사에서 다룬다.
- 인라인 이벤트 속성(`onclick="..."`) 안의 JS는 보지 않는다(W2도 이 안의 코드는 해석하지 않는다).
- 프롬프트는 바꾸지 않는다. 예비 측정을 이전과 비교할 수 있게 하기 위해서다.
- CSS 선택자(`#id {}`)는 보지 않는다. 스타일 규칙이 없는 요소에 적용되는 것은 오류가 아니다.

## 4. 설계

### 4.1 참조 — JS가 요소를 찾는 모양

대상은 페이지의 모든 클라이언트 `<script>` 블록이다. 블록마다 W2의 페이지 크기 보기 텍스트(`PageBlockView`, `<%= %>`는 `__aspN__`)에서 찾는다. 문자열 리터럴 인수만 보고, 연결식(`"#" + id`)이나 변수는 무시한다.

| 모양 | 종류 | 값 |
|---|---|---|
| `document.getElementById("x")` | id | `x` |
| `document.getElementsByName("x")` | name | `x` |
| `$("…")`, `jQuery("…")` — 인수가 하나이고 `<`로 시작하지 않는 문자열 | 선택자 안의 `#x`는 id, `[name=x]`·`[name="x"]`는 name | 각각 |

- 다른 문서를 가리키는 호출은 제외한다. `opener.document.getElementById`, `parent.document…`처럼 `document` 앞에 `.`이 있는 경우와, `$` 호출에 두 번째 인수(문맥)가 있는 경우다.
- 선택자 해석은 `#` 뒤 `[\w-]+`와 `[name=…]` 속성 조각만 뽑는다. 나머지(클래스, 태그, 가상 클래스)는 무시한다.
- JS 주석 안의 참조는 세지 않는다. 문자열과 주석 구분은 기존 `JsTokenScan.Mask`를 쓴다. 마스크는 주석·문자열 내용을 공백으로 바꾸되 길이와 줄을 그대로 두므로, 호출 모양은 마스크에서 찾고 인수 문자열 값은 같은 위치의 원문에서 읽는다.
- 서버 코드가 섞여 짝 비교로 낮춘 블록(`<% If %>`, W2의 `Broken`·Statements 블록)도 검사한다. 이 방식은 구문 트리가 필요 없다. 그래서 W2의 블록 짝짓기(`AspClientChecks.Pairs`)는 쓰지 않는다(4.3).
- 값에 `__aspN__` 자리 표시가 든 참조(`"#row<%= i %>"`)는 서버가 만드는 값이라 세지 않는다.

### 4.2 정의 — 페이지에 있는 id·name

다음을 모두 모은다. 어느 하나에라도 있으면 「있음」이다.

1. 페이지 텍스트 전체(HTML 구간, 서버 코드 안 문자열, 클라이언트 블록 안 문자열 포함)에서 `id`·`name` 속성 모양 `(id|name)\s*=\s*["']*값`을 찾는다. VBScript의 `""` 이중 따옴표(`Response.Write "<input name=""x"">"`)도 잡는다.
2. 페이지의 `#include`(재귀, W2 `PageScripts`가 따라가는 것과 같은 규칙)로 들어오는 파일의 같은 모양.
3. 대상 파일을 include하는 페이지(W2 `PageScripts`와 같이 사이트 색인의 includer, 최대 200개)의 같은 모양. 공용 `.inc`를 고칠 때 부모 페이지의 입력 칸이 「있음」이 되게 하려는 것이다. 원본과 고친 쪽 모두에 같은 includer 집합을 쓴다.
4. JS가 런타임에 만드는 것: `.id = "x"`, `setAttribute("id", "x")`·`setAttribute("name", "x")`. 페이지 블록과, 페이지가 `<script src>`로 부르는 사이트 안 `.js` 파일 모두에서 찾는다.

값에 서버 코드가 들어간 속성(`id="row<%= i %>"`)은 앞부분(`row`)을 그 종류(id 또는 name)의 접두사로 기억한다. 그 종류의 참조가 접두사로 시작하면 「있음」으로 본다. 값 전체가 서버 코드면(`id="<%= x %>"`, 접두사가 빈 문자열) 그 종류의 참조는 모두 「있음」으로 본다(다른 종류는 그대로 검사). 틀린 경고를 피하는 쪽을 고른 것이다.

### 4.3 판정 — 새로 생긴 것만

- 「끊긴 참조」 = 4.1의 참조 가운데 4.2에 같은 종류·같은 값(대소문자 구분)이 없는 것.
- 단위는 블록이 아니라 **페이지 전체**다. 원본 페이지(`ctx.Original.Text`)와 고친 페이지(`ctx.Current.Text`)를 각각 `AspPage`로 해석하고, 모든 `<script>` 블록의 참조를 합친다. 블록 수가 달라져도 상관없다.
- 원본 페이지와 고친 페이지에서 각각 끊긴 참조를 (종류, 값) 단위로 센다. 고친 쪽이 더 많은 (종류, 값)만 경고한다. id를 같은 페이지 안 다른 위치로 옮기면 끊긴 참조 수가 같아서 경고가 나오지 않는다. 경고의 줄 번호는 고친 페이지에서 그 (종류, 값)이 처음 나오는 참조 줄이다. 기존 검사들이 「원본 기준선 대비 새로 생긴 것만」 세는 방식과 같다.
- 이렇게 하면 `pelly js`로 `$("#custId")`를 새로 쓴 경우와, `pelly asp --lines`로 HTML의 `id="custId"`를 지워 기존 참조가 끊긴 경우를 같은 규칙으로 잡는다.
- 경고 문구에 덧붙이는 힌트:
  - id 참조인데 같은 값의 name이 있으면 「name="x"는 있음(줄 n)」. jQuery `#x`는 name으로 찾지 못한다. `getElementById`는 IE 호환 모드에서는 name도 찾지만, 표준 모드에서는 찾지 못한다.
  - name 참조인데 같은 값의 id가 있으면 「id="x"는 있음(줄 n)」.
  - 대소문자만 다른 값이 있으면 「대소문자만 다름: X(줄 n)」.
- 행 하나에 경고를 쉼표로 이어 쓴다. 형식은 `#custId(줄 116) — id 없음, name="custId"는 있음(줄 98)`이다. 줄 번호는 페이지 줄이다.

### 4.4 어디에 붙나

- **`pelly js` 페이지 실행:** `JsApiStep` 뒤에 새 단계 `JsElementsStep`. 행 이름은 `JsElements`, 표시 이름은 기존 행들과 같은 방식으로 정한다. 입력은 대상 블록 보기(`ViewOf`)가 아니라 원본·현재 페이지 전체 텍스트다(4.3). 대상이 페이지가 아니면(`.js` 파일) `Skipped`이고, 사유는 「페이지가 아님」이다.
- **`pelly asp`:** `AspClientWarningsStep` 뒤에 새 단계. 원본이나 고친 페이지 중 어느 쪽에라도 클라이언트 `<script>` 블록이 있으면 편집 범위와 상관없이 판정한다(HTML만 고친 편집도 대상). 행은 `Passed` 또는 `Warned`이다. 양쪽 모두 블록이 없으면 행을 남기지 않는다. `.asp`에 JS가 없는 것은 흔해서, 「건너뜀」 행이 판정 표를 채우지 않게 하려는 것이다.
- **명세 `apply`:** asp 작업은 위 경로를 그대로 타므로 따로 할 일이 없다.
- 검토 화면, `summary.json`의 판정 표, `pelly report`는 기존 경고 행과 똑같이 다룬다. 새 집계 숫자는 만들지 않는다.
- 경고는 재시도를 일으키지 않는다(`JsNames`와 같다).

### 4.5 설정

새 설정은 없다. 틀린 경고가 현장에서 많으면 그때 끄는 설정을 생각한다.

## 5. 성공 기준

- page-004에서 모델이 `$("#custId")`를 쓴 결과에 `JsElements` 경고가 「name="custId"는 있음」 힌트와 함께 나온다. 가짜 모델 테스트로 확인한다.
- 다시 잰 W2 예비 측정(`eval/benchmark/web/run.sh`, 페이지 사례)에서 다른 사례에 새 경고가 생기지 않는다. 생기면 그 원인을 측정 문서에 적는다.
- `pelly asp --lines`로 `id="x"`를 지우면 경고가 나오고, 다른 곳으로 옮기면 경고가 나오지 않는다.
