# V2-3 프로젝트 규칙 — 외부 사전 측정 (규칙 있음 / 없음)

> **요약:** 내장 50건에서는 효과가 잡음 수준(+1.3%p)이고, 대상 코드에 보이지 않는 관례를 판정하는 규칙 스위트 6건에서는 0/6 → 6/6이다. 주석 규칙 문구는 주석이 덜 늘어나는 쪽으로 바꿨다(§4). 효과의 크기는 실제 작업 중 "보이지 않는 관례"가 걸리는 비율에 달려 있으므로, 현장 판정에도 규칙 판정 작업이 필요하다(§6).

* **날짜:** 2026-10-24
* **용도:** PRD §12.6 "규칙 도입 효과(성공률 +5%p 이상)"의 **외부 참고치**다. PRD §2.1에 따라 KPI 최종 판정은 폐쇄망에서 실제 코드베이스로 한다. 이 수치로 판정하지 않는다.
* **환경:** macOS arm64(Darwin 25.6.0), Ollama 0.40.0, 모델 `qwen3.6:35b`(GGUF `Q4_K_M`, digest `a7eb95c53bcf…` — [M4 기준선](m4-gguf-baseline.md)과 같은 파일), SQL Server 2022 컨테이너
* **코드:** §2·§3은 `2bed072`, §4는 `68fb8e3`~`f9d8d59`(문구만 바꿈), §5는 `0f38fea`. 공통으로(pelly 0.9.1, 규칙 기능 + forbid 코드 토큰 검사 포함). 프롬프트 `cs-v2`·`sql-v1`, `llm.thinkMode = retry`, `budget.think = 512`, `budget.system = 450`, `budget.rules = 150`, 샘플링 기본값.
* **요약 파일:** [baseline.summary.json](v2-3-rules-premeasure/baseline.summary.json), [rules.summary.json](v2-3-rules-premeasure/rules.summary.json)

## 1. 방법

* 같은 날, 같은 코드·모델로 내장 벤치마크(50건)를 **규칙 없이** 3회, **규칙을 넣고** 3회 돌렸다. 두 실행 모두 시작 전에 SQL 코퍼스를 다시 배포했다.
* 규칙은 코퍼스 사본의 루트마다 `pelly rules init --yes`로 만든 초안을 **손대지 않고** 썼다. "초안 그대로의 효과"를 잰 것이다. 초안: [Modern](v2-3-rules-premeasure/agents/Modern.AGENTS.md) · [Legacy](v2-3-rules-premeasure/agents/Legacy.AGENTS.md) · [Sql](v2-3-rules-premeasure/agents/Sql.AGENTS.md)

  | 루트 | 규칙 |
  | :--- | :--- |
  | Modern | `[*]` 주석은 한국어로 · `[async]` `.Result`/`.Wait()` 금지(forbid) · `[dapper]` Dapper 파라미터 |
  | Legacy | `[*]` 주석은 한국어로 · `[dapper]` Dapper 파라미터 |
  | Sql | `[procedure]` 프로시저 본문 처음에 `SET NOCOUNT ON` |
* 규칙 스위트는 내장 스위트를 복사해 루트 안에 `AGENTS.md`를 두었다. SQL 작업은 작업 폴더 최상위가 작업 공간이라 Sql 초안을 `supportFiles`로 최상위에 넣었다.

```bash
dotnet run --project eval/PellyCoder.Eval -- [--suite <규칙 스위트>] --config <pelly.json: llm.model=qwen3.6:35b, sql 허용 목록> --repeat 3 --out <폴더>
dotnet run --project eval/PellyCoder.Eval -- compare <규칙 없음 summary.json> <규칙 있음 summary.json>
```

| 작업 | 규칙 없음 | 규칙 있음 | 요청 |
| :--- | :--- | :--- | :--- |

* 두 작업 모두 규칙 내용(주석 언어·동기 대기·Dapper·`NOCOUNT`)과 관계가 없다. 프롬프트에 규칙 몇 줄이 더해져 경계에 있던 작업의 출력이 흔들린 것으로 본다. 두 작업은 M3b 기준선에서도 불안정했다(cs-modern-003 2/3, [m3b-baseline.md](m3b-baseline.md)).

### 2.2 규칙이 실제로 들어간 정도와 지켜진 정도

* **들어간 규칙:** C# 실행 90회 모두에 규칙이 들어갔다(cs-legacy 평균 1.28개, cs-modern 2.25개). SQL은 60회 중 48회(프로시저 작업만, 함수·뷰는 `procedure` 태그가 맞지 않음). 예산 초과로 빠진 규칙은 없다.
* **forbid 위반:** 0회(`RULE` 오류 코드 0건). 규칙이 없을 때도 모델이 `.Result`/`.Wait()`를 추가한 적이 없다.
* **추가된 주석(종료 코드 0 실행의 마지막 패치 기준):**

  | 범주 | 규칙 없음 | 규칙 있음 |
  | :--- | :--- | :--- |
  | cs-legacy | 3개 (한국어 100%) | 24개 (한국어 100%) |
  | cs-modern | 6개 (한국어 100%) | 13개 (한국어 100%) |
  | sql | 0개 | 0개 |

  규칙이 없어도 주석은 이미 모두 한국어였다(코드와 요청이 한국어라서). 대신 "주석은 한국어로" 규칙을 넣자 **주석 수가 2~8배 늘었다.** 규칙을 "주석을 달라"로 읽은 것으로 보인다. diff가 커지는 부수 효과다.

## 3. 1차 해석 (내장 50건)

1. **내장 50건으로는 규칙 효과를 성공률로 잴 수 없다.** 차이 +1.3%p는 규칙과 무관한 두 작업의 흔들림이다. 이 작업들은 규칙을 지켜야 통과하는 판정이 없고, 초안 규칙(주석 언어·동기 대기 금지)은 모델이 규칙 없이도 이미 지키고 있었다.
2. **규칙은 해를 끼치지 않았다.** 불변 조건 위반 0건, 범주 감소 없음. 비용은 실행당 입력 약 21토큰과 작업 시간 중위값 +0.22초다.

## 4. 주석 규칙 문구 시험

`[*] 주석은 한국어로 작성한다`가 주석을 늘리는지, 문구로 줄일 수 있는지 C# 30건(종료 0 실행의 마지막 패치에서 새로 추가된 `//` 주석)으로 쟀다. 문구 외에는 §2의 "규칙 있음"과 같다.

| 변형 | 추가된 주석 (한국어 비율) | C# 평균 성공(30건) | 요약 |
| :--- | :--- | :--- | :--- |
| 규칙 없음 | 9 (100%) | 26.00 | [baseline](v2-3-rules-premeasure/baseline.summary.json) |
| `주석은 한국어로 작성한다` | 37 (100%) | 26.67 | [rules](v2-3-rules-premeasure/rules.summary.json) |
| `주석을 쓸 때는 한국어로 작성한다` | 36 (100%) | 26.33 | [comment-wording](v2-3-rules-premeasure/comment-wording.summary.json) (50건 실행) |
| 주석 규칙 빼기(나머지 규칙은 그대로) | 9 (100%) | 27.67 | [comment-nocomment](v2-3-rules-premeasure/comment-nocomment.summary.json) |
| **`새 주석은 꼭 필요할 때만 달고, 쓸 때는 한국어로 작성한다`** | 18 (100%) | 26.00 | [comment-limit](v2-3-rules-premeasure/comment-limit.summary.json) |

* 주석이 늘어나는 원인은 **주석 규칙 자체**다. 이 규칙을 빼면 다른 규칙이 있어도 규칙 없음과 같다(9개).
* "쓸 때는"으로 바꾸는 것만으로는 줄지 않았다. "꼭 필요할 때만"을 넣으면 절반으로 줄었다.
* 어느 경우에도 주석은 100% 한국어였다. 코드와 요청이 한국어인 코퍼스에서는 이 규칙이 언어를 바꾸지 못했다.
* **조치:** `pelly rules init` 초안 문구를 `[*] 새 주석은 꼭 필요할 때만 달고, 쓸 때는 한국어로 작성한다`로 바꿨다(`RulesDrafter`). 현장 코드에서도 주석이 이미 한국어라면 이 줄을 지우는 편이 diff가 가장 작다.
* 성공 수 차이(26.00~27.67)는 cs-modern-002·003의 흔들림이며 문구와의 관계는 확인되지 않았다.

## 5. 규칙 판정 스위트 (`eval/benchmark-rules`, 6건)

* **설계:** 코퍼스의 관례 중 대상 코드에 보이지 않는 것 하나를 골랐다. SQL의 현재 시각은 `GETDATE()`가 아니라 `SYSDATETIME()`을 쓴다. 작업 6건(SQL 4, Modern Dapper SQL 2)은 모두 현재 시각이 필요한 요청이고, 대상에는 시각 함수가 없다. 판정은 `mustContain: SYSDATETIME()`과 새 판정 `mustNotAdd: GETDATE(`다. 스위트 설명: [eval/benchmark-rules/README.md](../eval/benchmark-rules/README.md)
* **규칙:** `pelly rules init` 초안(§4의 새 문구)에 관례 한 줄을 사람이 더했다. Modern `- [dbo] SQL에서 현재 시각은 GETDATE() 대신 SYSDATETIME()을 쓴다`, Sql `- [*] 현재 시각은 GETDATE() 대신 SYSDATETIME()을 쓴다 | forbid: (?i)\bGETDATE\s*\(`
* **실행:** 같은 스위트를 `--no-rules`(작업 복사본의 `AGENTS.md`를 지움)로 3회, 규칙과 함께 3회. 그 밖의 조건은 §2와 같다.

| 지표 | 규칙 없음 (`--no-rules`) | 규칙 있음 |
| :--- | :--- | :--- |
| 평균 성공 | **0.00** (0·0·0) | **6.00** (6·6·6) |
| 검증 불변 조건 위반 | 0·0·0 | 0·0·0 |
| 시도 수 | 모두 1회 | 모두 1회 (forbid 위반 0건) |
| 작업 시간 중위값 | 1.50초 | 1.97초 |

* 규칙 없음: 5개 작업이 `GETDATE()`, sql-103은 `SYSUTCDATETIME()`을 썼다(18회 모두 같은 선택). 요청은 모두 올바르게 처리했고 관례만 어겼다.
* 규칙 있음: 18회 모두 첫 시도에 `SYSDATETIME()`을 썼다. `forbid` 재시도 없이 **프롬프트의 규칙만으로** 지켰다.
* `compare`(R4): 네 규칙 모두 ✓ → 채택. 요약: [rules-suite-norules](v2-3-rules-premeasure/rules-suite-norules.summary.json)(`rulesRemoved: true`), [rules-suite-rules](v2-3-rules-premeasure/rules-suite-rules.summary.json)

## 6. 해석과 폐쇄망 측정에 필요한 것

1. **규칙은 "대상 코드에 보이지 않는 관례"에 효과가 있다.** 코드에 보이는 관례(이번에 잰 것은 주석 언어와 동기 대기 금지)는 모델이 이미 따라 하므로 규칙이 거의 바꾸지 못한다. 보이지 않는 관례는 규칙 한 줄로 0% → 100%가 됐다.
2. **+5%p 판정은 작업 구성에 달려 있다.** 규칙 스위트는 모든 작업이 관례에 걸리도록 만든 것이라 0→6은 효과의 **크기**가 아니라 **방향과 기전**을 보여 준다. 참고로 내장 50건 + 규칙 6건을 합치면 46.00/56(82.1%) → 52.67/56(94.0%), +11.9%p다. 이 합계는 56건 중 6건(11%)이 관례에 걸린다는 가정의 숫자다.
3. **폐쇄망에서 할 일:** 실제 코드베이스에서 `pelly rules init` 초안을 만들고, 팀 관례 중 대상 코드에 잘 드러나지 않는 것(시각 함수, 공통 예외 타입, 로그 형식, 금지 API 등)을 사람이 더한다. 그 관례가 걸리는 작업을 현장 스위트에 `mustContain`·`mustNotAdd`로 넣고, 같은 스위트를 `--no-rules`와 함께 한 번씩 돌린다(`deploy/field-guide.md`). 관례에 걸리는 작업 비율은 실제 요청 이력에 가깝게 잡는다.
