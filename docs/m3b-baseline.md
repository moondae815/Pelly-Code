## 4. 불안정 작업과 실패 원인

* **불안정(1/3, 2/3):** cs-modern-003 (2/3) 1건
* **실패 유형 분포(전 회차 합계):** `Judge` 7건(cs-modern-003 1, cs-modern-007 3, cs-modern-008 3). 다른 유형은 0건이다.
* 원인은 수정된 파일(`run-<k>/work/<id>/Modern/…`)을 원본과 비교해서 정했다. 7건 모두 빌드는 통과했다.

| id | 회차 | 원인 분류 | 근거(수정본) |
| :--- | :--- | :--- | :--- |
| cs-modern-003 | 2 | 모델 실수 | `ORDER BY IsGiftItem DESC, OrderItemId`. 사은품(1)이 앞에 온다. 요청과 반대 방향이다. 회차 1·3은 `CASE WHEN IsGiftItem = 1 THEN 1 ELSE 0 END`로 맞게 고쳤다. |
| cs-modern-007 | 1·2·3 | 모델 실수 | 길이 검사를 기존 `if (!string.IsNullOrWhiteSpace(request.Keyword))` 블록 안에 넣었다. 그래서 공백뿐인 키워드(`"   "`)는 null이 되지 않고 그대로 넘어간다. 요청은 「공백을 뺀 키워드가 2자 미만이면 null」이라 이 경우도 null이어야 한다. 판정 테스트가 이 경계값을 일부러 넣었다. 3회 모두 같은 모양이다(회차 2는 지역 변수로 Trim). |
| cs-modern-008 | 1·2·3 | 모델 실수 | 조건을 `CommissionRate.Value > 0m && … <= 1m`로 썼다. 수수료율 0도 잘못된 값으로 보고 기본 12%를 쓴다. 요청은 「0보다 작거나 1보다 크면」이라 0은 그대로여야 한다(판정: 판매자 5 수수료율 0 → 기대 0, 실제 12000). C# 쪽 수정이라 가짜 DB 한계(SQL 안의 `CASE`)와는 관계없다. 3회 모두 같다. |

* 판정 산물(가짜 DB가 SQL 쪽 수정을 거부)이나 도구 오류로 분류한 실패는 없다.
* cs-modern-007·008은 경계값 실수다. R5 후보 1(모순 요청 회피)과는 원인이 다르다.
