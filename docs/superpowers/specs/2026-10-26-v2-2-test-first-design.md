# V2-2 테스트 우선 검증 (Test-First Verification) 설계

작성 2026-10-26. 상태: 초안, 사람 확인 전. 설계 검토(빌더 확인) 반영. 사람은 「질문 없이 바로 설계」를 골랐다. 아래에서 「Claude 결정」으로 표시한 것은 사람이 아직 확인하지 않은 판단이다.

근거 문서:
- PRD §12.4(V2-2 원안), §12.6(v2 KPI: 수용 기준 충족률·RED 확인 경고율), §12.7, FR-06 5번(v1 `--test`)
- [V2-1 설계](2026-10-24-v2-1-apply-design.md) — 명세 형식, `spec check`, 작업 그룹. §2 비목표에 「AC `test:` 참조의 실행은 V2-2」가 있다.
- `eval/benchmark/README.md` 「동작 판정」 — 원본에서 실패하는 판정 테스트(`judges/Modern/`)

## 1. 왜 하는가

v1 검증은 「컴파일이 되는가」까지다. `pelly cs --test`(M3a)는 여기에 「원래 통과하던 테스트를 깨지 않았는가」를 더했다. 둘 다 **요청한 동작을 했는지는 보지 않는다.** M3a 실측에서 요청이 기존 테스트와 맞지 않을 때 모델이 요청을 로그 출력으로 바꿔 피해 가고 종료 0으로 끝난 일이 20회 중 5회 있었다(FR-06 알려진 한계).

V2-2는 사람이 미리 쓴 테스트 하나를 「이 변경이 끝났다는 증거」로 쓴다. 패치 전에는 실패해야 하고(RED), 패치 뒤에는 통과해야 한다(GREEN). 통과하지 못하면 v1과 같은 자가 교정 루프로 돌아간다. 판정은 모두 테스트 실행 결과로 하므로 결정론적이다.

## 2. 이미 있는 것 (바탕으로 쓴다)

V2-2는 새 실행 도구를 만들지 않고 v1 `--test`의 부품 위에 판정만 더한다.

| 부품 | 지금 하는 일 |
| :--- | :--- |
| `Testing/TestRunner` | 테스트 프로젝트를 빌드하고 실행한다. 프로젝트 종류별 경로(xunit v3 `dotnet run … -result-trx`/`-trx`, VSTest `dotnet test --logger trx`, 레거시 `test.command`), TRX 결과 |
| `Testing/TestProjectLocator` | 대상 프로젝트를 참조하고 이름에 `Test`가 있는 프로젝트, 또는 `test.projects` |
| `Testing/TrxParser` | 테스트별 결과(이름·통과·첫 줄 메시지), 실행 중단 여부 |
| `LocatePhase`·`ApplyPhase` | 패치 전 테스트(기준)를 모델 생성과 병렬로 돌리고, 파일을 처음 쓰기 전에 기다린다 |
| `Verification/TestStep` | 패치 뒤 테스트를 돌려 **새로 실패한 테스트**만 실패로 본다(회귀 확인). 피드백 `TESTS FAILED …` + 「요청한 변경을 되돌리지 마라」 |
| `SpecChecker` | AC `test:` 이름이 작업 공간에 메서드로 있는지 구문으로만 본다(없으면 경고 `TestNotFound`) |
| `apply`의 작업 실행 | `FsmTaskExecutor`는 `RunTests`를 켜지 않는다. 지금 apply는 테스트를 전혀 돌리지 않는다 |

PRD §12.4의 「회귀 확인」은 v1 `--test`가 이미 한다. V2-2가 새로 하는 일은 **지정한 테스트의 RED·GREEN 판정**과 **그것을 명세의 수용 기준에 잇는 일**이다.

다만 부품을 손대지 않고 쓰지는 않는다. 바뀌는 v1 동작(테스트 우선 검증을 하는 실행에서만):
- `TrxParser`는 지금 건너뜀(`NotExecuted`) 결과를 버리고 메시지 첫 줄만 읽는다. 건너뜀을 「결과에 없음」과 구별하고, 메시지 전체와 스택을 읽도록 넓힌다.
- v1은 원본에서 빌드되지 않던 테스트 프로젝트를 비교 없이 건너뛰고, 원본과 같은 빌드 오류가 남으면 통과로 넘긴다(`TestStep`). 테스트 우선 검증에서는 컴파일 RED 규칙(§5.3)과 GREEN 실패(§5.4)로 바뀐다.
- v1은 테스트를 돌릴 수 없으면 알림 뒤 빌드로 판정한다. 테스트 우선 검증에서는 종료 4다(§3 실패 조건).

## 3. 목표 / 비목표 / 실패 조건

**목표**
- 단독 실행: `pelly cs <파일> … --verify-test <테스트 이름>`(여러 번 줄 수 있음)으로 RED 확인 → 패치 → GREEN 확인 → 회귀 확인을 한다.
- `pelly apply`: 작업이 참조하는 수용 기준에 `test:`가 있으면 같은 판정을 자동으로 한다.
- GREEN이 아니면 실패한 assert 메시지와 대상 파일 안의 스택 프레임을 자가 교정 피드백(296 토큰)으로 보낸다.
- `pelly report`에 수용 기준 충족률과 RED 확인 경고율(PRD §12.6)을 낸다.
- 벤치마크에 테스트가 연결된 작업 20건을 두고, 같은 작업을 v1 방식과 테스트 우선 방식으로 대조해 잰다.

**비목표**
- **모델이 테스트를 쓰는 것**(명세의 `test` 유형 작업). PRD대로 v2.x에서 V2-2 결과를 보고 검토한다.
- **테스트 원문을 모델 프롬프트에 넣는 것**(Claude 결정). 요청문이 명세이고, 테스트는 판정에만 쓴다. 넣으면 컨텍스트 예산(§3.3)을 나눠야 하고, 모델이 입력값을 하드코딩해 테스트만 맞추는 길이 열린다. 첫 시도는 v1과 같은 프롬프트, 재시도에서만 실패 메시지가 간다. 테스트 원문을 넣는 대조 실험은 V2-2 측정 뒤 사람이 정한다(§11).
- **SQL 작업의 테스트 검증.** pelly는 SQL 객체를 DB에 배포하지 않는다(NOEXEC 가실행만). 바뀐 SP를 테스트가 볼 방법이 없다.
- 일부 테스트만 골라 돌리는 필터 실행(`--filter`). §5.1.
- 불안정한(flaky) 테스트 재실행·판정, 변이 테스트, 커버리지.
- `pelly apply --test`(테스트가 연결되지 않은 작업까지 회귀 확인). 필요하면 뒤에 따로 더한다.

**실패 조건** (돌아가도 실패인 경우)
- 지정한 테스트가 **실행되지 않았는데** GREEN으로 센다. 결과에 이름이 없거나, 건너뜀(NotExecuted)이거나, 테스트 호스트가 중간에 죽은 경우다.
- 테스트를 돌릴 수 없는 환경(레거시 on macOS, 테스트별 결과가 없는 프로젝트, 기준 테스트 실행 실패)에서 **조용히 빌드 판정으로 내려간다.** v1 `--test`는 이때 알림만 남기고 빌드로 판정하지만, 테스트 우선 검증에서는 테스트가 유일한 판정이므로 종료 4다(V2-1 그룹의 「검증할 수 없으면 통과시키지 않는다」와 같은 원칙).
- 모델이 연결된 테스트 자체를 고쳐 GREEN을 만든다.
- 비식별 리포트(`--sanitize`)에 테스트 이름이나 AC 문구가 남는다.
- `--verify-test`도 연결된 AC도 없는 실행의 프롬프트·동작·벤치마크 수치가 바뀐다.

## 4. 제약

- .NET 10, 기존 구조(`PellyCoder.Core`, `PellyCoder.Cli`). 새 구성 요소는 PRD의 `Verifiers/TestRunner.cs`·`Verifiers/TestBaseline.cs` 대신 기존 `Testing/`·`Verification/` 아래에 둔다(이미 같은 일을 하는 파일이 있다).
- 토큰 예산(§3.3)과 시스템 프롬프트는 바꾸지 않는다. 바뀌는 것은 재시도 피드백 문구뿐이다.
- 폐쇄망·오프라인 동작. 테스트 실행 도구는 v1과 같다(SDK `dotnet`, 레거시 `test.command`).
- 레거시 테스트는 Windows에서만 돈다. 레거시 테스트 우선 검증의 측정은 Windows에서 사람이 한다.
- 테스트 한 번 실행 상한은 `test.timeoutSeconds`(기본 300초) 그대로다.

## 5. 판정

### 5.1 실행 방법: 프로젝트 전체를 돌리고 지정한 테스트의 결과를 읽는다 (Claude 결정)

PRD §12.4는 `dotnet test --filter "FullyQualifiedName~<이름>"`과 `vstest.console.exe /Tests:<이름>`을 적었다. 이 설계는 필터를 쓰지 않는다.
- 회귀 확인에는 어차피 같은 프로젝트의 다른 테스트 결과가 다 필요하다. 전체를 한 번 돌리면 RED·GREEN·회귀를 한 결과로 판정한다. 필터 실행을 따로 하면 시도마다 실행이 두 번이다.
- 필터 문법이 실행 경로마다 다르다. v1은 .NET 10에서 `dotnet test`가 Testing Platform 프로젝트의 VSTest 옵션을 거부해 xunit v3를 `dotnet run`으로 돌린다(TestRunner 주석). 코퍼스의 Modern 테스트가 바로 이 경우다.
- 레거시는 사람이 설정한 `test.command`로 돈다. `vswhere`로 `vstest.console.exe`를 찾는 일은 하지 않는다.

그래서 **테스트별 결과(TRX)가 있어야 한다.** 종료 코드만 주는 프로젝트(`OtherTestingPlatform`, `{trx}`가 없는 레거시 `test.command`)에서는 테스트 우선 검증을 할 수 없고 종료 4다(「테스트별 결과가 없어 지정한 테스트를 판정할 수 없습니다」). 조치 문구에 `{trx}`를 안내한다.

### 5.2 테스트 이름 맞추기

`test:` 값과 `--verify-test` 값은 `[네임스페이스.]클래스.메서드` 또는 `메서드`다.
- 결과의 전체 이름은 `네임스페이스.클래스.메서드`로 맞춘다. 어댑터가 `testName`에 짧은 이름만 주는 경우(MSTest 등)는 TRX의 `TestMethod`(`className`·`name`)에서 만든다. 실제로 어떤 어댑터가 무엇을 주는지는 만드는 사람이 픽스처로 확인한다.
- 맞춤은 점(`.`) 경계의 뒷부분 일치다. `OrderServiceTests.Cancel_WhenShipped_Throws`는 `Shop.Api.Tests.OrderServiceTests.Cancel_WhenShipped_Throws`와 맞고 `XOrderServiceTests.…`와는 맞지 않는다.
- 데이터 행(`Theory`·`TestCase`)의 인자 부분(`메서드(...)`)은 떼고 맞춘다. 한 메서드의 행이 여럿이면 **모든 행이 통과해야 통과**, 하나라도 실패하면 실패다.
- 맞는 메서드가 서로 다른 전체 이름으로 둘 이상이면(다른 클래스, 다른 테스트 프로젝트) 모호함으로 종료 4다. 메시지에 후보를 나열하고 더 길게 쓰라고 한다.
- 이름 비교는 대소문자를 구별한다(C# 식별자).

### 5.2a 어느 테스트 프로젝트를 돌리나 (설계 검토 반영, Claude 결정)

`TestProjectLocator`는 대상 프로젝트를 **직접** 참조하는 프로젝트만 찾는다. 서비스 작업의 AC 테스트가 컨트롤러 테스트 프로젝트에 있으면 기준 결과에 그 테스트가 없다. 그래서 돌릴 프로젝트는 다음의 합집합이다.
- v1 `--test`처럼 대상에서 찾은 테스트 프로젝트(`test.projects`가 있으면 그것)
- 지정 테스트 메서드가 선언된 파일의 가장 가까운 `.csproj`. 작업 공간을 구문으로 훑어 테스트 특성(§7.1)이 붙은 메서드에서 찾는다. `spec check`와 같은 탐색을 쓴다.

훑기에서 찾지 못하거나 둘 이상에서 찾으면 실행 전에 종료 4(찾지 못함·모호함)다.

### 5.2b 깨질 것으로 정한 테스트 (`breaks:`) (설계 검토 반영, Claude 결정)

요청이 바꾸는 동작을 기존 테스트가 고정해 두었으면(코퍼스의 `*_CurrentlyCancels`), 회귀 확인 때문에 그 변경은 늘 실패한다. 모델은 테스트를 고칠 수 없다(§5.6). 그래서 사람이 「이 변경으로 깨져도 되는 테스트」를 적게 한다.
- 명세: AC 아래에 `test:`와 같은 들여쓰기로 `breaks: <이름>`을 둔다(여러 줄 가능). 이름 규칙은 §5.2와 같다.
- 단독 실행: `--expect-break <이름>`(여러 번).
- 적힌 테스트는 그 AC의 연결 작업(단독 실행이면 그 실행)의 회귀 판정에서 뺀다. 패치 뒤에도 통과하면 알림만 남긴다(「깨질 것으로 정한 테스트가 여전히 통과합니다」).
- 기준에서 이미 실패하거나 결과에 없으면 `breaks:`가 쓸모없으므로 경고한다(실행은 계속).
- `spec check`는 `breaks:` 이름이 테스트 메서드로 있는지 `test:`와 같은 규칙으로 본다. `breaks:`와 `test:`에 같은 테스트가 있으면 오류다.
- 이것은 벤치마크 `judge.failingTests`와 같은 뜻이다. 회귀를 사람이 명시적으로 허용하는 유일한 길이므로, 리포트에 `breaks:`로 뺀 테스트 수를 남긴다.

### 5.3 RED 확인 (패치 전)

패치 전 기준 테스트 실행(v1이 이미 모델 생성과 병렬로 돌리는 것)의 결과로 판정한다. 판정 시점은 지금 v1이 기준 테스트를 기다리는 곳, 곧 **파일을 처음 쓰기 직전**이다(Claude 결정). 모델 생성과 테스트 실행을 계속 병렬로 두기 위해서다. 파일은 아직 바뀌지 않았으므로 PRD의 「패치 전」이다.

| 기준 결과 | 판정 | 다음 |
| :--- | :--- | :--- |
| 지정 테스트가 실패 | **RED** | 계속 |
| 테스트 프로젝트가 컴파일 오류로 빌드되지 않고, 오류가 모두 그 테스트 프로젝트 파일 안이며 하나 이상이 지정 테스트 메서드 안 | **RED(컴파일)** | 계속. 아래 「컴파일 RED」 |
| 지정 테스트가 통과 | **이미 통과** | 경고 「이 테스트는 변경을 검증하지 못합니다」. 대화형이면 계속할지 묻고, 거부하면 종료 2. `--yes`면 기록하고 계속 |
| 결과에 없음 | 찾지 못함 | 종료 4. `test.projects` 설정을 안내(테스트 프로젝트가 대상을 직접 참조하지 않거나 이름에 `Test`가 없을 때) |
| 건너뜀(NotExecuted) | 판정 불가 | 종료 4 |
| 기준 테스트를 돌리지 못함(오류, 시간 초과, TRX 없음, 위 조건이 아닌 빌드 오류) | 판정 불가 | 종료 4 |

- **컴파일 RED:** 사람이 새 시그니처로 테스트를 먼저 쓰면(TDD의 흔한 모양) 테스트 프로젝트가 빌드되지 않는다. 이것을 RED로 받는다(Claude 결정). **그룹 작업에서만 받는다**(설계 검토 반영). 그룹 밖 실행의 멤버 모양 검사는 본문만 고치게 하므로(시그니처·public 추가 불가) 컴파일 오류를 풀 수 없어 재시도만 쓰고 끝난다. 그룹 밖에서 컴파일 RED가 나오면 편집 전에 종료 4(「테스트가 빌드되지 않습니다 — 시그니처를 바꾸는 작업은 그룹으로 묶으세요」)다. 이때 그 프로젝트에는 비교할 기준 결과가 없으므로, 패치 뒤 **그 프로젝트의 모든 테스트가 통과해야** 한다(회귀를 엄격하게 본다). 화면에 그 사실을 알린다. 오류가 지정 테스트와 상관없는 곳에도 있으면 판정 불가(종료 4)다. 오류 위치→멤버 대응은 그룹 오류 귀속(`GroupErrorAttribution`)과 같은 방식으로 한다.
- 기준 테스트의 실패 메시지 첫 줄은 실행 기록(`events.jsonl`)과 `--verbose` 출력에 남긴다. 테스트가 DB 연결 같은 환경 문제로 「실패」한 것도 RED로 보이므로, 사람이 RED 이유를 볼 수 있어야 한다(§10 알려진 한계).

### 5.4 GREEN 확인과 회귀 확인 (패치 뒤)

VERIFY의 테스트 단계(`TestStep`)가 한 번 실행한 결과로 둘을 함께 판정한다. 순서는 v1과 같다: 구문 → 규칙 → 빌드 → 테스트.
- **GREEN:** 지정 테스트(행이 여럿이면 모두)가 결과에 있고 통과해야 한다. 결과에 없거나 건너뛰었으면 실패다. 테스트 호스트가 죽어 TRX가 없으면 v1처럼 실패로 본다(모델이 고칠 수 있는 실패).
- **테스트 프로젝트가 여전히 빌드되지 않으면**(컴파일 RED였는데 같은 오류가 남음) GREEN 실패다. v1은 이 경우를 통과로 넘긴다. 피드백은 assert 메시지 대신 테스트 프로젝트의 컴파일 오류를 v1 빌드 피드백 형식(`파일(줄): CSxxxx 메시지`, 앞뒤 줄)으로 준다. 모델은 테스트 파일을 고칠 수 없지만, 오류 메시지가 테스트가 기대하는 시그니처를 알려 준다.
- **회귀:** v1 규칙 그대로 기준에서 실패하지 않던 테스트가 새로 실패하면 실패다. `breaks:`로 정한 테스트는 뺀다(§5.2b). 컴파일 RED 프로젝트는 위의 엄격한 규칙.
- 둘 중 하나라도 실패하면 자가 교정 피드백을 주고 다시 시도한다(`retry.max` 안에서). 다 쓰면 롤백, 종료 1.
- 실패 유형: GREEN 실패는 `TestGreenFailed`, GREEN은 됐는데 회귀만 있으면 `TestRegression`(Claude 결정. v1 `--test`의 회귀 실패 유형 이름은 그대로 둔다).

### 5.5 피드백 (296 토큰)

PRD대로 실패한 테스트 이름, assert 메시지, **대상 파일 안의 스택 프레임**만 보낸다.

```
TEST NOT PASSING: Shop.Api.Tests.OrderServiceTests.Cancel_WhenShipped_Throws
Assert.Throws() Failure: No exception was thrown
  at OrderService.CancelAsync (Services/OrderService.cs:42)
The test cannot be changed. Make it pass by implementing the request.
```

- 스택 프레임은 TRX의 `StackTrace`에서 파일 경로가 대상 파일인 줄만 고른다(없으면 생략). 지금 `TrxParser`는 메시지 첫 줄만 읽으므로 스택을 읽게 넓힌다.
- 메시지는 첫 줄이 아니라 assert 메시지 전체를 예산 안에서 앞부터 쓴다(xunit의 `Expected:`/`Actual:` 줄이 둘째 줄부터 나온다). 예산을 넘으면 v1 `ForTests`처럼 줄인다.
- GREEN과 회귀가 함께 실패하면 GREEN을 먼저 쓰고, 남은 예산에 회귀 목록(v1 형식)을 쓴다.
- 끝 줄은 v1의 「요청한 변경을 되돌리지 마라」 대신 위의 문장이다. 정확한 문구는 구현 때 재생 실험으로 고른다(V2-1 그룹 프롬프트와 같은 방식).

### 5.6 테스트를 고쳐 통과시키는 것 막기

- 단독 실행에서 `--verify-test`가 대상 멤버 자신을 가리키면 종료 4.
- 명세에서 작업 대상이 그 작업이 참조하는 AC의 테스트 메서드면 `spec check` 오류다.
- 그 밖에는 v1 멤버 모양 검사가 대상 멤버 밖을 못 고치게 한다. 그룹 작업도 대상 멤버의 시그니처·이름만 바꿀 수 있다.
- 실행이 끝나면(성공·실패 모두) 지정 테스트가 든 파일의 해시가 RED 확인 때와 같은지 본다. 다르면(pelly 밖에서 바뀌었거나 다른 작업이 고쳤으면) GREEN을 인정하지 않고 종료 4(Claude 결정).

## 6. 단독 실행: `pelly cs --verify-test`

`pelly cs <파일> [대상 지정] "<요청>" --verify-test <이름> [--verify-test <이름2>]`

- `--test`를 켠 것과 같다(회귀 확인에 같은 실행 결과를 쓴다).
- 테스트 프로젝트는 v1 `--test`와 같이 찾는다. 찾지 못하면 v1은 알림 뒤 빌드로 판정하지만, `--verify-test`는 종료 4다.
- 레거시 프로젝트를 Windows 밖에서 실행하면 종료 4다(v1 `--test`는 알림 뒤 건너뜀).
- `--dry-run`은 테스트를 돌리지 않고 「테스트 우선 검증: <이름> (dry-run에서는 실행하지 않음)」만 보인다.
- `pelly sql`에는 없다.
- 이름이 여럿이면 각각 RED를 확인한다. 하나라도 「이미 통과」면 경고·확인은 한 번만 묻는다. GREEN은 모두 통과해야 한다.

## 7. `pelly apply`와 수용 기준

### 7.1 어느 작업이 무엇을 판정하나 (Claude 결정)

수용 기준 하나를 여러 작업이 함께 채우는 일이 흔하다(서비스 메서드 + 컨트롤러, 또는 C# + SQL). 그래서 판정을 **AC 단위**로 놓는다.

- AC의 **연결 작업**은 그 AC를 `(AC…)`로 참조하는 `cs` 작업이다. SQL 작업은 테스트로 판정하지 않는다(§3 비목표).
- 연결 작업은 모두 테스트를 돌린다(회귀 확인).
- **RED는 그 AC의 첫 연결 작업**의 기준 실행에서 확인한다. 앞 작업의 결과가 이미 파일에 있으므로, 앞선(연결되지 않은) 작업이 테스트를 통과시켜 버렸으면 「이미 통과」로 나온다.
- **GREEN은 그 AC의 마지막 연결 작업**에서 확인한다. 그 사이 작업에서 지정 테스트는 기준에서 실패하던 것이라 회귀로 세지 않는다.
- 연결 작업이 하나면 단독 실행과 같다.
- AC에 `test:`가 있는데 연결 `cs` 작업이 없으면(SQL만 참조하거나 아무도 참조하지 않음) `spec check` 경고 「테스트로 검증되지 않는 수용 기준」이고, 리포트에서는 「미검증」으로 센다.
- `spec check`는 연결 작업이 있는 AC의 테스트를 찾지 못하면 지금의 경고가 아니라 **오류**로 올린다(apply가 어차피 종료 4로 멈추므로 미리 알린다). 연결 작업이 없는 AC는 지금처럼 경고다.
- 구문 검사로 찾을 때는 테스트 특성(`Fact`, `Theory`, `Test`, `TestCase`, `TestMethod`, `DataTestMethod`)이 붙은 메서드만 센다. 지금은 모든 메서드를 세서 `Cancel` 같은 짧은 이름이 제품 코드 메서드와 맞을 수 있다. 같은 이름의 테스트 메서드가 둘 이상이면 모호함 오류다.

### 7.2 실행 중 상태

- 작업 실행 요청(`RunRequest`)에 판정할 테스트와 각각 RED만·GREEN만·둘 다인지를 넘긴다. `FsmTaskExecutor`가 명세의 AC를 보고 채운다.
- RED 「이미 통과」 확인은 apply의 대화형 확인과 같은 방식이다. `--yes`면 기록하고 계속한다. 거부하면 그 작업은 실행하지 않고 apply는 종료 2(지금까지 된 작업은 그대로).
- `--review-at-end`에서는 작업이 승인 없이(`Yes`) 돌기 때문에 실행 중에 묻지 않는다. 「이미 통과」를 기록하고 계속한 뒤, 끝의 전체 승인 직전에 「이미 통과한 테스트로 판정된 수용 기준」 목록을 보여 준다(설계 검토 반영, Claude 결정). 거부하면 지금처럼 전체 롤백이다.
- **`--resume`:** 첫 연결 작업이 이미 `[x]`면 그 AC의 RED는 다시 확인하지 않고 「RED 확인 안 함(이어서 하기)」으로 기록한다. 파일이 이미 바뀌어 있어 다시 재면 의미가 없기 때문이다.
- **`--continue`:** GREEN 실패 작업은 v1 실패와 같이 롤백되고 `[ ]`로 남는다. 그 AC는 「불충족」이다.
- **`--review-at-end`:** 판정은 작업마다 하고, 승인만 끝에 한 번 받는다. 「이미 통과」 처리는 위와 같다.
- **`--dry-run`:** 테스트를 돌리지 않는다.

### 7.3 작업 그룹 (Claude 결정)

그룹은 지금 빌드를 그룹 끝으로 미루고 테스트를 전혀 돌리지 않는다. 시그니처 변경에야말로 테스트가 필요하므로 그룹도 지원한다.
- **기준:** 그룹 안 작업이 연결된 AC가 있으면, 그룹 기준 빌드 뒤 영향 범위 안의 테스트 프로젝트 전부의 기준 테스트를 돌린다. 그룹 안에 첫 연결 작업이 있는 AC의 RED를 여기서 확인한다. 새 시그니처로 쓴 테스트는 보통 컴파일 RED다.
- **판정:** 그룹 빌드가 통과한 뒤 같은 테스트 프로젝트를 돌려 GREEN(그룹 안에 마지막 연결 작업이 있는 AC)과 회귀를 본다.
- **GREEN 실패:** 그 AC의 그룹 안 마지막 연결 작업에 §5.5 피드백을 주고 그 작업만 다시 실행한 뒤 그룹 빌드·테스트를 다시 한다. 재시도는 빌드 오류 재실행과 같은 그룹 `retry.max` 하나를 함께 쓴다.
- **회귀:** 새로 실패한 테스트를 어느 작업에도 귀속할 수 없으므로 그룹 전체를 롤백하고 종료 1(빌드에서 「명세에 없는 곳의 오류」와 같은 처리). 메시지에 테스트 이름을 적는다.
- 그룹 테스트를 돌릴 수 없으면 편집 전(기준)이면 종료 4, 편집 뒤면 그룹 롤백 후 종료 4. 그룹의 「검증 불가」와 같다.
- 레거시 그룹은 그룹 빌드부터 Windows 전용이다.

## 8. 기록과 리포트

- **`summary.json`(실행 하나):** 테스트 우선 검증을 한 실행에만 `testFirst`를 더한다. 고정 값과 개수만 둔다: 판정한 테스트 수, RED 상태(`Red`, `RedCompile`, `AlreadyPassed`, `Skipped`(이어서 하기), `NotChecked`), GREEN 상태(`Passed`, `Failed`, `NotChecked`), 회귀 개수. 테스트 이름은 넣지 않는다(이름은 v1처럼 오류 메시지 쪽에만 있고, 비식별 리포트는 메시지를 쓰지 않는다).
- **`apply.json`:** AC별로 결과를 남긴다: RED 상태, GREEN 결과(`Met`, `NotMet`, `Unverified`), 판정한 작업의 run-id. AC ID(`AC1`)는 비식별 리포트에서 지우고 개수만 남긴다.
- **`pelly report`:**
  - **수용 기준 충족률** = GREEN 확인까지 간 AC 중 GREEN·회귀 없음으로 끝난 AC 비율. PRD §12.6은 「테스트가 연결된 작업」 기준이지만, 이 설계는 판정이 AC 단위라 AC로 센다(Claude 결정). 단독 실행(`--verify-test`)은 실행 하나를 AC 하나로 센다. 「미검증」 AC는 분모에서 빼고 따로 개수를 낸다.
  - RED가 「이미 통과」였던 AC는 GREEN이 거의 저절로 나오므로 **분자와 분모 모두에서 뺀다**(설계 검토 반영, Claude 결정). RED 확인 경고율에만 들어간다.
  - **RED 확인 경고율** = RED 확인을 한 AC 중 「이미 통과」 비율. 기록만 한다.
  - 실패 유형 고정 목록(`FailureKinds`)에 `TestGreenFailed`, `TestRegression`, `TestNotFound`, `TestAmbiguous`, `TestUnverifiable`, `TestRedDeclined`, `TestFileChanged`를 더한다. 비식별 허용 목록 규칙은 그대로다.

## 10. 알려진 한계 (설계에서 받아들이는 것)

- **환경 탓 실패도 RED로 보인다.** DB나 네트워크가 필요한 테스트는 기준에서 「실패」하고 패치 뒤에도 실패해 재시도를 다 쓰고 종료 1로 끝난다. 결정론적으로 가를 방법이 없어 RED 실패 메시지를 기록·`--verbose`에 보여 사람이 보게 한다.
- **입력값 하드코딩.** 모델이 테스트 입력에만 맞는 분기를 넣어 GREEN을 만들 수 있다. 테스트 원문을 프롬프트에 넣지 않아 가능성은 낮지만, 피드백의 assert 메시지에 기대값이 보인다. diff 승인이 마지막 방어선이다. 벤치마크에서 사람 표본 검토로 잰다(§12).
- **불안정한 테스트.** 한 번씩만 돌린다. RED가 우연히 통과하면 「이미 통과」 경고가 나고, GREEN이 우연히 실패하면 재시도가 하나 쓰인다.
- **실행 시간.** 시도마다 테스트 프로젝트 전체를 돈다. 큰 테스트 프로젝트에서는 `test.timeoutSeconds`와 `test.projects`로 조절한다.

## 11. 벤치마크와 검증 방법

- **단위·통합 테스트:**
  - 이름 맞추기(점 경계, 데이터 행, 모호함, 짧은 `testName`의 TRX), 테스트 프로젝트 합집합(§5.2a)
  - `breaks:` 파싱과 회귀 제외, 쓸모없는 `breaks:` 경고
  - RED 표의 각 행, 컴파일 RED 귀속
  - GREEN의 「결과에 없음·건너뜀·호스트 사망」 실패
  - 피드백 예산과 스택 프레임 고르기
  - `spec check`의 연결 작업 판정, 오류·경고 승격, 테스트 특성 필터
  - apply의 첫·마지막 연결 작업, `--resume` RED 생략, 그룹 GREEN 재실행과 회귀 롤백
  - 비식별 리포트에 테스트 이름·AC ID가 없음
  - `--verify-test` 없는 실행이 v1과 같은 프롬프트·결과를 내는지(기존 스냅샷 테스트 그대로 통과)
- **E2E 벤치마크 (Claude 결정):**
  - **재료 12건은 이미 있다.** Modern C# 작업 12건(`cs-modern-001`~`012`)의 판정 테스트(`judges/Modern/`)는 원본에서 실패하도록 검사되어 있다(`JudgeTestDefinitionTests`). 이것을 `--verify-test`의 대상으로 쓰는 실행 방식을 `pelly-eval`에 더한다. 판정 프로젝트는 코퍼스 밖에 있고 `JudgeTargetRoot` 속성으로 작업 복사본을 가리키므로, pelly가 그것을 테스트 프로젝트로 쓰게 하는 방법(작업 폴더의 `test.projects`와 속성 전달)은 만드는 사람이 정한다.
  - 12건 중 기존 동작을 고정한 코퍼스 테스트가 있는 사례(`cs-modern-001`의 `failingTests`)는 그 테스트를 `--expect-break`로 넘긴다(§5.2b).
  - **대조 실험:** 같은 12건을 v1 방식(지금의 `pelly-eval`)과 테스트 우선 방식으로 같은 모델·같은 반복 수로 돌려 최종 작업 성공률 차이를 낸다. 규칙 효과 측정(`--no-rules`)과 같은 모양이다. 이 대조가 V2-2의 효과 근거가 된다.
  - **나머지 8건:** apply 명세로 만든다. AC 하나를 여러 작업이 채우는 것, C#+SQL로 SQL이 미검증인 것, 그룹(시그니처 변경 + 새 시그니처로 쓴 컴파일 RED 테스트), 「이미 통과」 사례 하나를 넣는다. 에이전트가 만들고 S6 정답처럼 사람이 승인한다(`APPROVED.json`). 승인 전 측정은 「예비」로 표시한다.
  - 판정 테스트를 GREEN 판정에 쓰므로, 그 사례의 독립 판정은 빌드 + GREEN 테스트의 독립 재실행 + diff 사람 표본 검토(하드코딩 확인)다.
  - 레거시 사례는 Windows에서만 잰다.
- **현장:** 반입 뒤 사람이 현장 테스트 프로젝트에서 `--verify-test`를 써 보고 RED 확인 경고율과 수용 기준 충족률을 `deploy/field-results.md`에 남긴다.

## 13. 만드는 사람에게 맡기는 것

- RED·GREEN 상태를 `RunContext`·`RunRequest`에 싣는 모양, `TestStep`을 넓힐지 새 단계를 둘지.
- TRX에서 전체 이름·스택을 읽는 방법(어댑터별 차이는 픽스처로 확인).
- 피드백 끝 문장의 정확한 문구(재생 실험).
- `pelly-eval`에서 판정 프로젝트를 pelly의 테스트 프로젝트로 넘기는 방법.
- 화면 표시(RED·GREEN 줄, 그룹 테스트 진행)의 모양.
