# `pelly js`·`pelly css` W2 — 페이지 안 `<script>`·`<style>` 수정 설계

작성 2026-11-06. 상태: 설계 초안, 빌더 확인 반영(질문 4건은 「Claude 결정, 빌더 확인 반영」으로 표시).

- **진행 방식:** 사람이 고른 방식은 「질문 없이 바로 설계」다.
- **사람이 알려 준 현장 사실(2026-11-06, 「사람 답」):**
  - 화면만 고칠 때는 ASP만 고친다.
  - 업무 로직을 고칠 때는 ASP와 SP를 함께 고친다.
  - JS는 대부분 페이지 안 `<script>`에 있다. 별도 `.js` 파일에는 유틸·공통 함수만 있다.
- **이 문서가 이어 받는 것:**
  - W1 설계(`docs/superpowers/specs/2026-11-04-pelly-js-css-design.md`)의 §4.8.
  - ASP A1 설계(`docs/superpowers/specs/2026-11-04-pelly-asp-design.md`). 둘 다 main에 구현되어 있다.
- **표시:**
  - 「Claude 결정」·「Claude 짐작」은 사람이 아직 확인하지 않은 판단이다.
  - 「W1과 같음」은 W1 설계·구현의 규칙을 그대로 쓴다는 뜻이다.

## 1. 왜 하는가

**현장 수정의 대부분이 W1 판정 밖에 있다.**
- 현장의 JS 수정은 대부분 `.asp` 페이지 안 `<script>` 블록에서 일어난다(사람 답).
- W1(`pelly js`·`pelly css`)은 따로 있는 `.js`·`.css` 파일만 고친다.
- 그래서 지금은 페이지 안 JS를 `pelly asp --lines`로 고칠 수밖에 없다.

**`pelly asp`는 클라이언트 JS·CSS를 판정하지 않는다.**
- `pelly asp`는 클라이언트 JS·CSS를 그냥 텍스트로 본다.
- 규칙 검사의 코드 가리기(`CodeMask.Asp`)도 VBScript 토큰만 남기고 JS·CSS는 지운다.
- 그래서 괄호가 하나 빠지거나, IE에서 안 도는 화살표 함수가 들어가거나, `eval`이 들어가도 아무 검사에도 걸리지 않는다. 문제는 운영 화면에서야 드러난다.

W2는 W1의 JS·CSS 판정을 페이지 안 블록에 그대로 쓴다. 쓰는 방법은 두 가지다.
1. `pelly js`·`pelly css`가 페이지를 받아 블록 안의 함수·규칙·줄 범위를 고친다.
2. `pelly asp --lines`로 고친 범위가 클라이언트 블록에 걸치면, 그 블록에 JS·CSS 판정을 더한다.

## 2. 목표 / 비목표 / 실패 조건

**목표**
1. `pelly js <페이지> "<요청>"`가 페이지 안 클라이언트 `<script>` 블록의 함수 하나 또는 줄 범위를 고친다.
   - 대상 지정 방식(`--function`·`--line`·`--lines`)은 W1과 같다.
   - `pelly css <페이지>`도 `<style>` 블록에서 같은 방식으로 고친다.
   - 페이지 = `asp.extensions`(기본 `.asp`·`.inc`) + `.htm`·`.html`이다(Claude 결정).
2. 판정은 W1과 같다.
   - 막는 검사: 패치·인코딩·문법·문법 수준·대상 모양·안전.
   - 경고만 하는 검사: 이름·API·CSS 속성·덮어쓰기.
   - 여기에 더해 **블록 밖 페이지(HTML·ASP 코드)가 바이트 그대로**인지 확인한다.
3. `pelly asp --lines`의 범위가 클라이언트 블록에 걸치면, 걸친 블록마다 JS·CSS 판정을 ASP 판정 표에 행으로 더한다.
   - 새로 생긴 문법 오류·문법 수준 초과·안전 문제는 막는다.
   - 이름·API 문제는 경고만 한다.
4. 블록 안의 ASP 출력식 `<%= … %>`를 해석할 수 있게 다룬다(§4.3).
5. JS 이름 검사가 페이지에서 보이는 이름을 안다(§4.6).
   - 같은 페이지의 다른 블록, include한 `.inc`의 블록, `<script src>`로 부르는 `.js`.
6. jQuery 기준 버전을 그 페이지가 실제로 부르는 jQuery로 정한다(§4.6).
7. `pelly edit <페이지>`가 대상 위치를 보고 js·css·asp 중 하나로 보낸다(§4.8).
8. `summary.json`·`pelly report`·README·`deploy/usage.md`·PRD·`deploy/field-results.md`·자동완성에 반영한다.

**비목표**
- 인라인 이벤트 속성(`onclick="fnSave()"`), `style="…"` 속성, `href="javascript:…"`. 판정 단위(블록)가 아니고 한 줄짜리라 실익이 적다(Claude 결정). 이런 곳은 `pelly asp --lines`로 고친다(지금과 같이 텍스트로).
- VBScript 문자열로 출력하는 스크립트(`Response.Write "<script>…</script>"`). 서버 코드이므로 ASP 판정만 한다.
- 클라이언트 VBScript(`<script language="vbscript">`)와 `text/template` 등 JS가 아닌 `<script>`. 블록으로 보지 않는다(HTML 그대로).
- `pelly js`로 서버 코드(`<% … %>`, `<%= … %>`) 바꾸기. 블록 안의 ASP 코드는 읽기 전용이다(§4.4). 서버 값이 새로 필요하면 `pelly asp --lines`를 쓴다. 이때 W2가 그 블록에 JS 판정을 더한다.
- 브라우저 실행 검증(W1·ASP와 같음).
- 명세(`pelly spec`·`apply`)의 `js`·`css` 작업 종류, 함수 이름 변경과 부르는 곳 함께 고치기. W3에 남긴다.

**실패 조건 (기술적으로 돌아가도 실패로 본다)**
- 블록 밖 HTML·ASP 코드의 바이트가 바뀐다. 인코딩이 바뀌어 한글이 깨지는 경우도 포함한다.
- `<%= … %>`가 든 정상 스크립트를 「문법 오류」로 막는다. 현장 페이지 대부분이 서버 값을 JS 변수에 넣으므로, 이걸 못 다루면 W2는 쓸 수 없다.
- 원본 페이지에 이미 있던 JS 오류나 낡은 문법 때문에 아무것도 못 고친다. 블록마다 원본을 기준선으로 쓰고 **새로 생긴 것만** 본다.
- 이름 검사가 페이지 안 다른 블록이나 include에 있는 함수를 「모르는 이름」으로 쏟아낸다.
- 수정이 `</script>`를 새로 넣어 블록이 일찍 끝난다. 브라우저에서 뒤쪽 코드가 HTML로 보이게 된다.

## 3. 사용 흐름

```
pelly js  admin/order/list.asp "검색 버튼 누를 때 주문 상태도 넘겨 줘" --function fnSearch
pelly js  admin/order/list.asp "날짜 입력 검사에서 빈 값은 통과" --line 214
pelly js  admin/member/edit.asp "휴대폰 번호 하이픈 자동 입력" --lines 140-175
pelly css admin/order/list.asp "목록 표 머리글 높이 32px" --selector ".list_tbl th"
pelly asp admin/order/list.asp "검색 조건에 상태 추가" --lines 30-180    # 서버+클라이언트를 함께 고침, 걸친 블록에 JS 판정 추가
pelly edit admin/order/list.asp "…" --line 214                           # 214줄이 <script> 안이면 js로 보냄
```

- **대상 지정:** W1과 같은 옵션을 쓴다. 다른 점만 적는다.
  - `--function <이름>`: 페이지 안의 **모든 클라이언트 `<script>` 블록**에서 찾는다.
    - 같은 이름이 여러 블록에 있으면 선택 화면에 줄 번호를 함께 보인다(비대화형이면 종료 3).
    - include한 `.inc`의 함수는 찾지 않는다. 대상은 지정한 파일 안에만 있다.
  - `--line N`: N번 줄이 클라이언트 블록 안이어야 한다.
    - 블록 밖이면 종료 3. 문구: 「N번 줄은 <script> 블록 안이 아닙니다. pelly asp를 쓰십시오」.
    - 블록 안에서는 이름 있는 가장 안쪽 함수를 찾는다(W1과 같음).
  - `--lines A-B`: 범위가 **블록 하나의 내용 안에 완전히** 들어가야 한다.
    - 여는·닫는 태그를 포함하거나 블록 밖에 걸치면 종료 3. 문구: 「줄 A-B 범위가 <script> 블록 밖에 걸칩니다. pelly asp --lines를 쓰십시오」.
    - 문장 경계 규칙은 W1과 같다.
  - 셋 다 없을 때:
    - 페이지 전체에서 이름 있는 함수가 하나뿐이면 그것을 대상으로 한다.
    - 여럿이면 선택 화면을 보인다(W1과 같음).
    - 클라이언트 블록이 없으면 종료 3: 「이 페이지에는 고칠 수 있는 <script> 블록이 없습니다」.
  - `pelly css`도 같은 규칙이다(`<style>`, `--selector`). 셋 다 없으면 멈춘다(W1과 같음).
- 그 밖의 옵션과 종료 코드는 W1과 같다.

## 4. 설계

### 4.1 클라이언트 블록 찾기 (페이지 해석기 확장)

ASP 페이지 해석기(`AspPage`)는 지금 클라이언트 `<script>`·`<style>`을 HTML 구간으로 둔다. `runat="server"`만 따로 본다. 여기에 **클라이언트 블록 목록**을 더한다.

- **구간 종류를 새로 만들지 않는다.** 블록 안에도 `<% … %>`·`<%= … %>` 구간이 끼어 있기 때문이다.
  - 그래서 블록은 기존 구간 목록과 **겹쳐서** 존재하는 별도 목록이다.
  - 각 블록에 담는 것: 종류(Js·Css), 여는 태그 위치, 내용 시작·끝 위치, 닫는 태그 위치, `type`·`language`·`src` 속성 값(Claude 결정).
  - 이렇게 하면 A1 해석·판정 동작이 바뀌지 않는다.
- **블록으로 보는 것:**
  - `<script>`: `runat="server"`가 없어야 한다. `type`이 없거나 `text/javascript`·`application/javascript`·`text/jscript`·`module`이어야 한다. `language`가 없거나 `javascript`(·`javascript1.x`)·`jscript`여야 한다.
  - `<style>`: `type`이 없거나 `text/css`여야 한다.
  - 대소문자는 구분하지 않는다.
- **블록으로 보지 않는 것:**
  - 일반 HTML 주석(`<!-- … -->`) 안의 태그. 브라우저도 실행하지 않는다.
  - ASP 코드 구간(문자열 포함) 안의 태그.
- **블록이 끝나는 곳:** 여는 태그 뒤 처음 나오는 `</script`(`</style`)다. 대소문자는 구분하지 않는다.
  - JS 문자열 안의 `"</script>"`도 블록을 끝낸다. 브라우저 규칙과 같다. ASP의 「문자열 안 `%>`도 코드를 끝낸다」와 같은 원칙이다.
  - ASP 구간 안의 `</script`는 세지 않는다. 서버가 처리하고 브라우저에 가는 텍스트가 아니기 때문이다.
- **`src`가 있는 `<script>`:** 내용이 비어 있으면 고칠 블록이 아니다. 다만 §4.6의 이름·jQuery 정보로 쓴다.
- **닫히지 않은 블록:** 원본에 닫는 태그가 없으면 그 블록은 대상이 될 수 없다. 종료 3: 「줄 N의 <script>가 닫히지 않았습니다」.

### 4.2 블록 판정용 텍스트 (줄 번호 유지)

W1의 해석기와 검사 API(`JsDocument.Parse`, `JsLevels.Detect`, `JsChecks`, `CssSheet.Parse`, `CssChecks`)는 텍스트 전체를 받고, 그 텍스트 기준의 줄·열을 돌려준다.

W2는 이 API를 바꾸지 않는다. 대신 **블록마다 「페이지 크기의 보기 텍스트」**를 만든다(Claude 결정). 그러면 결과 줄 번호가 곧 페이지 줄 번호다. 대상 범위·피드백·REVIEW가 W1 코드를 그대로 쓴다.

- **보기 텍스트 만드는 법:**
  - 그 블록의 **내용**만 남긴다.
  - 블록 밖(여는·닫는 태그 포함)은 공백으로 바꾸고 줄바꿈은 그대로 둔다(`CodeMask`와 같은 방식).
  - 블록 안의 ASP 구간은 §4.3대로 바꾼다.
- **블록마다 따로 판정한다.** 브라우저는 `<script>` 블록마다 따로 해석·실행한다. 블록 하나의 문법 오류는 그 블록만 망가뜨린다.
  - 그래서 블록마다 다음을 따로 정한다: 문법 수준(원본 기준선), 원본 해석 결과, 안전 기준선.
- **블록 안의 오래된 HTML 주석 감싸기:** `<!--`로 시작해 `//-->`로 끝나는 옛 숨김 방식이 흔하다(Claude 짐작).
  - 이 두 줄(앞뒤 공백만 있는 줄)은 보기 텍스트에서 공백으로 바꾼다.
  - Acornima가 ES 부록 B의 HTML 모양 주석을 스스로 받는지는 빌더가 확인한다. 받으면 바꾸지 않아도 된다.
  - `//<![CDATA[`·`//]]>`는 JS 주석이라 그대로 둔다.

### 4.3 블록 안의 ASP 코드

**`<%= 식 %>`(출력):** 보기 텍스트에서 자리 표시 이름 `__aspN__`(N = 블록 안 순번)으로 바꾼다.
- 자리 표시는 원래 구간의 첫 줄에 둔다. 구간이 여러 줄이면 나머지 줄은 빈 줄로 만들어 줄 번호를 지킨다.
- 해석 결과는 위치에 따라 다르다.
  - 문자열 안(`'<%= no %>'`)이면 문자열의 일부가 된다.
  - 밖(`var cnt = <%= cnt %>;`)이면 식별자가 된다.
- 자리 표시 이름은 이름 검사·API 검사에서 뺀다.
- `<%= %>` 뒤에 바로 이름 글자가 붙어 있는 모양(`fn<%= n %>()`)도 식별자 하나로 이어져 해석된다(Claude 짐작). 빌더는 코퍼스로 확인한다.

**`<% 문장 %>`(분기·반복):** `<% If … %> … <% End If %>`처럼 블록 안에 서버 문장이 있으면, 분기마다 다른 JS가 브라우저에 간다. 한 번에 해석할 수 없다.
- 그런 블록의 JS 문법·문법 수준 검사는 「건너뜀(서버 코드가 섞인 스크립트)」이다.
- 대신 W1의 대체 경로를 쓴다. 문장 구간을 공백으로 바꾼 텍스트에 괄호·문자열·주석 짝 비교(`JsTokenScan`)를 하고, 안전 검사도 텍스트 기준으로 한다.
- 원본 해석이 실패한 블록과 같은 처리다.
- 대상 지정도 W1 대체 경로(`function 이름(` 모양)로 한다.

**ASP 지시문·include 구간**이 블록 안에 있으면 문장 구간과 같이 취급한다(Claude 결정, 드물다).

### 4.4 쓰기와 블록 밖 보호

**쓰기:** 인코딩을 정하고 바이트를 이어 붙이는 쓰기는 ASP 부품(`AspTextCodec`, `SplicingTextCodec`)을 쓴다. 페이지 인코딩 규칙은 A1과 같다(BOM → `CodePage` → 엄격한 UTF-8 → CP949 → 순수 ASCII는 `asp.encoding`).
- `.htm`·`.html`에는 `CodePage`가 없다. 그래서 BOM 다음에 `<meta charset="…">`·`<meta http-equiv="Content-Type" content="…; charset=…">`를 읽는다(Claude 결정).
- 받는 값은 W1 `@charset`과 같다: `utf-8` → UTF-8, `euc-kr`·`ks_c_5601-1987` 등 → CP949, 그 밖은 종료 4.

**APPLY에서 쓰기 전에 하는 검사 (앞이 실패하면 뒤는 하지 않는다):**
1. **패치·인코딩:** W1과 같다. 편집 영역은 대상 범위(블록 내용 안)다.
2. **블록 경계:** 수정한 페이지를 다시 해석해 클라이언트 블록 목록을 원본과 비교한다.
   - 블록 개수, 블록마다 여는·닫는 태그, 대상 블록 밖의 모든 바이트가 같아야 한다.
   - 다르면 피드백 후 재시도한다.
   - 새 실패 유형 `WebBlockChanged`: 「수정이 <script> 블록 경계를 바꿨습니다(예: 문자열 안 </script>)」. 모델 피드백은 영어로, `"</script>"` 대신 `"<\/script>"`를 쓰라고 알려 준다.
3. **블록 안 ASP 코드 그대로:** 대상 블록 안 ASP 구간(`<% %>`, `<%= %>`)의 순서와 내용이 원본과 같아야 한다.
   - 다르면 재시도. 새 실패 유형 `WebServerCodeChanged`.
   - 끝내 안 되면 종료 1. REVIEW 문구: 「서버 값이 필요하면 pelly asp --lines를 쓰십시오」.
   - 이유: 서버 코드가 바뀌면 ASP 판정(이름·컴파일·안전)이 필요한데, `pelly js`는 그걸 하지 않는다(Claude 결정).
4. **JS·CSS 판정:** W1 순서와 같다(문법 → 수준 → 모양 → 안전). 대상 블록의 보기 텍스트로 판정한다.
5. **ASP 판정:** ASP 구조 검사를 「새 문제 없음」으로 한 번 확인한다. 2·3이 통과하면 사실상 늘 통과하지만, 안전망으로 남긴다.

**VERIFY:** 이름·API 경고(§4.6), 규칙(`RulesStep`)을 한다.
- 규칙 검사의 코드 가리기는 **블록 보기 텍스트**를 쓴다. 그래서 프로젝트 규칙의 JS 금지 패턴이 페이지 안 JS에도 걸린다.
- 이를 위해 `CodeMask`에 페이지 블록용 가리기를 더한다.

**REVIEW:** W1 고정 문구를 보이고, 대상 블록 위치를 한 줄 더한다(「admin/order/list.asp 120–260줄 <script> 블록」).

### 4.5 `pelly asp --lines`가 블록에 걸칠 때

**적용 범위:** 원본 편집 영역(`EditableRegions`)과 겹치는 클라이언트 블록마다 JS·CSS 판정을 더한다.
- 줄 범위 모드(`--lines`)와 프로시저 모드(`--proc`) 모두 해당한다.
- Classic ASP에서는 `<% Sub DrawScript() %><script>…</script><% End Sub %>`처럼 프로시저 몸체 안에 클라이언트 블록이 들어갈 수 있다. 그런데 프로시저 모드의 편집 영역은 그 HTML까지 포함한다(Claude 결정, 빌더 확인 반영).
- 이 절의 「줄 범위」는 이 편집 영역을 말한다.
- 수정 뒤 블록 목록이 원본과 다르면(블록을 새로 넣거나 지움) 이렇게 비교한다.
  - **겹친 블록:** 원본의 같은 순번 블록과 비교한다.
  - **새 블록:** 원본 기준선이 빈 블록이다. 그래서 문법 수준 기준선은 사이트·페이지 기본(`web.jsTarget`, `auto`면 페이지의 다른 블록 중 가장 낮은 수준, 블록이 없으면 ES5)이다(Claude 결정).

**ASP 판정 표에 더하는 행:**

| 행 | 막는가 | 내용 |
|---|---|---|
| `JsSyntax` | 막음(재시도) | 새로 생긴 문법 오류 |
| `JsLevel` | 막음(재시도) | 문법 수준 초과 |
| `JsSafety` | 막음(재시도, 끝내 남으면 종료 5) | 새로 생긴 안전 문제 |
| `CssSyntax` | 막음(재시도) | 새로 생긴 구조 문제 |
| `CssSafety` | 막음(재시도, 끝내 남으면 종료 5) | 새로 생긴 안전 문제 |
| `JsNames` | 경고 | 이름 경고(§4.6) |
| `JsApi` | 경고 | API 경고 |

- 막는 행은 `AspApplyPhase`의 구조 검사 뒤, 쓰기 전에 둔다. 경고 행은 VERIFY 단계로 둔다. 정확한 자리는 빌더가 정한다.
- 블록 안에 바뀐 `<%= %>`가 있어도 된다. ASP 판정이 이미 서버 코드를 본다.
- **규칙 검사(`RulesStep`)는 `pelly asp`에서 바꾸지 않는다**(Claude 결정, 빌더 확인 반영). `CodeMask.Asp`는 지금처럼 VBScript만 드러낸다.
  - 이유: 프로젝트 규칙의 금지 패턴에는 언어 구분이 없다. 블록을 드러내면 VBScript용 패턴이 JS에 걸리는 등 기존 `pelly asp` 결과가 바뀐다.
  - 그래서 `pelly asp`로 고친 페이지 안 JS에는 프로젝트 규칙이 걸리지 않는다. README에 이 한계를 적는다.
  - 규칙에 언어 구분을 더하는 일은 나중에 정한다.
- `<% 문장 %>`이 섞인 블록은 §4.3대로 짝 비교로 낮춘다.

**ASP 프롬프트:** 고정 규칙에 한 줄을 더한다: 「클라이언트 `<script>` 안에서는 [READ-ONLY: env]의 JS 문법 수준을 지킨다」. 줄 범위가 블록에 걸칠 때만 [READ-ONLY: env]에 그 블록의 JS 문법 수준·jQuery 버전을 넣는다. 프롬프트 판은 `asp-v2`로 올린다.

### 4.6 이름과 jQuery — 페이지에서 보이는 것

**페이지가 부르는 `.js`:**
- 그 페이지와 그 페이지가 include한 파일(A1 `AspIncludeResolver`를 재귀로, 같은 깊이 제한)의 `<script src="…">`를 모은다.
- 경로는 브라우저 규칙으로 푼다. `/`로 시작하면 사이트 루트 기준, 아니면 페이지 폴더 기준이다(Claude 결정).
- 이렇게 모은 `.js`를 「페이지가 부르는 `.js`」라고 부른다.
- `http(s)://`로 시작하는 외부 주소와 `<%= %>`가 든 주소는 무시한다.

**JS 이름 검사(경고만)가 아는 이름:** W1 목록에 다음을 더한다.
- 같은 페이지의 **다른 클라이언트 블록**의 최상위 선언(함수·`var`).
- include한 파일의 클라이언트 블록 최상위 선언.
- 페이지가 부르는 `.js`의 최상위 선언. 사이트 색인에 이미 있지만, 그 파일이 라이브러리(`web.vendorPaths`)여도 여기서는 넣는다.
  - 예: `jquery.form.js` 플러그인의 `$.fn.ajaxForm`은 메서드라 이름 검사와 무관하다. 하지만 플러그인이 만든 전역 함수가 있을 수 있다(Claude 짐작).
- **사이트 색인 확장:** 사이트 색인이 `.js` 파일뿐 아니라 **모든 페이지의 클라이언트 블록 최상위 선언**과 **페이지마다 include 목록**도 담는다.
  - 캐시는 W1과 같이 `.pelly/cache/`에 파일 해시와 함께 둔다.
  - 파일 수 한도는 `.js`와 페이지가 따로 쓴다(각각 W1의 2000). 그래서 페이지가 많아도 `.js`가 잘려 나가지 않는다.
  - (Claude 결정, 빌더 확인 반영)
- **페이지 블록 선언을 「아는 이름」으로 치는 범위:** 색인은 `.js` 선언과 페이지 블록 선언을 **구분해서** 담는다(Claude 결정, 빌더 확인 반영).
  - **`.js` 파일 대상(W1):** `.js` 선언과 **모든 페이지 블록 선언**을 아는 이름으로 친다. 공용 `.js`가 페이지 안 전역 함수를 부르는 일이 흔하기 때문이다. W1의 「확신할 수 없다」 경고가 줄어든다.
  - **페이지 대상:** `.js` 선언(W1과 같음)과 위 「그 페이지에서 보이는 이름」만 친다. 다른 페이지에만 있는 함수는 그 페이지에서 보이지 않으므로 경고한다. 모든 페이지 블록을 치면 이름 검사가 사실상 꺼진다.
- **`.inc` 대상 — 위쪽 맥락:** 공용 `.inc` 안의 `<script>`는 그 `.inc`를 include하는 페이지의 jQuery·함수를 쓴다. 그래서 대상이 `.inc`면 색인의 include 목록으로 **그 `.inc`를 (직접이든 거쳐서든) include하는 페이지**를 찾는다(Claude 결정, 빌더 확인 반영).
  - **이름:** 그 페이지들에서 보이는 이름의 **합집합**을 아는 이름으로 친다.
  - **jQuery:** 그 페이지들이 부르는 jQuery 중 **가장 낮은 버전**을 쓴다. 출처는 `page`로 적는다.
  - **부르는 페이지가 없을 때:** 페이지 대상과 같이 아래쪽만 본다.

**jQuery 기준 버전 순서:**
1. `web.jqueryVersion` 설정.
2. 페이지가 부르는 `.js` 중 jQuery 본체의 버전. W1과 같이 머리 주석, 없으면 파일 이름에서 읽는다. 여럿이면 가장 낮은 것.
3. 사이트에서 찾은 가장 낮은 버전(W1).

REVIEW·`summary.json`에 어디서 정했는지 적는다: `setting`·`page`·`site`.

### 4.7 모델 입력

형식과 예산은 W1과 같다. 프롬프트는 W1 것(`js-v1`·`css-v1`)을 쓰되, 페이지일 때 고정 규칙을 더한 판 `js-page-v1`·`css-page-v1`을 따로 둔다(Claude 결정). `.js` 파일 동작은 바뀌지 않는다.

**`pelly js` (페이지):**
1. **[EDITABLE: target]** 대상 범위. 원문 그대로 둔다. `<%= %>`도 그대로 보인다.
2. **[READ-ONLY: env]** W1 항목, 그리고 다음을 넣는다.
   - 「ASP 페이지의 <script> 블록」.
   - 블록 문법 수준.
   - jQuery 버전과 출처.
   - 고정 문구: 「`<%= … %>`와 `<% … %>`는 서버 코드다. 바꾸거나 새로 쓰지 않는다」.
   - 고정 문구: 「`</script>`를 문자열에 쓰지 않는다(`<\/script>`)」.
3. **[READ-ONLY: callees]** W1과 같다. 찾는 범위에 같은 페이지 블록과 페이지가 부르는 `.js`를 더한다.
4. **[READ-ONLY: page]** 같은 페이지 다른 블록과 include 블록의 최상위 선언 목록(이름·매개변수). W1 [READ-ONLY: file]의 자리다.
5. **[READ-ONLY: html]** 대상 함수·범위가 쓰는 id·name이 붙은 HTML 요소의 태그 줄. `$("#x")`, `document.getElementById("x")`, `frm.x`, `$("[name=x]")`에서 문자열 리터럴인 것만 모은다. 최대 20줄.
   - 이유: 「검색 조건 추가」류 요청에서 모델이 입력 칸 이름을 지어내지 않게 한다(Claude 결정).
6. **[READ-ONLY: around]** 대상 앞뒤 10줄. 블록 밖이면 HTML·ASP 원문 그대로다.

**`pelly css` (페이지):** W1 목록에 [READ-ONLY: env]의 「ASP 페이지의 <style> 블록」을 더한다. [READ-ONLY: related]는 같은 페이지의 다른 `<style>` 블록에서도 찾는다.

### 4.8 `pelly edit`이 페이지를 보내는 곳

지금은 `asp.extensions`에 맞는 파일이 늘 `pelly asp`로 간다. W2에서는 대상을 보고 고른다(Claude 결정). 페이지 = `asp.extensions` + `.htm`·`.html`이다. `.htm`·`.html`은 지금 `pelly edit`이 거절하는 확장자다.

| 지정 | 보내는 곳 |
|---|---|
| `--function` | js |
| `--selector` | css |
| `--proc` | asp |
| `--line N` | N번 줄이 클라이언트 `<script>` 안이면 js, `<style>` 안이면 css, 아니면 asp |
| `--lines A-B` | 범위 전체가 블록 하나의 내용 안이면 js·css, 아니면 asp(걸친 블록은 §4.5로 판정) |
| 지정 없음 | asp. `.htm`·`.html`이면 js |

- `.htm`·`.html`은 `pelly asp`가 받지 않는다. 그래서 asp로 가야 할 지정이면 종료 4로 안내한다: 「.htm 파일의 HTML 부분은 고치지 않습니다」(Claude 결정).
- 고른 결과는 W1처럼 한 줄로 보인다: 「admin/order/list.asp 214줄 → <script> 블록이라 pelly js로 실행합니다」.
- 다른 언어 전용 옵션(예: `--proc`과 `--function`을 함께 줌)은 지금처럼 종료 4.
- 줄 위치를 보려면 파일을 읽고 해석해야 한다. 그래서 `pelly edit`은 이 판정만 하고, 나머지는 고른 명령에 맡긴다. 인코딩이 틀리면 고른 명령이 보고한다.

### 4.9 결과와 기록

- `EditKind`는 그대로 `Js`·`Css`·`Asp`다.
- `summary.json`의 `web` 블록에 더하는 것:
  - `container`: `"file"` 또는 `"page"`.
  - `block`: 페이지일 때만. `{ "kind": "script"|"style", "startLine", "endLine", "serverCode": "none"|"output"|"statements" }`.
  - `jquerySource`: `setting`·`page`·`site`.
- `asp` 블록의 `checks`에 §4.5의 행 이름(`JsSyntax` 등)이 생긴다.
- `pelly report`: W1의 JS·CSS 줄에 「페이지 안 K건」을 덧붙인다.
- 새 실패 유형: `WebBlockChanged`, `WebServerCodeChanged`, `WebOutsideBlock`.
  - `WebOutsideBlock`은 대상이 블록 밖이라는 뜻이다(종료 3).
- `pelly doctor`: 바뀌지 않는다. 사이트 색인 크기를 보이지 않는 W1 결정과 같다.

  - `type`·`language`별 포함·제외.
  - `runat="server"` 제외, HTML 주석 안 제외, VBScript 문자열 안 제외.
  - 문자열 안 `</script>`에서 끝남, ASP 구간 안 `</script`는 무시, 닫히지 않은 블록.
  - `src` 블록, 대소문자.
- **보기 텍스트:**
  - 줄 번호가 페이지 줄과 같다.
  - `<%= %>` 자리 표시(문자열 안·밖·여러 줄).
  - `<% If %>` 블록은 짝 비교로 낮아짐.
  - 옛 `<!--`·`//-->` 감싸기.
- **대상:**
  - `--function`이 여러 블록에서 찾음, 같은 이름이 둘이면 선택.
  - `--line`·`--lines`가 블록 밖이거나 걸치면 종료 3.
  - 블록 없는 페이지.
- **쓰기·보호:**
  - 블록 밖 바이트 그대로(CP949, 줄 끝 섞임).
  - `</script>` 넣기 → `WebBlockChanged` 재시도.
  - `<%= %>` 바꾸기 → `WebServerCodeChanged`.
  - `.htm` `<meta charset>`.
- **판정:**
  - 블록별 기준선. 원본 오류가 있는 블록 + 다른 블록 수정 → 통과.
  - ES5 블록에 화살표 → 거절.
  - 새 `eval` → 거절.
  - 다른 블록·include 블록·부르는 `.js`의 이름은 경고 없음.
  - jQuery 출처 순서.
- **`pelly asp --lines`:**
  - 블록에 걸친 범위에서 JS 문법 오류 → 거절.
  - 블록을 새로 넣은 경우 기준선.
  - 블록에 안 걸친 범위는 행 없음.
- **`pelly edit`:** §4.8 표의 각 줄.
- **사이트 색인:** 페이지 블록 선언이 들어가고, 파일이 바뀌면 캐시가 갱신된다.
- **게이트:** `dotnet build -warnaserror` 종료 0, `dotnet test` 실패 0.

## 7. 사람이 확인할 것

**결정 (아직 없음 — 아래 Claude 결정 중 바꾸고 싶은 것)**
- 블록 안 서버 코드는 `pelly js`에서 읽기 전용이다. 서버 값이 새로 필요하면 `pelly asp --lines`로 고친다(§4.4).
- `pelly edit`이 줄 위치로 js·css·asp를 고른다(§4.8).
- 인라인 이벤트 속성(`onclick=`)은 대상이 아니다(§2).
- 페이지 대상의 이름 검사는 그 페이지에서 보이는 이름만 안다. 다른 페이지에만 있는 함수는 경고한다(§4.6).
- `.inc` 대상은 그 `.inc`를 include하는 페이지에서 jQuery·이름을 가져온다(§4.6).
- `pelly asp --proc`도 프로시저 안 클라이언트 블록에 JS·CSS 판정을 더한다(§4.5).
- `pelly asp`의 규칙 검사는 페이지 안 JS를 보지 않는다(§4.5).

**현장 (`deploy/field-results.md` §17에 더함)**
- 페이지 안 `<script>`에 `<% If %>` 같은 서버 문장이 얼마나 섞여 있는가. 많으면 짝 비교로 낮아지는 블록이 많아진다. 그러면 분기별로 펼쳐 해석하는 확장을 검토한다.
- 공용 머리 `.inc`가 jQuery·공용 JS를 `<script src>`로 부르는가(§4.6 jQuery 출처).
- 실제 요청 3건(페이지 안 JS 2건, `pelly asp --lines`로 서버+클라이언트 1건)의 결과와 화면 확인.
