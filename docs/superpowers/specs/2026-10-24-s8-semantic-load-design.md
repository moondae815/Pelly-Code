# S8 의미 분석 불러오기 측정 설계

작성 2026-10-24. 상태: 설계(사람 승인 전). 설계 검토(빌더 확인) 반영.

## 1. 왜 하는가

S6([docs/s6-planning-probe.md](../../s6-planning-probe.md))에서 두 가지가 확인되었다.

- **호출부·구현체 찾기는 모델이 못한다.** 시그니처를 바꾸는 범주 A에서 모델(생각 켬)의 쓸 만함은 5/15였다.
- **이름만 보는 코드 탐색은 헷갈린다.** 구문 탐색(arm C)은 재현율 1.00이었지만, 이름이 같은 다른 메서드(`IOrderService.GetOrder`)의 호출부를 금지 대상인데도 끌어왔다.

LSP 서버를 붙이는 것도 검토했다. 그러나 C# LSP 서버도 내부에서는 Roslyn으로 솔루션을 읽는다. Pelly는 이미 .NET이고 Roslyn(`Microsoft.CodeAnalysis.CSharp` 5.9.0)을 쓰므로, 같은 기능을 `MSBuildWorkspace`로 직접 얻는 쪽을 먼저 본다.

지금 Pelly의 C# 분석은 모두 구문 분석이다(`MemberLocator`, `RoslynSlicer`, `DtoCollector` 등). 의미 분석으로 넘어가기 전에 답해야 할 것은 「현장 솔루션이 의미 분석용으로 제대로 읽히는가」다. 이 실험이 그것을 잰다. 효과 측정(S6 arm C를 의미 탐색으로 다시 재기)과 제품 적용은 이 실험의 결과를 보고 따로 정한다.

**묻는 질문:** Pelly와 같은 배포 형태(.NET 10, self-contained)의 도구가 현장 솔루션을 `MSBuildWorkspace`로 불러왔을 때
1. 오류 없이 불러와지는가
2. 불러온 뒤 타입 정보가 실제로 채워지는가
3. 몇 초 걸리는가
4. 단일 파일 exe로 배포해도 되는가

## 2. 현장 조건 (사람이 알려 준 것)

- 솔루션 하나에 프로젝트는 보통 4개이고, 1개인 것도 있다.
- Visual Studio 2025를 쓰고, 솔루션을 여는 데 오래 걸리지 않는다.
- 현장 측정은 사람이 직접 한다. 시기는 Pelly가 어느 정도 준비된 뒤다. 그래서 이 실험의 현장 단계는 M4 반입과 묶지 않고, 언제든 들고 가서 돌릴 수 있는 독립 도구로 만든다.

## 3. 목표 / 비목표 / 실패 조건

**목표**
- 세 환경(macOS 개발 PC, GitHub Windows 러너, 현장 PC)에서 코퍼스와 현장 솔루션을 불러와 위 네 질문에 수치로 답한다.
- 「열리긴 했는데 타입 정보가 비어 있는」 조용한 반쯤 실패를 별도로 잡는다.
- 코퍼스에서는 S6 a3의 정답과 대조해 참조 찾기·구현 찾기가 맞는지 확인한다.

**비목표**
- 제품 코드(`src/`)를 바꾸지 않는다. 스파이크 디렉터리에만 둔다.
- LSP 서버를 띄우지 않는다.
- SQL 의미 분석은 다루지 않는다(지금처럼 ScriptDom과 DB 메타데이터).
- 모델 성능 효과는 재지 않는다. 그것은 다음 단계(S6 arm C 재측정)의 일이다.

**실패 조건** (돌아가도 실험이 무효인 경우)
- 불러오기 성공을 「예외 없이 끝남」으로만 판정했다. 타입 정보가 비어도 예외는 나지 않는다. 반드시 3.2의 해석률과 컴파일 오류 수로 판정한다.
- 현장 보고에 코드, 파일 이름, 심볼 이름이 들어갔다. 현장 결과는 폐쇄망 밖으로 가지고 나와야 하므로 숫자만 담는다.
- 판정 기준을 결과를 본 뒤에 바꿨다.

## 4. 제약

- 위치: `spikes/S8-semantic-load/`. S1~S6과 같은 .NET 10 스파이크이고, `spikes/Directory.Build.props`의 설정을 따른다. 번호 S7은 Rider 확인에 이미 쓰였으므로 S8을 쓴다.
- 패키지: `Microsoft.CodeAnalysis.Workspaces.MSBuild`와 `Microsoft.CodeAnalysis.CSharp.Workspaces`. 둘 다 제품과 같은 5.9.0이다. 그 버전이 없으면 가장 가까운 5.x를 쓰고, 버전을 보고서에 적는다.
- 레거시(.NET Framework, 비 SDK 형식) 프로젝트는 Roslyn이 별도 보조 프로세스(BuildHost, net472)를 띄워 Visual Studio의 MSBuild로 읽는다. SDK 형식은 .NET 보조 프로세스로 읽는다. 이 보조 프로세스가 배포물 안에서 뜨는지가 측정 대상이다.
- 사전 확인한 사실 (설계 검토, 2026-10-24):
  - **보조 프로세스 위치:** `Microsoft.CodeAnalysis.Workspaces.MSBuild` 5.9.0은 NuGet에 있고 net10.0을 지원한다. 보조 프로세스는 NuGet contentFiles로 와서 `BuildHost-net472/`(exe)와 `BuildHost-netcore/`(dll)에 놓인다.
  - **.NET 보조 프로세스는 `dotnet`이 필요하다.** 이 프로세스는 프레임워크 종속(net8.0, rollForward Major)이라 `dotnet`으로 실행된다. 그래서 도구를 self-contained로 만들어도 SDK 형식 프로젝트를 읽으려면 그 PC에 .NET이 있어야 한다. Pelly도 SDK 형식 프로젝트는 이미 `dotnet build`로 검증하므로(`BuildToolResolver`) 새 요구 사항은 아니다. 현장 질문지 3-2가 SDK 버전을 묻는다.
  - **단일 파일 배포만으로는 실패했다.** osx-arm64 작은 앱으로 확인했다. 보조 프로세스의 dll·exe가 묶음 안에 들어가 「build host not found」로 실패했다. 폴더 배포는 되었다.
  - **macOS의 레거시 코퍼스는 조용히 반쯤 실패했다.** 프로젝트 4개가 예외 없이 「불러와졌다」. 그러나 프로젝트마다 컴파일 오류가 127~345개였고, Mono MSBuild를 못 찾은 경고 뒤 .NET SDK로 대신 읽었다. 프로젝트 수와 예외 유무로는 성공을 판정할 수 없다는 §3의 전제가 실제로 확인되었다.
  - **복원 전의 SDK 형식 프로젝트는 오류가 수백 개다.** Modern 코퍼스는 `dotnet restore` 뒤에는 3개 프로젝트 모두 컴파일 오류 0이었다(net48 `Shop.Jobs`는 ReferenceAssemblies 패키지로 해석됨). 복원 전에는 583·165·56개였다.
  - **MSBuild를 지정하는 공개 API가 없다.** 보조 프로세스가 스스로 MSBuild를 고른다. 바깥에서 줄 수 있는 것은 `MSBUILD_EXE_PATH` 환경 변수뿐이고, 어떤 MSBuild를 골랐는지도 알려 주지 않는다.
- 현장 PC는 폐쇄망이다. NuGet 복원을 하지 않는다. 레거시 프로젝트의 `packages/` 폴더는 현장에 이미 있다고 가정한다(지금 Pelly 빌드 검증이 이미 그것으로 빌드한다).
- 보고는 사람이 읽는 요약 한 화면과 JSON 파일 하나다. 현장 모드에서는 둘 다 숫자만 담는다.

## 5. 측정 도구

명령 하나로 동작한다: `s8 load <솔루션 또는 프로젝트 경로> [옵션]`

| 옵션 | 뜻 |
| :--- | :--- |
| `--repeat N` | 같은 대상을 새 프로세스로 N번 불러온다(기본 3). 첫 회가 콜드, 나머지가 웜이다 |
| `--detail` | 로컬 전용. 실패 진단의 메시지·파일 이름·심볼 이름을 출력한다. 현장에서는 쓰지 않는다 |
| `--out <파일>` | JSON 보고 경로 |
| `--check-corpus a3` | 코퍼스 전용. S6 a3 정답과 참조 찾기 결과를 대조한다(§6.4) |

### 5.1 재는 것 (한 번 불러올 때마다)

**불러오기**
- 솔루션의 프로젝트 수와 실제로 불러온 프로젝트 수
- 작업 공간 진단(`WorkspaceDiagnostic`)의 실패 건수와 경고 건수
  - 메시지는 `--detail`일 때만 출력한다.
  - 현장 모드에서는 메시지를 몇 가지 유형으로만 나눠 센다. 유형은 MSBuild를 못 찾음, 프로젝트 형식 미지원, 참조 해석 실패, 기타다.
- 쓰인 MSBuild 종류와 버전은 최선 노력으로만 적는다. 보조 프로세스가 알려 주지 않으므로, 진단 메시지와 `vswhere` 결과에서 추정하고 「추정」이라고 표시한다(Claude 결정).
- 프로젝트 형식별 수: SDK 형식, 레거시 C#, C#이 아닌 프로젝트(`.sqlproj`, VB, C++, 웹 사이트 등)
- 복원되지 않은 SDK 형식 프로젝트 수: `obj/project.assets.json`이 없는 것

**시간** (단계별 초)
- MSBuild 찾기와 등록
- 솔루션 열기
- 모든 프로젝트의 컴파일 정보 만들기(`GetCompilationAsync`)
- 전체
- 최대 메모리(working set)

**타입 정보가 채워졌는가**
- 프로젝트별 컴파일 오류 수(`Compilation.GetDiagnostics()`의 Error). 실제 빌드가 성공하는 솔루션이라면 0이어야 한다.
- 해석하지 못한 메타데이터 참조 수. 참조한 DLL 파일이 없는 경우다.
- **호출 해석률:** 솔루션의 모든 메서드 호출 구문 가운데, 의미 모델이 대상 메서드를 하나로 알아낸 비율이다. 기준은 `GetSymbolInfo(...).Symbol != null`이다. 이 지표에는 정답이 필요 없어서 현장에서도 잴 수 있다. 조용한 반쯤 실패를 잡는 주 지표다.
  - 분모에서 빼는 것: `dynamic` 호출과 `nameof`.
  - 후보가 여럿이라 하나로 못 고른 것(`CandidateSymbols`)은 「해석 실패」로 따로 센다.

**참조 찾기가 도는가** (현장에서도 잼, 숫자만)
- public 메서드를 최대 20개, 시드 고정 난수로 고른다. 각각 `SymbolFinder.FindReferencesAsync`와 `FindImplementationsAsync`를 돌려 다음을 기록한다.
  - 걸린 시간
  - 찾은 위치 수
  - 위치 수가 0인 메서드의 비율. 참고용이며, 정말로 안 쓰이는 메서드일 수도 있다.

### 5.2 배포 형태 확인

같은 도구를 세 가지 형태로 만들어 각각 불러오기를 시도한다. 결과는 「됨 / 안 됨 / 안 되면 오류 유형」이다. 2는 macOS에서 이미 실패를 확인했으므로 Windows에서 같은지 확인하는 용도다. 3에서는 `BuildHost-*` 폴더 파일을 묶음에서 빼야 한다(`ExcludeFromSingleFile`).

1. 폴더 배포: `dotnet publish -r win-x64 --self-contained`
2. 단일 파일 배포: `-p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true`. Pelly와 같은 형태다.
3. 단일 파일 + BuildHost 폴더를 exe 옆에 함께 둔 배포

2가 안 되고 3이 되면, 제품에 넣을 때 배포 묶음 구조를 바꿔야 한다는 뜻이다. 그 경우 반입 zip의 파일 목록이 바뀐다.

### 5.3 MSBuild가 없을 때

Visual Studio가 없는 환경(macOS의 Legacy가 그 예다)에서 돌려도 도구는 죽지 않아야 한다. MSBuild를 못 찾아도 예외가 나지 않고 다른 MSBuild로 조용히 대신 읽기 때문에, 작업 공간 진단을 유형으로 분류해서 알아낸다. 「MSBuild를 찾을 수 없음」 유형이 하나라도 있으면 그렇게 보고하고 종료 코드 3으로 끝낸다. 이것은 제품에서 「의미 분석 실패 → 지금의 구문 방식으로 돌아감」을 판단할 신호가 있는지 보는 확인이다. Windows 러너에서는 `MSBUILD_EXE_PATH`에 없는 경로를 줘서 같은 상황을 만들어 본다.

## 6. 실행 환경과 대상

### 6.1 macOS 개발 PC
- 대상: `eval/corpus/Modern/Modern.sln`, `eval/corpus/Legacy/Legacy.sln`.
- 예상: Modern은 불러와진다. Legacy는 Visual Studio MSBuild가 없어 실패하거나 반쯤 실패할 가능성이 높다. 그 결과도 기록한다. 개발 PC에서는 레거시 의미 분석을 쓸 수 없다는 근거가 되고, 제품에 구문 방식으로 돌아가는 경로가 꼭 필요하다는 뜻이다.

### 6.2 GitHub Windows 러너 (현장 대리)
- `windows-latest`에는 Visual Studio MSBuild가 있다. CI는 이미 `eval/corpus/Legacy/build.ps1`로 레거시 코퍼스를 복원·빌드한다.
- 수동 실행 전용 워크플로(`workflow_dispatch`)를 하나 둔다. 매 push마다 돌리지 않는다. 순서는 다음과 같다.
  1. 레거시 코퍼스를 복원·빌드하고(`build.ps1`), Modern 코퍼스를 `dotnet restore`한다.
  2. 세 가지 배포 형태로 Modern·Legacy를 각각 `--repeat 3`으로 불러온다.
  3. JSON을 아티팩트로 올린다.
- 러너의 Visual Studio 버전은 현장(2025)과 다를 수 있다. 버전 번호를 보고서에 적는다.

### 6.3 현장 PC (사람이 직접)
- 단일 파일 exe 하나(5.2에서 되는 형태)와 실행 안내 한 장을 가지고 들어간다.
- 현장 솔루션마다 `s8 load <솔루션> --repeat 3 --out <파일>`을 돌린다. 화면 요약을 사진이나 메모로 남기거나 JSON을 반출한다. 둘 다 숫자만 담는다.
- 전제: 측정 직전에 그 PC의 Visual Studio에서 솔루션이 빌드되어야 한다. 그래야 레거시는 `packages/`가, SDK 형식은 `obj/project.assets.json`이 채워져 있다. Pelly 빌드 검증(`pelly doctor --project`)이 통과하는 솔루션을 대상으로 한다.
- 빌드가 안 되는 솔루션과 복원되지 않은 SDK 형식 프로젝트의 컴파일 오류는 이 실험의 실패로 세지 않고 따로 적는다(Claude 결정).
- C#이 아닌 프로젝트(`.sqlproj`, VB 등)는 분모에서 빼고 수만 따로 적는다. 그 프로젝트 때문에 생긴 작업 공간 진단도 따로 센다(Claude 결정). 이 규칙은 실행 전에 고정한다.

### 6.4 코퍼스 정답 대조 (`--check-corpus a3`)
- 대상 심볼: `Legacy/Shop.Data/IOrderDao.cs`의 `GetOrder`.
- 기대값은 S6 a3 정답(`spikes/S6-planning/cases/a3-rename-getorder/gold.md`)과 금지 목록(`gold.constraints.json`)에서 읽는다.
  - **구현 찾기:** `OrderDao.GetOrder`와 테스트 프로젝트의 가짜 DAO가 나와야 한다.
  - **참조 찾기:** `OrderService.GetOrder`와 `OrderService.Cancel` 안의 호출이 나와야 한다.
  - **금지:** 다른 인터페이스의 같은 이름 메서드 `IOrderService.GetOrder`(선언)와 그 호출부 `OrderController.Detail`은 나오면 안 된다. 금지 목록 `gold.constraints.json`에 둘 다 있다.
- 결과는 「정답과 같음 / 빠짐 n / 금지 포함 n」이다. 이 대조로 구문 탐색의 이름 혼동이 의미 탐색에서는 사라지는지를 직접 본다.

| 시간 | 프로젝트 4개 이하 솔루션의 콜드 불러오기(열기 + 컴파일 정보) ≤ 15초, 웜 ≤ 10초 |
| 참조 찾기 | 메서드 하나당 ≤ 2초 |
| 코퍼스 대조 | 6.4가 「정답과 같음」 |
| 배포 | 5.2의 2(단일 파일) 또는 3(단일 파일 + BuildHost 폴더) 중 하나가 된다. 사전 확인으로는 3만 가능성이 있다 |
| 실패 처리 | 5.3에서 죽지 않고 「MSBuild를 찾을 수 없음」 유형을 보고한다 |

**결과에 따른 다음 행동**

## 9. 만드는 사람에게 맡기는 것

- 호출 구문 수집 방법(`InvocationExpressionSyntax`만인지, 객체 생성·속성 접근까지 넣는지)은 맡긴다. 다만 무엇을 넣었는지 보고서에 적는다.
- 오류 유형 분류 규칙(메시지 → 유형)은 맡긴다. 규칙을 코드 한 곳에 두고 테스트한다.
- 콜드/웜 측정에서 OS 파일 캐시는 통제하지 않는다. 「첫 회」를 콜드로 부르되, 보고서에 그 한계를 적는다.
