# `pelly spec draft` — 모델 명세 초안 설계

작성 2026-10-27. 상태: 설계, 사람 확인 전. 사람은 기능 진행을 결정했고(2026-10-27, PRD 반영 포함), 설계는 「질문 없이 바로 설계」를 골랐다. 설계 검토(빌더 확인) 반영. 「Claude 결정」으로 표시한 것은 사람이 아직 확인하지 않은 판단이다.

근거: S6 작업 분해 프로브(`docs/s6-planning-probe.md`, 설계 `docs/superpowers/specs/2026-10-21-s6-planning-probe-design.md`, 코드 `spikes/S6-planning/`). V2-1 설계(`2026-10-24-v2-1-apply-design.md`) §9가 「`spec draft`는 V2-1 뒤」로 미뤘다.

## 1. 왜 하는가

`pelly apply`는 사람이 쓴 명세(`changes/<id>.md`)의 작업 줄을 차례로 실행한다. 작업 줄을 쓰려면 바꿀 파일과 멤버를 하나하나 찾아 정확한 경로·이름으로 적어야 한다. 요청이 C#과 SQL에 걸치거나, 같은 파일의 여러 메서드에 걸치면 이 일이 번거롭다.

S6는 모델이 이 초안을 쓸 수 있는지 쟀다(같은 대상 모델, 12사례 × 5회).

| 범주 | 생각 켬(arm B) | 뜻 |
| :--- | ---: | :--- |
| C# + SQL 동시 변경 | 15/15 | 초안 후보 |
| 한 곳만 바꾸면 되는 요청 | 15/15 | 초안 후보(과분해하지 않음) |
| 같은 파일 여러 메서드 | 10/15 | 조건부 |
| 시그니처 변경과 호출부·구현체 전파 | 5/15 | 모델에 맡기지 않음 |

결론은 세 가지였다.
1. 전파(호출부·구현체 찾기)는 모델이 아니라 **의미 기반 코드 탐색**으로 한다. 이것은 이제 있다(V2-1c `spec check --impact`, V2-1d SQL 영향 탐색).
2. 기계 판정을 통과한 초안에도 지시 문구 실패가 있었다. 없는 이름(`CancelTime`)은 **문구 안 식별자 대조**로 잡을 수 있다. 이것도 이제 있다(`spec check`의 이름 검사).
3. 이미 있는 것을 다시 하라는 지시는 코드를 읽어야 보인다 → **사람 승인 없이는 못 쓴다.**

그래서 이 기능은 「모델 초안 + 코드 검사(이름·대상·영향) + 사람 승인」이다. 모델이 쓴 초안은 명세 파일이 될 뿐이고, 실행은 여전히 사람이 `pelly apply`로 한다.

## 2. 목표 / 비목표 / 실패 조건

**목표**
1. `pelly spec draft <id> "<요청>" --scope <경로>…`가 범위 안 코드의 색인(서명만)과 요청으로 모델에게 작업 줄 초안을 받는다.
2. 초안을 기존 파서와 `spec check`(문법·대상 존재·문구 안 이름·영향 탐색)로 검사하고, **영향 탐색이 찾은 빠진 전파 대상은 코드가 작업 줄로 더한다**(같은 그룹, 「영향 탐색으로 추가」 표시).
3. 초안과 검사 결과를 보여 주고 사람이 승인하면 `changes/<id>.md`(`status: draft`)로 쓴다. 거부하면 아무것도 쓰지 않는다.
4. PRD에 반영한다(§12.7의 비목표 문구 조정, 새 절, 로드맵 행, 변경 이력).

**비목표**
- 초안을 바로 실행하기(`--apply` 같은 것). 실행은 늘 `pelly apply`가 따로 한다.
- 수용 기준(AC)·`test:` 줄을 모델이 쓰기. S6가 재지 않았다. 템플릿 자리만 둔다(Claude 결정).
- 범위를 모델이 정하기. 색인 범위는 사람이 `--scope`로 준다(§4.2).
- 모델이 고쳐서 다시 쓰기(대화형 수정 루프). 한 번 부르고 끝. 마음에 안 들면 요청을 고쳐 다시 실행하거나 파일을 손으로 고친다.
- 전파 대상의 지시 문구를 모델로 쓰기. 코드가 정해진 문구로 더한다.
- 벤치마크 확정 수치. 로컬 모델 예비 측정만 하고 「예비」로 표시한다(§8).

**실패 조건**
- 승인 없이 `changes/<id>.md`가 생기거나 바뀐다.
- 지어낸 경로·멤버가 경고 없이 명세에 들어간다.
- 색인을 잘라서 넣는다(S6 규칙: 넘치면 자르지 않고 멈춘다).
- 모델이 문법을 벗어난 줄을 냈는데 코드가 「고쳐서」 받아 주거나, 버린 줄을 사람에게 보이지 않는다.
- 기존 `spec new`·`spec check`·`apply`의 동작이 바뀐다.
- 첫 입력이 4096 토큰을 넘거나, 생각·답을 더한 전체가 `num_ctx` 8192를 넘는다(§4.1).

## 3. 사용 흐름

```text
pelly spec draft cancel-shipped "배송된 주문은 취소할 수 없게 하고, 취소 SP도 배송 완료 주문은 건너뛰게 해줘" \
    --scope src/Orders --scope db/sp/usp_CancelOrder.sql

색인: 파일 7개, 멤버 31개, 1,840 토큰 (예산 4,096)
모델 초안 받는 중… (생각 단계 포함, 수십 초 걸릴 수 있음)

## 작업 (초안)
- [ ] T1 cs  src/Orders/OrderService.cs#CancelAsync 배송 완료 상태면 InvalidOperationException 던지기
- [ ] T2 sql db/sp/usp_CancelOrder.sql WHERE 조건에 ShipStatus 배송 완료 제외 추가

검사: 오류 0, 경고 1
  경고 T2: 요청 문구의 'ShipStatus'가 SQL 파일에 없습니다 (이름 검사)

changes/cancel-shipped.md에 쓸까요? [y/N]
```

- 요청문을 생략하면 대화형에서 입력받는다(비대화형이면 종료 4). `spec new`와 같은 ID 규칙.
- 이미 `changes/<id>.md`가 있으면 종료 4(`--force`면 덮어씀. 승인 질문에 「덮어씁니다」를 밝힌다. `--yes`면 묻지 않는다).
- `--dry-run`: 초안과 검사 결과만 보여 주고 쓰지 않는다(종료 0).
- `--yes`: 승인 질문 없이 쓴다(비대화형에서 필요). 쓴 뒤에도 `pelly apply`가 작업마다 승인을 받는다는 점은 그대로다.
- 모델·서버 옵션은 `pelly cs`와 같은 공통 옵션(`--config`, `--model`, `--endpoint`)을 받는다.

## 4. 동작 (Claude 결정, S6에서 잰 조건을 바꾸지 않는 것이 원칙)

### 4.1 모델 호출 — S6 arm B 그대로

- 시스템 프롬프트는 S6의 고정 프롬프트(`spikes/S6-planning/S6Planning/PlanPrompt.cs`)를 **문구 그대로** 옮긴다. 영어, 작업 줄 문법, 규칙 5개, 무관한 도메인(도서 대출) 예시 하나. 잰 것과 다른 프롬프트로 바꾸면 S6 수치가 근거가 되지 않는다.
- 사용자 메시지는 S6와 같은 모양: `Index:\n<색인>\nRequest:\n<요청>`.
- 생각 단계 켬, 상한 2048 토큰, 그 뒤 답 생성(S6 arm B의 2단계 호출). 값은 S6 실행기(`spikes/S6-planning/S6Planning/Runner.cs`)의 상수 그대로다(설계 검토 반영): 생각 단계 temperature 0.6 / top_p 0.95 / top_k 20 / repeat_penalty 1.0 / seed 0, `num_predict` 2048, stop `</think>`; 답 단계 0.1 / 0.9 / 20 / 1.05 / 0, `num_predict` 1024, stop 턴 끝 토큰; `num_ctx` 8192, `keep_alive` "10m". 설정 키는 만들지 않는다(YAGNI).
- 생각이 잘려도 S6 실행기처럼 **원문 그대로** 이어 붙여 답 단계에 넘긴다(S6는 60회 중 48회가 잘렸고 그 상태로 잰 수치다). 편집 경로(`GenerateEditAsync`)의 다듬기(TrimEnd, 줄 단위 자르기)를 쓰지 않는다. 호출은 Core의 기존 스트림 클라이언트로 한다(백엔드를 넓히지 않는다).
- 예산: 첫 입력(시스템 + 색인 + 요청) ≤ 4096 토큰은 편집 경로와 같다. 계획 호출만 생각 2048 + 답 1024를 더해 전체가 `num_ctx` 8192 안이다(최대 4096 + 2048 + 1024 = 7168). 편집용 요청문 상한(`budget.request` 200)은 적용하지 않는다 — 요청은 첫 입력 4096 안에서만 센다. 이 두 예외를 PRD §12.1의 「토큰 예산은 바꾸지 않습니다」 옆에 적는다(§6).
- 요청에 모델 제어 토큰 문자열이 있으면 서버를 부르기 전에 종료 4(기존 입력 제한과 같다).
- 서버 연결·대기·재연결은 기존 `OllamaBackend` 경로를 쓴다.

### 4.2 색인 범위

- `--scope`는 하나 이상 필수다. 파일, 폴더, `.csproj` 중 무엇이든 되고, 폴더는 그 아래 `.cs`·`.sql`을 모두 넣는다(`bin`·`obj`·`.pelly` 등 기존 탐색이 빼는 폴더는 뺀다). 모두 작업 공간 안이어야 한다.
- 색인은 S6 `CorpusIndex`와 같은 형식이다: 파일마다 경로(작업 공간 기준 `/` 구분), 형식 이름, 멤버 시그니처. 본문은 넣지 않는다. SQL은 객체 이름과 파라미터 목록. S6에서 옮기는 것은 `Render`와 색인 빌더뿐이다(존재 확인은 `SpecChecker`가 맡는다). 생성자가 색인에 없는 S6의 한계는 바이트를 맞추기 위해 그대로 둔다(알려진 한계로 문서에 적는다). S6와 다르게 하는 것 둘(설계 검토 반영): 파싱되지 않는 `.sql`은 색인에서 빼고 경고로 알린다(명령이 죽지 않게), SQL 파서는 설정 `sql.compatLevel`을 따른다.
- 입력 전체(시스템 + 색인 + 요청)가 4096 토큰을 넘으면 **모델을 부르지 않고** 종료 4. 토큰이 큰 파일부터 몇 개를 알려 주고 「`--scope`를 좁히십시오」라고 안내한다. 잘라서 넣지 않는다.
- 범위를 사람이 주는 이유: 실제 코드베이스는 4096 토큰에 들어가지 않고, 모델에게 범위를 고르게 하면 S6가 재지 않은 일을 시키게 된다. 범위 밖 전파는 §4.4의 영향 탐색이 찾는다.

### 4.3 초안 받기와 검사

1. 응답의 줄을 제품 파서(`ChangeSpecParser`)의 작업 줄 문법으로 받는다. 맞지 않는 줄은 버리고, **버린 줄을 원문 그대로** 「형식에 맞지 않아 버린 줄」로 보여 준다(실행 기록에도 남는다). 고쳐서 받지 않는다. S6는 한 줄이라도 틀리면 초안 전체를 실패로 셌다 — 지어낸 대상이 깨진 줄 뒤에 숨는 것을 막기 위해서였다. 여기서는 버린 줄을 사람이 원문으로 보므로 숨지 않는다(Claude 결정, 설계 검토 반영). 받는 문법은 제품 파서 기준이라 S6 채점기보다 조금 관대하다(예비 측정에서 이 차이를 적는다).
2. 받은 줄로 명세 문서를 만든다: 앞머리(`id`, `status: draft`), 제목(요청 첫 줄을 60자에서 자름), `## 목표`(요청 원문), `## 수용 기준`(템플릿 자리 `- AC1: …`), `## 작업`(받은 줄).
3. 이 문서를 기존 `SpecChecker`로 검사한다. 검사기는 파일 경로가 필요하고 그 경로로 작업 공간을 정하므로, 초안을 작업 공간의 `.pelly/drafts/<id>.md`에 써서 검사하고 끝나면 지운다(`changes/`는 승인 전까지 건드리지 않는다, 설계 검토 반영). 문법, 대상 파일·멤버 존재, 문구 안 이름, 작업 수 상한(20).
4. 영향 탐색(§4.4)을 돌린다.
5. 오류가 있으면 영향 탐색은 돌지 않는다(기존 검사기가 오류가 있으면 영향 탐색을 건너뛴다). 이때 「검사 오류가 있어 영향 탐색을 하지 않았습니다」를 보인다(설계 검토 반영, Core는 바꾸지 않는다).
6. 오류가 있어도 승인 질문은 한다. 다만 오류가 있으면 질문 전에 「오류가 있는 명세는 `pelly apply`가 실행하지 않습니다. 쓴 뒤 고치십시오」를 보이고, 쓴 파일의 `## 작업` 위에 검사 결과를 HTML 주석으로 남긴다. 기본 답은 N.

### 4.4 전파는 코드로 (설계 검토 반영)

- **출발점은 그룹 작업뿐이다.** `pelly apply`의 기본 영향 탐색과 같다(`ImpactCheck.Seeds`, 전체 cs 작업 아님). 프롬프트 규칙 3이 「시그니처를 바꾸면 같은 그룹에 넣어라」라고 하므로, 시그니처를 바꾸는 초안은 그룹을 단다. 그룹이 없는 동작 변경에서는 탐색하지 않는다 — 그래야 S6에서 15/15였던 「한 곳 변경」이 과분해되지 않는다.
- 탐색 결과의 구조화된 대상(`SpecCheckResult.Impact.Targets`)을 쓴다. 경고 문자열을 파싱하지 않는다.
- **작업 줄로 더하는 대상은 C# 의미 기반 결과 중 아래를 모두 만족하는 것뿐이다.** 하나라도 어긋나면 더하지 않고 경고(기존 「영향 대상이 명세에 없습니다」)만 남긴다.
  - 멤버 안의 대상이다(「멤버 밖」·형식 선언 줄·생성자 안 호출처럼 멤버 이름을 정할 수 없는 대상은 빼다).
  - 그 파일에 그 이름의 멤버가 하나뿐이다(둘 이상이면 `SymbolAmbiguous`가 나므로 빼다).
  - 출발 작업들이 모두 한 그룹에 속한다(여러 그룹에서 나온 대상은 출처 그룹을 정할 수 없으므로 빼다).
- 더한 줄: `- [ ] T<새 번호> cs <경로>#<멤버> T<출처 번호>의 변경에 맞춰 이 코드를 고친다 (영향 탐색으로 추가) [G<k>]`. 「(영향 탐색으로 추가)」가 요청문 안에 들어가 사람도 구분하고, 실행 때 모델도 출처를 본다. 줄 끝 HTML 주석은 쓰지 않는다 — 지금 파서는 줄 끝 주석으로 `<!-- run|failed: … -->`만 받아서 다른 주석은 요청문과 그룹 표시를 삼킨다(설계 검토에서 확인). 새 번호는 기존 최대 번호 다음부터 매긴다.
- 위치: 그 그룹의 마지막 작업 바로 뒤(그룹은 연속이어야 한다).
- **SQL 대상과 이름 기준 대상은 더하지 않는다.** SQL 모듈(`SqlObject`)은 로컬 파일 경로가 없을 수 있고, C# 문자열에서 찾은 대상(「이름 호출(문자열)」)과 의미 분석 실패로 떨어진 「이름 기준(부정확)」 결과는 S6 a3처럼 엉뚱한 같은 이름을 끌어올 수 있다. 경고(SQL은 기존의 `pelly sql pull` 안내 포함)만 남긴다.
- SQL 영향 탐색의 DB 선택은 `spec check --impact`와 같다(운영 설정이 있으면 운영 읽기 전용, 없으면 개발; V2-1d 사람 결정). 이 탐색은 `.pelly/impact/<id>-sql.json`을 쓴다 — `.pelly`는 작업 폴더이고, 같은 id의 명세가 이미 있으면 §3에서 멈추므로 다른 명세의 기록을 덮지 않는다(`--force` 때는 덮는다).
- 더한 뒤 검사(정적)를 한 번 더 돌려 결과를 보인다. 영향 탐색은 다시 돌리지 않는다.

### 4.5 쓰기와 기록

- 승인하면 `changes/<id>.md`에 UTF-8(BOM 없음), `\n`으로 쓴다(`spec new`와 같다).
- 실행 기록: `.pelly/runs/<run-id>/`에 프롬프트, 모델 응답 원문, 버린 줄, 검사 결과, 더한 영향 줄을 남긴다(기존 실행 기록과 같은 마스킹). 나중에 「초안을 얼마나 고쳐 썼는가」를 재려면 원문이 필요하다.

## 7. 검증

1. **색인**: 작은 코퍼스 폴더로 만든 색인이 S6 `CorpusIndex.Render`와 같은 바이트인지(옮김 검증; 스파이크로 한 번 만든 기준 파일과 비교 — 테스트 프로젝트가 스파이크를 참조하지 않는다). 파싱되지 않는 `.sql`은 빠지고 경고. 경로 구분자 `/`, 범위 밖 경로 거부, 폴더 제외 규칙.
2. **예산**: 큰 범위 → 모델 호출 0회, 종료 4, 큰 파일 목록 안내.
3. **줄 받기**: 문법 밖 줄 버림·개수 보고, 예시 이름(`LoanService` 등)이 나오면 그대로 받되 대상 없음 오류로 걸림.
4. **검사 연결**: 지어낸 멤버 → 오류, 없는 이름 → 경고, 오류가 있으면 쓴 파일에 주석.
5. **영향 줄**: 그룹 작업으로 시그니처를 바꾸는 초안(가짜 백엔드)에 대해 의미 탐색이 찾은 호출부가 그 그룹 끝에 더해짐(요청문에 「(영향 탐색으로 추가)」), 그룹 없는 초안은 탐색 안 함, 멤버 밖·이름 중복·여러 그룹 출처·SQL·이름 기준 대상은 경고만, 검사 오류가 있으면 탐색 안 함과 안내. 더한 줄이 파서에서 그룹을 잃지 않음(요청문에 그룹 표시가 섞이지 않음). 기존 영향 탐색 테스트 픽스처(`tests/fixtures/impact/…`)를 쓴다.
6. **승인**: 거부 → 파일 없음(종료 2), 승인 → 파일 내용, `--dry-run` → 파일 없음, 이미 있음 → 종료 4, `--force` 확인.
7. **문서 왕복**: 쓴 파일을 `pelly spec check`가 같은 결과로 읽는다.
8. **기존 게이트**: `dotnet build -warnaserror` 종료 0, `dotnet test` 실패 0.
