# S6 작업 분해 프로브 — 설계

- 작성일: 2026-10-21
- 상태: 설계 (실행 전)
- 관련: PRD §12.1 「작업을 쪼개고 계획하는 일은 사람이 합니다」, §12.3 V2-1 명세 형식, §12.7 「v2에서도 하지 않을 것」 1항

## 1. 왜 재는가

PRD는 「활성 3B 모델은 작업 분해가 약하다」를 **전제**로 두고 모델의 계획 기능을 v2 비목표로 정했다. 이 전제는 측정한 적이 없다. 측정된 것은 인접한 약점뿐이다.

- 지시 준수: 모순 요청 우회 35~45%
- 긴 추론: think 512 안에 끝난 비율 0/30

이 실험은 그 전제를 한 번 재서 둘 중 하나로 닫는다.

- 전제가 맞다 → 비목표에 측정 근거를 붙인다.
- 전제가 틀렸다 → 「모델이 명세 초안을 쓰고 사람이 승인한다」로 PRD를 바꿀 근거가 생긴다. 바꿀지는 사람이 결정한다.

**묻는 질문 하나:** 다중 작업 변경 요청과 저장소 색인을 주면, qwen3.6:35b(현장 파일)가 V2-1 작업 줄 문법으로 **사람이 쓴 정답 명세와 같은 대상·순서·그룹**을 내는가.

## 2. 목표 / 비목표 / 실패 조건

**목표**
- 사례 단위 「초안으로 쓸 만함」 비율을 반복 측정한다.
- 대상 누락, 없는 대상 지어내기, 순서 위반, 그룹 누락을 따로 센다.
- 시그니처 변경 사례에서는 모델과 결정론적 코드(Roslyn 호출부 탐색)를 같은 채점기로 비교한다.

**비목표**
- 분해한 명세를 실행하지 않는다. `pelly apply`(V2-1)는 아직 없다.
- 작업 줄의 「요청 문구」 품질은 기계로 채점하지 않는다. 사람이 표본만 읽는다(§6.3).
- 제품 코드(src/)는 바꾸지 않는다. 스파이크 디렉터리에만 둔다.
- 프롬프트 튜닝 반복은 하지 않는다. 프롬프트는 한 벌로 고정하고, 설계 오류가 아니면 고치지 않는다.

**실패 조건** (기술적으로 돌아가도 실험이 무효인 경우)
- 정답을 모델 출력을 본 뒤에 쓰거나 고쳤다. 오라클 순환이 된다.
- 판정 기준을 결과를 본 뒤에 정했다.
- 프롬프트 예시를 그대로 베낀 출력이 점수를 받았다. 예시 복사율을 따로 센다.
- 측정 모델이 현장 파일이 아니었다. digest `a7eb95c53bcf`를 시작 시 확인한다.

## 3. 제약

- 모델: `qwen3.6:35b`. GGUF Q4_K_M, manifest digest `a7eb95c53bcf…`이며 실행 시작 시 `/api/show`로 확인한다. nvfp4로 잰 결과는 무효다.
- 예산: num_ctx 8192, 입력 4096 이하. 시스템 프롬프트, 요청, 색인을 합쳐 이 안에 든다. 토큰은 제품과 같은 토크나이저로 센다.
- 호출: Ollama `/api/generate` raw 모드, 제품과 같은 채팅 템플릿을 쓴다.
- 실행 형태: S1~S5와 같은 .NET 10 단일 파일 스파이크 `spikes/S6-planning/`. 환경 변수는 `PELLY_SPIKE_OLLAMA`, `PELLY_SPIKE_MODEL`.
- 코퍼스: `eval/corpus/`(Modern, Legacy, Sql)만 쓴다. 현장 코드는 쓰지 않는다.

## 4. 사례 (12건, 4범주 × 3)

| 범주 | 무엇을 보나 | 정답 작업 수 | 후보 (정답 작성 때 코드로 확정) |
| :--- | :--- | :--- | :--- |
| A. 시그니처 변경 + 호출부 | 호출부를 빠짐없이 찾고 그룹으로 묶는가 | 3~5 | Modern `IOrderService.CancelAsync`에 파라미터 추가 / Modern `IOrderRepository.AddRefundAsync`에 사유 추가 / Legacy `IOrderDao.UpdateStatus` 변경 |
| B. C#과 SQL 교차 | cs와 sql을 가르고 순서를 지키는가 | 2~4 | `usp_CancelOrder` 조건 + Legacy 취소 / `usp_SearchOrders` 파라미터 + 호출부 / `usp_BuildSettlement` + `DailySettlementJob` |
| C. 같은 계층 여러 멤버 | 멤버 단위로 쪼개는가(v1 단위 유지) | 2~4 | Modern `OrderService` 공개 메서드 전부에 `orderId` 검사 / Legacy `OrderController` 액션 로그 / Modern 리포지토리 쿼리 시간 제한 |
| D. 단일 작업 대조군 | 쪼갤 필요 없는 일을 과하게 쪼개지 않는가 | 1 | 기존 벤치마크 과제 셋 (예: cs-modern-001) |

- 요청 문구는 현업이 쓰듯 한 문장으로 쓴다. 파일명과 심볼은 넣지 않는다.
- 후보가 코퍼스 코드로 성립하지 않으면 같은 범주의 다른 사례로 바꾼다. 바꾼 사유를 정답 파일에 남긴다.

## 5. 입력과 출력

**색인 (결정론적 생성)**
- 사례가 속한 솔루션의 파일마다 경로, 형식 이름, 멤버 시그니처를 적는다. 본문은 넣지 않는다.
- SQL은 객체 이름과 파라미터 목록을 적는다.
- 색인 생성기는 Roslyn과 ScriptDom을 쓰고, 출력은 파일로 저장해 사례마다 같은 바이트가 들어가게 한다.
- 예산을 넘으면 사례가 속한 프로젝트로 좁힌다. 좁혀도 넘으면 사례를 바꾼다. 잘라서 넣지 않는다.

**프롬프트**
- 영어 시스템 프롬프트에 작업 줄 문법(§12.3)과 예시 하나를 넣는다.
- 예시는 코퍼스와 무관한 도메인(도서 대출)으로 만든다. 예시의 파일명이나 심볼이 출력에 나오면 「예시 복사」로 센다.

**출력 문법** (V2-1과 같다)

```
- [ ] T<n> <cs|sql> <파일>[#심볼] <요청> [G<k>]
```

이 문법을 벗어난 줄은 파싱 실패로 센다. 고쳐서 받아 주지 않는다.

## 6. 측정

### 6.1 조건 (arm)

| arm | 설명 | 반복 |
| :--- | :--- | :--- |
| A | 모델, think 없음. 제품 CODE 단계 샘플링 값 | 사례당 5회 |
| B | 모델, think 상한 2048 (입력 4096 + 출력 여유 안) | 사례당 5회 |
| C | 코드: Roslyn으로 대상 멤버의 구현체·호출부·테스트를 찾고 규칙으로 작업 줄 생성 | 범주 A만, 1회 (결정론적) |

호출 수는 12 × 2 × 5 = 120회다. 예상 시간은 1~2시간이며, 대부분 arm B에서 쓴다.

### 6.2 기계 채점 (정답 대비, 반복마다)

| 지표 | 정의 |
| :--- | :--- |
| 파싱률 | 문법을 지킨 출력의 비율 |
| 대상 재현율 / 정밀도 | 정답의 (파일, 심볼) 집합 대비. 심볼은 이름 정확 일치 |
| **지어낸 대상** | 코퍼스에 없는 파일·심볼 수. 하나라도 있으면 그 반복은 「쓸 만함」 불가 |
| 순서 위반 | 정답에 적은 선후 제약(예: 인터페이스 → 구현 → 호출부) 위반 수 |
| 그룹 정확도 | 범주 A에서 시그니처 변경과 호출부가 한 그룹인가 |
| 종류 정확도 | cs / sql 구분 |
| 과분해 | 범주 D에서 작업이 2개 이상인 비율 |
| 예시 복사 | 예시의 이름이 출력에 나온 반복 수 |

「초안으로 쓸 만함」은 한 반복이 다음을 모두 만족할 때다.
- 재현율 100%
- 지어낸 대상 0
- 순서 위반 0
- (범주 A) 그룹 정확
- (범주 D) 작업 1개

정밀도는 따지지 않는다. 사람이 승인하면서 지우기는 쉽기 때문이다.

### 6.3 사람 확인 (보조)

arm A와 B에서 「쓸 만함」 반복을 각각 10개 무작위로 뽑는다. 사람이 각 작업 줄의 요청 문구가 v1 단일 작업으로 실행 가능한지 예/아니오로 표시한다. 기계 판정을 뒤집지 않고 함께 보고한다.

## 7. 판정 기준 (실행 전에 고정)

사례 단위 쓸 만함 비율은 12사례 × 5반복 = 60반복 중 몇 반복인지로 센다. 더 나은 arm을 기준으로 판정한다.

| 결과 | 판정 | 다음 행동 |
| :--- | :--- | :--- |
| ≥ 80% 그리고 모든 범주 ≥ 60% 그리고 지어낸 대상 0 | 전제 기각 | PRD 개정안 「`pelly spec draft`: 모델 초안 + `spec check` + 사람 승인」 작성. 채택은 사람이 결정 |
| 50~80% | 부분 | 잘 된 범주만 초안 후보로 기록. PRD는 그대로 둔다 |
| < 50% 또는 지어낸 대상이 반복의 10% 초과 | 전제 확인 | §12.7 1항에 측정 근거(이 문서 링크) 추가 |

별도 판정: 범주 A에서 arm C의 재현율이 모델 이상이면, 호출부 찾기는 모델이 아니라 코드(`pelly spec check`의 확장)로 한다고 기록한다. 이 판정은 위 표의 결과와 무관하게 내린다.

## 8. 정답 작성 절차 (오라클 출처)

1. 정답 명세 `spikes/S6-planning/cases/<id>/gold.md`를 V2-1 형식으로 쓰고, 선후 제약을 `gold.constraints.json`에 적는다.
2. 정답은 코퍼스 코드를 직접 열어 확인해서 쓴다. 범주 A의 호출부는 grep과 빌드 에러로 확인하고, arm C의 출력은 보지 않는다.
3. **사람이 12건을 검토하고 승인한 뒤** 커밋한다. 이 커밋 해시를 결과 보고서에 적는다. 이 커밋 이후 정답은 바꾸지 않는다.
4. 실행 뒤 정답 오류가 발견되면 정답을 고치지 않는다. 그 사례를 보고서에 「정답 결함」으로 표시하고 분모에서 뺀 수치를 함께 낸다.

## 9. 산출물

- `spikes/S6-planning/`: 다음을 둔다.
  - `plan.cs`: 실행기. 색인 생성, 호출, 원문 저장을 맡는다.
  - `score.cs`: 채점기.
  - `callers.cs`: arm C.
  - `cases/`
  - `raw/`: 원문 응답. 재채점에 쓴다.
  - `results.csv`
- `docs/s6-planning-probe.md`: 결과 보고서. 모델 digest, 정답 커밋, 판정, 범주별 표, 실패 원문 예시를 담는다.
- 채점기는 원문을 다시 읽어 결과를 재현할 수 있어야 한다. 채점 규칙을 고치면 모델을 다시 부르지 않고 재채점한다.

## 10. 작성자 판단 (검토 바람)

사용자가 질문 없이 진행하라고 해서 다음은 작성자가 정했다.

1. 사례 수를 12(4범주 × 3), 반복을 5로 잡았다. 통계적 결론이 아니라 방향을 보기 위한 크기다.
2. 「쓸 만함」에서 정밀도를 뺐다. 남는 작업은 사람이 지우면 된다는 가정이다.
3. arm B의 think 상한을 2048로 잡았다. 제품 THINK 512로는 끝나지 않는다는 측정(S3) 때문이다. 이 값으로 좋은 결과가 나와도, 계획 단계에 별도 예산을 두는 것은 PRD 결정 사항이다.
4. 정답 초안은 작업자(Claude)가 써도 되지만, **사람 승인이 실행의 선결 조건**이다. 승인 없이 실행하면 결과는 무효다.
5. 판정 기준선 80% / 50%는 PRD v2 KPI 「명세 완료율 ≥ 70%」보다 엄격하게 잡았다. 초안 단계의 오류는 실행 단계로 누적되기 때문이다.
