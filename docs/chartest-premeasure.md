# pelly test 예비 측정 (Modern 사례)

> **예비 — 사람 승인 전 수치.** 에이전트가 개발 맥(macOS)의 로컬 Ollama로 한 번 잰 값이다. 사례 4건 × 3회, 표본이 작아 비율보다 **실패 원인**을 읽는 자료다. 레거시(net48) 사례는 이 맥에서 못 돌려 Windows 현장 측정으로 둔다(`deploy/field-results.md` 13절).

설계: [docs/superpowers/specs/2026-10-29-pelly-test-characterization-design.md](superpowers/specs/2026-10-29-pelly-test-characterization-design.md) §7 · 사례와 실행기: `eval/benchmark/chartest/`

## 1. 요약

- 종료 0(남김)은 **3/12 (25%)**. 성공은 모두 `OrderService.SearchAsync` 한 사례이고, 컨트롤러 3개 사례는 9회 모두 재시도 4번을 소진하고 종료 1이다.
- 성공한 3회는 모두 3개 테스트가 현재 코드 통과, 재실행 일치, **변이 검출 3/3**이었다. 판정 7(변이)까지 간 실행은 이 3회뿐이고 모두 통과했다.
- 실패 원인은 거의 하나다. **새 테스트 파일에서 모델이 `using`을 빠뜨려 빌드가 실패한다**(CS0246). 전체 시도 중 빌드 실패 31회(실패 판정 38회의 82%).
- 운영 코드가 바뀌었다는 신호는 없었다(전 실행 종료 코드 0 또는 1, 종료 4 없음). 다만 이번 실행기는 대상 파일 해시를 따로 재지 않았다. 바이트 보존은 자체 테스트(`CharTest*`)가 본다.

## 5. 관찰 (시도 프롬프트·출력을 읽고)

기록 원본은 `/private/tmp/claude-501/chartest-premeasure/`(리포지토리 밖, 사례별 `console.log`, `summary.json`, `run/attempt-*/prompt.txt`·`output.txt`·`feedback.txt`).

1. **빠진 `using`이 실패의 대부분이다.** 기존 테스트 클래스가 있는 m1은 프롬프트에 「test usings」(그 파일의 using 목록)가 있어 모델이 그대로 쓴다. 새 파일을 만드는 m2~m4에는 그 구역이 없고 모델이 쓴 `### USINGS`만 새 파일에 들어간다. 모델은 `Task`, `IReadOnlyList<>`, `Order`, `IOrderService`(각각 `System.Threading.Tasks`, `System.Collections.Generic`, `Shop.Api.Models`, `Shop.Api.Services`)를 빠뜨리거나, 피드백을 받고 고치면 다른 using을 빼먹었다. 프롬프트의 의존성 서명에는 타입 이름만 있고 네임스페이스는 없다. 피드백은 CS0246을 보이지만 모델은 한 번에 하나씩만 고쳤고 4번 안에 다 맞추지 못했다.
2. **모델이 테스트 대역(fake)을 직접 쓰다 인터페이스를 다 구현하지 못한다.** 컨트롤러는 `IOrderService`를 받아 모델이 `FakeOrderService`를 중첩 클래스로 쓰는데, m3에서 `CS0535`(멤버 구현 누락), `CS0738`(반환 형식 불일치)이 나왔다. 서명 목록이 있어도 `Task`/`Task<T>` 반환을 틀린다.
3. **async 대상을 동기로 부른다.** m2의 첫 시도는 `Get`(`Task<IActionResult>`)을 `sut.Get(1)`로 부르고 `result.Result`로 단언했다. 이런 경우는 빌드가 되더라도 `await` 없이 `Task`를 단언하게 된다.
4. **환경 의존 금지(판정 3)가 2번 걸렸다.** 모델이 `Order`의 `OrderedAt = DateTime.UtcNow`로 채웠다(m2). 거부 사유가 이름을 짚어 주지만 그 시도는 어차피 다음 시도에서 빌드로 막혔다.
5. **「단언 없음」(m4, 시도 3회)과 없는 패키지.** 모델이 `Moq`로 `Mock<IOrderService>`를 만들고 `Verify(...)`로만 확인하며 반환값은 `_ =`로 버렸다. pelly의 단언 검사는 `Assert.*`를 찾으므로 「단언 없음」으로 거부된다. 같은 지적을 받고도 한 번 더 나온 실행이 있다(m4 1회). `Moq`는 테스트 프로젝트에 없어 CS0246도 났다(m4 마지막 시도). 프롬프트는 「대역을 직접 만들라」고 하지만 모델이 익숙한 모의 객체 라이브러리로 돌아간다.
6. **형태 거부(m3 1회, m4 1회)는 마지막 시도에서 나왔다.** m3는 테스트 메서드가 4개(최대 3개), m4는 `### USINGS` 구역에 using 줄 뒤 `//` 설명이 붙어 「using 줄이 아닌 내용」으로 거부됐다. 모델이 네임스페이스를 모른다고 스스로 적은 설명이다(관찰 1을 뒷받침).
7. **성공 사례(m1)는 첫 시도 빌드 실패 2회가 모두 같다.** 기존 `OrderServiceTests.FakeOrderRepository`(생성자에 `Order`가 필요한 private 중첩 클래스)를 인자 없이 만들어 `CS7036`이 났고, 다음 시도에서 고쳤다. 남은 테스트는 3개씩, 변이를 모두 잡았다(대상 본문을 예외로 바꾸면 3개 모두 실패).
8. **시간.** 시도 1번 약 5~11초(생성 5초 내외, 빌드·테스트 수 초). 실패 사례는 4번을 모두 쓰므로 42~61초로 길다.

## 6. 의미와 한계

- 표본이 작다(사례 4건 × 3회). 25%는 「성공률 추정」이 아니라 컨트롤러 사례의 새 파일 경로가 거의 안 된다는 신호로 읽는다.
- 사례 선택이 어렵다. Modern에서 테스트 프로젝트가 참조하는 프로젝트는 `Shop.Api`뿐이고, 거기서 테스트가 없는 public 메서드는 `SearchAsync`와 컨트롤러 3개다(`Shop.Jobs`는 테스트 프로젝트가 참조하지 않아 종료 3). 레거시 4건(`l1`~`l4`)은 Windows 측정이다.
- 변이 검출 판정 7은 3회분만 검증됐다. 컨트롤러 사례가 판정 4(빌드)를 넘지 못해 판정 5~7의 분포는 이번에 모르겠다.
- 위 관찰 1이 사실이면 새 테스트 파일 경로의 성공률은 이 수치보다 훨씬 올라갈 수 있다. 이 작업에서는 제품을 고치지 않았다. 후보 개선은 작업 보고서에 따로 적었다.
- 현장 모델 ID와 로컬 ID를 확인하지 못했고, Windows·net48은 측정하지 않았다.
