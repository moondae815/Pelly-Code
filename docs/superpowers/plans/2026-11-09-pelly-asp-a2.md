# `pelly asp` A2 (SP와 ASP를 한 명세로) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 명세에 `asp` 작업 종류를 더해 SP 수정과 그 SP를 부르는 ASP 수정을 한 명세(그룹 포함)로 실행하고, SP를 부르는 ASP 페이지를 영향 탐색으로 찾는다.

**Architecture:**
- 파서와 검사기에 `TaskKind.Asp`와 줄 범위 대상(`#L시작-끝`)을 더한다.
- 그룹은 「함께 되돌림 + (cs 작업에만) C# 빌드 검증」으로 넓힌다.
- W2 사이트 색인에 SP 호출 항목을 담아, 파일만으로 SP → ASP 영향을 찾는다. 이 찾기는 SQL DB 탐색과 따로 돈다.
- 앞선 sql 작업이 바꾼 SP의 「파일 기준 서명」을 asp 작업에 넘겨, 모델 입력과 SP 검사가 배포 전 상태를 기준으로 한다.

**Tech Stack:** .NET 10, C#, ScriptDom(이미 있음), xUnit, System.IO.Abstractions(MockFileSystem).

**Spec:** `docs/superpowers/specs/2026-11-09-pelly-asp-a2-design.md`. 이어 받는 설계는 `2026-11-04-pelly-asp-design.md`·`2026-10-24-v2-1-apply-design.md`·`2026-10-26-v2-1d-sql-impact-design.md`다.

  - push하지 않는다. 서브에이전트를 띄우지 않는다. `.superpowers/` 아래를 `git add -f`하지 않는다.

- **경로:** 이 머신은 macOS다. 경로 테스트는 Windows에서도 맞게 쓴다.
  - MockFileSystem 루트는 `OperatingSystem.IsWindows() ? @"C:\w" : "/w"` 식으로 둔다.
  - 메시지 단언은 파일 이름만 확인한다.

- **명세 문법:** 종류 낱말은 `asp`, 대상은 `#이름`(Function·Sub, `Class.이름`) 또는 `#L시작-끝`(L 대문자, 1부터, 시작 ≤ 끝)이다(설계 §3.1).
- **새 spec check 문제 코드:** `AspTargetRequired`, `LinesOutOfFile`, `LinesNotSupported`, `AspLinesAfterEdit`. 재사용하는 코드는 `KindMismatch`, `SymbolNotFound`, `SymbolAmbiguous`, `AspEncoding`이다(설계 §3.3).
- **고정 문구 (설계 그대로):**
  - `AspLinesAfterEdit` 문구: 「{뒤 작업}의 줄 범위는 같은 파일을 먼저 고치는 {앞 작업} 뒤에 어긋날 수 있습니다. 프로시저 대상(#이름)으로 쓰거나 작업을 하나로 합치십시오」
  - 그룹 없는 sql+asp 실패 경고: 「{sql 작업}(sql)은 적용됐고 {asp 작업}(asp)는 실패했습니다. SP와 페이지가 어긋나 있을 수 있습니다. 함께 되돌리려면 [G1]로 묶으십시오」(`[G1]`은 다음 빈 그룹 번호)
  - ASP 영향 경고: 「작업 {ids}의 영향 대상이 명세에 없습니다: {path}:{line} ({SP} 호출, 인수 {n}개)」(인수를 모르면 「인수 모름」). include면 끝에 「(include: 그 파일을 쓰는 페이지 {k}곳)」.
  - SP 하나당 ASP 경고는 최대 10개, 넘으면 「외 {n}곳」 한 줄.
  - 서명 해석 실패 경고: 「{작업}의 SP 파일을 해석하지 못해 개발 DB의 매개변수를 씁니다」
  - apply 뒤 경고: 「{SP}의 매개변수가 바뀌었습니다({변경 요약}). 고치지 않은 호출: {path}:{line} 외 {n}곳」. 기본값 있는 매개변수만 끝에 더해졌으면 「 — 기존 호출은 그대로 동작할 수 있음」을 덧붙인다.
- **A1·W1·W2 단독 실행은 바뀌지 않는다.** `pelly asp`·`pelly js`·`pelly css`에 명세 정보가 없으면 지금 동작 그대로다. 기존 테스트를 고쳐 통과시키지 않는다. 다만 `SqlInGroup`을 기대하던 테스트는 설계상 바뀐 동작이므로 고친다.
- 사내 값·로컬 임시 경로(계정 번호가 든 경로)를 커밋 파일에 쓰지 않는다.

## Review Focus

1. **`#객체` 없이 쓴 sql 작업(파일에 SP 배치가 하나).** 영향 탐색 씨앗 SP 이름은 그 배치에서 와야 한다. → Task 5 테스트 `Seed_from_single_batch_sql_without_symbol_finds_asp_callers`.
2. **이름 표기 차이:** `[dbo].[usp_X]`(SQL) ↔ `"usp_X"`·`"dbo.usp_X"`·`{call usp_x(?)}`(ASP). 같은 SP로 맞아야 한다. → Task 5 테스트 `Bracketed_and_schema_less_names_match`.
3. **그룹에서 asp가 실패하면 앞선 sql 파일이 원래 바이트로 돌아와야 한다**(CP949·CRLF SQL 파일 포함). → Task 3 테스트 `Group_sql_then_failing_asp_restores_sql_bytes`.
4. **asp 실패 뒤 `apply --resume`.** 이미 완료된 sql 작업의 SP도 파일 기준 서명을 써야 한다. → Task 6 테스트 `Resume_uses_file_signature_of_done_sql_task`.
5. **ASP 페이지가 없거나 `asp.siteRoot`가 없는 저장소의 sql 전용 명세.** ASP 영향 탐색은 조용히 아무것도 내지 않아야 하고, apply에 새 확인 질문이 생기면 안 된다. → Task 5 테스트 `No_asp_pages_no_asp_warnings_and_no_new_prompt`.

  - `CheckAsync(…, AspOptions? asp = null)`(맨 뒤 선택 매개변수)
  - `asp`가 null이면 `new AspOptions()` 기본값(확장자 `.asp`·`.inc`, 인코딩 `cp949`)을 쓴다.
  - 호출하는 곳은 설정의 `options.Asp`를 넘긴다.

  - 확장자가 `asp.extensions`에 없으면 `KindMismatch`: 「작업 {id}: asp 작업의 파일이 {확장자 목록 `, `로} 중 하나가 아닙니다: {path}」
  - 파일 읽기는 `AspTextCodec(asp.Encoding)`로 한다. 읽기 실패(InvalidDataException)는 `AspEncoding`: 「작업 {id}: 파일을 읽을 수 없습니다: {path} ({메시지})」
  - `Symbol`·`Lines` 둘 다 없으면 `AspTargetRequired`: 「작업 {id}: asp 작업은 #프로시저 또는 #L시작-끝으로 대상을 지정해야 합니다.」
  - `#이름`은 `AspPage.Parse(text).Procedures`에서 `Class.이름`/`이름`으로 찾는다(A1 `AspLocatePhase`와 같은 규칙). 없으면 `SymbolNotFound`, 여럿이면 `SymbolAmbiguous`(기존 문구 형식).
  - `#L`이 파일 줄 수를 넘으면 `LinesOutOfFile`: 「작업 {id}: 줄 범위 L{a}-{b}가 파일(1-{n}줄) 밖입니다」
  - `AspLinesAfterEdit`(Global Constraints 문구): 같은 파일 경로(대소문자 무시, `/`·`\` 같음)의 완료되지 않은 asp 작업 중 첫 작업이 아니면서 `Lines` 대상인 작업에 낸다.
  - 완료된(`Done`) asp 작업은 대상 검사를 건너뛴다(cs·sql과 같음).
  - asp 작업은 요청문 이름 검사(`UnknownIdentifier`)를 하지 않는다. VBScript 이름 색인이 없어 오탐이 많기 때문이다(Claude 결정).
