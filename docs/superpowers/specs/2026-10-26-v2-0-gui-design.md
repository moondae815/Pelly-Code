# V2-0 GUI 승인 창 (`pelly ui`) 설계

작성 2026-10-26. 상태: 설계, 사람 확인 전. 설계 검토(빌더 확인) 반영. 사람은 「질문 없이 바로 설계」를 골랐다. 「Claude 결정」으로 표시한 것은 사람이 아직 확인하지 않은 판단이다.

근거: PRD §12.2 V2-0 행 — 「GUI 승인 창 (`pelly ui`, Avalonia): External Tools에서 띄우는 작은 창으로 요청 입력·진행 표시·diff 승인」, 1~2주, v1 직후 착수 가능.

## 1. 왜 하는가

지금 IDE 연동은 External Tools가 띄운 **콘솔 창**에 기댄다. 요청문은 콘솔에서 입력하고, diff는 콘솔 컬러 출력으로 보고, `[y/N]`으로 승인한다(`deploy/ide-external-tools.md`). 여기에 알려진 약점이 셋 있다.

1. **입력이 막히는 IDE가 있다.** Rider는 외부 도구 출력을 Run 도구 창에 보여 줄 수 있는데, 이 창이 키 입력을 받지 않으면 요청문을 입력할 수 없다. 그러면 요청문을 인수에 고정하고 `--dry-run`/`--yes`로 돌아가야 해서, 승인 단계가 사실상 사라진다.
2. **diff 읽기가 불편하다.** 긴 diff는 콘솔에서 스크롤이 밀리고, 구형 콘솔(conhost)에서는 색·한글 표시가 환경에 따라 다르다.
3. **창이 바로 닫힌다.** `--pause-on-exit`라는 우회가 필요하다.

GUI 창은 셋을 한 번에 없앤다. 표준 입력이 필요 없고, diff를 스크롤 가능한 창에 보여 주고, 사람이 닫을 때까지 남는다.

## 2. 목표 / 비목표 / 실패 조건

**목표**
1. `pelly ui cs <파일> [--line n | --class/--method]`와 `pelly ui sql <파일> [--line n | --object]`로 작은 창을 띄운다.
2. 창에서 요청문을 입력하고 실행한다. 진행 상황(FSM 단계·시도·서버 대기)을 보여 준다.
3. 검증을 통과하면 diff를 보여 주고 「적용」/「거부」를 받는다. 거부하면 원본으로 되돌린다 — CLI와 똑같다.
4. 대상이 모호하면 창 안에서 고른다(`SelectAsync`). 경고 확인(`ConfirmAsync`)도 창 안에서 받는다.
5. 실행이 끝나도 창은 남는다. 결과를 보여 주고, 요청문을 고쳐 **다시 실행**할 수 있다.
6. 같은 `pelly.exe`의 새 명령으로 반입한다. 새 실행 파일을 더하지 않는다(GUI 네이티브 DLL만 `pelly.exe` 옆에 둔다, §7.2).
7. `deploy/ide-external-tools.md`에 GUI용 External Tools 항목을 더한다.

**비목표**
- `pelly apply`(명세 실행), `doctor`, `report`, `spec`, `rules`의 GUI. V2-0은 단발 실행(cs·sql)만 다룬다.
- diff 편집, 부분 승인(일부 hunk만 적용), 나란히 보기(side-by-side) diff. 통합(unified) diff만 보여 준다(CLI와 같은 내용).
- IDE 플러그인(VSIX·Rider 플러그인). PRD §1.4 제외 범위 그대로다.
- 대화형 채팅, 여러 파일 동시 수정 — v1 범위 밖 그대로다.
- macOS·Linux용 배포. 개발 PC(macOS)에서 창이 뜨기는 하지만 반입본은 win-x64뿐이다.
- 창에서 옵션(`--test`, `--think` 등)을 고르는 UI. 옵션은 명령줄 인수로만 준다(§4.2).
- 테마·다국어·창 위치 기억.

**실패 조건 (만들어도 실패로 보는 것)**
- 검증을 통과하지 않은 패치가 GUI 경로에서 파일에 남는다(PRD §1.3 불변 조건). 창을 닫든, 프로세스가 죽든 CLI와 같은 롤백을 지켜야 한다.
- 승인 없이 패치가 남는다. 「적용」을 누르지 않은 모든 경로(거부·창 닫기·취소·오류)는 원본으로 되돌린다.
- `pelly ui`가 실행 중 네트워크에 접속한다(설정된 Ollama·SQL 서버 제외). 빌드 시점 수집도 끈다(§7.3).
- 기존 CLI 명령(`cs`, `sql`, `apply` 등)의 동작·출력·종료 코드가 바뀐다.
- 한국어 Windows에서 요청문에 한글을 입력할 수 없다(IME 조합 문제). 이건 CI가 못 잡으므로 사람이 확인한다(§9).

## 3. 사용 흐름

```text
IDE External Tools ─ pelly ui cs "C:\src\OrderService.cs" --line 120
        │
        ▼
┌─ Pelly — OrderService.cs ──────────────────────────────────┐
│ 대상: OrderService.cs  120번 줄                            │
│ ┌──────────────────────────────────────────────────────┐ │
│ │ 수정 요청: 배송 중인 주문은 취소할 수 없게 해줘          │ │
│ └──────────────────────────────────────────────────────┘ │
│                                          [실행]  [닫기]   │
│ ── 진행 ───────────────────────────────────────────────── │
│ LOCATE   OrderService.Cancel                               │
│ EDIT (시도 1)  서버 응답 대기 중 (4초)                     │
│ VERIFY (시도 1)  빌드 통과                                  │
│ ── 변경 내용 ─────────────────────────────────────────── │
│ @@ -118,6 +118,8 @@                                        │
│ - if (order is null) return false;                         │
│ + if (order is null || order.Status == Shipping) ...       │
│                                       [적용]  [거부]       │
└────────────────────────────────────────────────────────────┘
```

1. 창이 뜨면 대상(파일, 줄 또는 멤버 이름)과 요청문 입력 칸이 보인다. 인수에 요청문을 주었으면 미리 채워 둔다. 실행은 사람이 「실행」을 눌러야 시작한다(Claude 결정: 요청문을 고칠 기회를 준다).
2. 실행 중에는 입력 칸과 「실행」이 잠기고 「취소」가 생긴다. 진행 줄은 `ShowStatus`가 부를 때마다 한 줄씩 쌓인다(CLI 출력과 같은 문구). 서버 대기처럼 같은 단계의 갱신은 마지막 줄을 바꾼다.
3. 모호한 대상은 목록에서 고른다. 경고 확인은 경고 문구와 「계속」/「중단」으로 받는다.
4. 검증을 통과하면 diff가 보이고 「적용」/「거부」가 생긴다. 이때 파일은 이미 바뀐 상태다(CLI와 같다). 「적용」은 승인, 「거부」는 거부(종료 2)다.
5. 끝나면 결과 줄을 보여 준다: 종료 코드와 뜻(PRD FR-00 표), 실패면 마지막 오류 요약. 입력 칸과 「실행」이 다시 열린다.
6. 「닫기」나 창 닫기로 끝낸다. 프로세스 종료 코드는 **마지막 실행의 종료 코드**다. 한 번도 실행하지 않고 닫으면 2(사용자 중단)다(Claude 결정).

## 4. 명령과 인수

### 4.1 형식 (Claude 결정)

```text
pelly ui cs  <file.cs>  ["<요청>"] [--class <Name>] [--method <Name>] [--line <n>] [cs 실행 옵션]
pelly ui sql <file.sql> ["<요청>"] [--object <Name>] [--line <n>] [sql 실행 옵션]
```

- `ui`는 Spectre 분기(branch)다. `ui cs`는 `CsSettings`, `ui sql`은 `SqlSettings`를 그대로 쓰고, 같은 검증(`--line`과 `--class/--method` 배타, 테스트 이름 형식 등)을 한다. 검증 코드는 복사하지 말고 `cs`·`sql` 명령과 함께 쓰도록 뽑아낸다.
- 허용하지 않는 옵션: `--yes`(GUI의 목적이 승인이다), `--pause-on-exit`(창이 남는다). 주면 종료 4. 나머지 옵션은 CLI와 같은 뜻이다. 공통 옵션(`--dry-run`·`--verbose`·`--think`·`--model`·`--endpoint`·`--config`·`--max-retries`)은 둘 다, `--test`·`--verify-test`·`--expect-break`·`--strict-baseline`·`--warn-as-error`는 `ui cs`에서만 받는다(PRD FR-00의 cs 전용 그대로).
- `CliApp.CommandSettings`와 `FindOptionWithoutValue`의 분기 목록에 `ui cs`·`ui sql`을 더한다(값 빠진 옵션 검사가 `ui`에서도 돌게).
- `--dry-run`이면 diff만 보여 주고 「적용」/「거부」 대신 「확인」만 둔다(파일은 안 바뀜, CLI와 같다).
- `--verbose`면 끝난 뒤 실행 요약(`ShowRunSummary`)을 결과 아래 접힌 영역에 보여 준다.

### 4.2 인수 오류

인수 오류는 두 층으로 나뉜다(설계 검토 반영, Claude 결정).
- **명령 검증 오류**(파일 없음, 옵션 충돌, `--yes` 지정, 설정 오류 등 — 명령 코드 안에서 걸리는 것): 창을 띄운 뒤 창 안에 빨간 오류로 보여 주고 「실행」을 잠근다. 종료 4. 이유: External Tools에서 「출력 창 사용」을 켜면 콘솔이 잘 안 보이므로, 창 없이 끝나면 사람은 아무것도 못 본다. 같은 문구를 표준 출력에도 쓴다.
- **명령줄 파싱 오류**(모르는 옵션, `--line abc` 같은 형식 오류, 값 빠진 옵션 — Spectre 파싱 또는 `RejectOptionWithoutValue`에서 걸리는 것): 창 없이 지금처럼 표준 출력에 쓰고 종료 4. 이 오류는 External Tools 항목을 처음 등록할 때만 생기고 출력 창에 보인다. 파싱 층까지 창으로 바꾸는 것은 비용에 비해 이득이 작다.

예외: 창 자체를 만들 수 없으면(그래픽 환경 없음, 네이티브 라이브러리 적재 실패) 표준 오류에 이유를 쓰고 종료 4.

## 5. 구조 (Claude 결정)

### 5.1 같은 FSM, 다른 `IUserInteraction`

실행 흐름은 바꾸지 않는다. Core의 모든 진행 표시와 입력은 이미 `IUserInteraction`(`IsInteractive`, `ConfirmAsync`, `SelectAsync`, `ShowDiff`, `ShowStatus`, `Warn`, `ShowRunSummary`) 하나로 나간다. GUI는 이것의 두 번째 구현(`GuiUserInteraction`)을 만든다. FSM·`IRunner`·`OrchestratorRunner`·롤백 코드는 그대로 쓴다.

**인터페이스를 조금 넓힌다** (설계 검토 반영, Claude 결정). 지금 인터페이스에는 GUI가 필요한 의미 정보가 없다.
- 최종 승인(`ReviewPhase`의 「적용할까요?」)과 경고 확인(`ApplyPhase`의 「그래도 계속할까요?」, `SpecRunner`의 경고 확인)이 똑같이 `ConfirmAsync`로 온다. GUI는 앞엣것에 「적용/거부」, 뒤엣것에 「계속/중단」을 보여야 한다. → 질문 종류(승인 / 경고 확인)를 구분할 수 있게 한다. 문구로 추측하지 않는다.
- `ShowStatus`에는 「새 줄」인지 「같은 줄 갱신」(서버 대기 초 세기)인지 구분이 없다. (단계, 시도)가 같은지로 추측하면 EDIT 머리 줄이 대기 줄에 덮이고 `ApplyPhase`의 여러 안내 줄이 뭉개진다. → 갱신 줄을 구분할 수 있게 한다.
- 정확한 모양(매개변수 추가, 새 메서드, 열거형)은 만드는 사람이 고른다. 조건: **CLI 출력과 동작은 바뀌지 않는다**(Spectre 구현은 새 정보를 무시해도 된다). 테스트 대역(가짜 `IUserInteraction`)도 함께 고친다.

**조립**: `Composition.Services`는 지금 Spectre `IUserInteraction`과 공용 취소 토큰을 프로세스 시작 때 싱글턴으로 등록한다. `ui` 명령은 GUI 구현과 실행마다 새 취소 토큰으로 `IRunner`를 조립해야 한다. 방법(`ui` 전용 조립 함수, 실행마다 만드는 팩토리 등)은 만드는 사람이 고르되, 실제 Ollama 백엔드·`HttpClient` 생성은 계속 `Composition.cs` 안에만 둔다(`NetworkPolicyTests`).

- `IsInteractive`는 항상 참이다.
- `ShowStatus`·`Warn`·`ShowDiff`·`ShowRunSummary`는 UI 스레드에 **게시(post)** 하고 바로 돌아온다. 실행 스레드를 막지 않는다.
- `ConfirmAsync`·`SelectAsync`는 UI에 질문을 띄우고 사람이 답할 때까지 기다린다(`TaskCompletionSource`). 취소 토큰이 취소되면 기다림도 취소된다(→ CLI와 같이 롤백·종료 2).
- 질문은 한 번에 하나다. 실행이 하나뿐이고 FSM이 순차라서 겹치지 않는다. 겹치면 프로그래밍 오류로 본다.

### 5.2 실행 세션 (화면과 분리한 상태 기계)

창의 상태는 화면 코드와 분리한 `UiSession`(가칭) 하나가 가진다: `대기 → 실행 중 → (질문 대기) → 끝남 → (다시 실행) …`. 「실행」·「취소」·「적용」·「거부」·「닫기」는 이 상태 기계의 입력이다. 이렇게 나누면 상태 전이와 롤백 경로를 Avalonia 없이 단위 테스트할 수 있다(§8).

### 5.3 취소와 창 닫기

- 실행 중 「취소」 또는 창 닫기 = Ctrl+C와 같다. 실행의 취소 토큰을 취소하고, FSM이 롤백을 마칠 때까지 기다린 뒤 닫는다. 그 동안 창은 「되돌리는 중…」을 보여 주고 버튼은 잠근다.
- 롤백을 기다리는 중 창 닫기를 또 눌러도 강제로 끝내지 않는다(Claude 결정). 롤백을 끝까지 하는 것이 불변 조건이다.
- 질문 대기 중 창 닫기 = 거부(종료 2) 후 닫기.
- 프로세스 종료 신호(SIGTERM·SIGHUP, Windows 콘솔 닫기)는 기존 `ShutdownCoordinator` 경로를 그대로 탄다. GUI 세션의 취소 토큰은 이 공용 종료 토큰과 연결한다.
- 「다시 실행」마다 새 취소 토큰을 만든다. 앞 실행의 취소가 다음 실행으로 번지지 않게 한다.

### 5.4 스레드

- Avalonia UI 스레드는 프로세스의 **주 스레드**다(macOS는 필수, Windows는 클립보드·IME 때문에 STA가 필요하다). `Program.cs`의 진입이 `ui` 분기일 때 이 조건을 지키는 방법(동기 `Main` + `[STAThread]`, 또는 `ui`일 때만 별도 STA 스레드)은 만드는 사람이 고른다. 단, **`ui`가 아닌 명령의 동작은 바뀌지 않아야 한다**(기존 Cli 테스트가 그대로 통과).
- FSM 실행은 스레드 풀에서 돈다. UI 스레드를 막는 `.Result`·`.Wait()`를 쓰지 않는다.

### 5.5 프로젝트 배치

- 새 프로젝트 `src/PellyCoder.Ui`(Avalonia 참조, 창·뷰모델·`GuiUserInteraction`·`UiSession`). `PellyCoder.Cli`가 이것을 참조하고 `ui` 명령을 등록한다. Ui는 Cli를 참조하지 않는다(순환 금지).
- 통합 diff 줄 계산(`Cli/Terminal/DiffRenderer.UnifiedLines`)은 Core로 옮겨 CLI와 GUI가 함께 쓴다. 복사하지 않는다. `DiffPlex` 참조도 Core로 옮긴다.
- 종료 코드 뜻 문구는 지금 어디에도 없다(Core `ExitCodes`에는 숫자만 있다). PRD FR-00 표를 보고 Core에 새로 쓴다(`ExitCodes` 옆, 한국어 한 줄씩).
- 새 테스트 프로젝트 `tests/PellyCoder.Ui.Tests`(헤드리스 창 테스트 + `UiSession` 단위 테스트).

## 6. 화면 세부 (Claude 결정)

- 크기: 처음 약 900×640, 크기 조절 가능, 최소 크기 있음. 항상 위(topmost) 아님. 제목 `Pelly — <파일 이름>`.
- 글꼴: Windows 시스템 글꼴을 쓴다. 본문은 맑은 고딕(Malgun Gothic), diff는 고정폭(Consolas, 한글은 대체 글꼴). Avalonia 기본 글꼴 패키지(Inter)는 한글 글리프가 없으므로 쓰지 않거나, 한글 대체가 되는지 확인한다.
- diff: CLI와 같은 통합 diff 줄. `+` 초록 배경, `-` 빨강 배경, `@@` 청록. 읽기 전용, 선택·복사 가능, 세로 스크롤. 파일 경로를 위에 보여 준다.
- 키보드: 「적용」 기본 단추 아님(실수 방지, CLI 기본값 N과 같은 취지). Esc = 거부/닫기, Ctrl+Enter = 실행.
- 테마: Fluent 밝은 테마 하나.
- 모든 외부 문자열(요청문, 파일 내용, 모델 응답, 오류 문구)은 텍스트로만 표시한다. 마크업으로 해석하지 않는다(Spectre 쪽 `Markup.Escape`와 같은 취지).

## 7. 반입·의존성 제약

### 7.1 패키지 (Claude 결정)

- Avalonia **12.x 최신 안정판**(.NET 10 지원, 헤드리스 xUnit v3 지원)을 `Directory.Packages.props`에 정확한 버전으로 고정한다. 저장소 테스트 스택(`xunit.v3.mtp-v2`, Microsoft Testing Platform)과 `Avalonia.Headless.XUnit`이 맞지 않으면, `Avalonia.Headless`만 쓰고 헤드리스 세션을 테스트에서 직접 띄운다. 12.x 안정판이 없거나 .NET 10 단일 파일에서 동작하지 않을 때만 11.x 최신 안정판으로 내린다. 어느 쪽이든 고른 이유를 원장에 남긴다(설계 검토 반영, Claude 결정). 필요한 것: `Avalonia`, `Avalonia.Desktop`, `Avalonia.Themes.Fluent`, 테스트에 `Avalonia.Headless.XUnit`. 그 밖의 패키지는 꼭 필요한 것만 쓴다(MVVM 툴킷·ReactiveUI는 쓰지 않는다: 창 하나에 의존성을 더할 이유가 없다).
- 라이선스 게이트(MIT·Apache-2.0·BSD 계열만)를 통과해야 한다. Avalonia·SkiaSharp·HarfBuzzSharp와 그 네이티브 패키지의 라이선스를 패키지 스크립트로 확인하고, 게이트에 걸리는 패키지가 나오면 **예외를 스스로 승인하지 말고 멈춰서 사람에게 묻는다**(예외 승인자는 사람).
- 간접 의존 패키지 중 알려진 취약 버전이 있으면 기존 방식대로 `Directory.Packages.props`에서 고정한다.

### 7.2 단일 파일

- `pelly.exe`는 계속 단일 파일, 트리밍 없음, 압축 없음이다. Avalonia의 **관리 어셈블리**는 단일 파일 안에 들어가고 `ui` 경로에서만 적재된다.
- **Avalonia 네이티브 라이브러리(Skia, HarfBuzz, ANGLE 등)는 단일 파일에 묶지 않고 `pelly.exe` 옆에 둔다** (설계 검토 반영, Claude 결정). 이유: `IncludeNativeLibrariesForSelfExtract`로 묶인 네이티브 파일은 명령과 상관없이 첫 실행 때 전부 임시 폴더에 풀린다. 그러면 `pelly cs`만 쓰는 사람도 수십 MB 추출 시간을 떠안고, 임시 폴더 DLL이 늘어 응용 프로그램 제어(AppLocker·WDAC)에 걸릴 위험이 커진다. 옆에 두면 `ui`일 때만 적재되고, 설치 폴더에서 바로 읽힌다. 단일 파일 게시 설정에서 해당 네이티브 파일만 번들에서 빼는 방법(`ExcludeFromSingleFile` 등)은 만드는 사람이 고른다. 기존 SqlClient SNI 등 다른 네이티브 파일의 처리는 바꾸지 않는다.
- 그래서 반입 zip에 파일이 늘어난다. `deploy/package-files.txt` 허용 목록, SHA256SUMS, 패키지 테스트, 설치 문서(`deploy/install.md`: 「`pelly.exe` 옆의 DLL을 함께 두어야 `pelly ui`가 뜬다」)를 함께 고친다. 네이티브 DLL이 없을 때 `pelly ui`는 이유를 말하고 종료 4, 다른 명령은 영향이 없다.
- `pelly.exe` 크기와 zip 크기가 늘어난다. 측정해 PRD §11.1에 적는다.
- 시작 시간: CI `publish-check`가 재는 첫 실행·두 번째 실행 모두, **`ui`가 아닌 명령(`--offline-selftest`)이 기존보다 10% 넘게 늘면 안 된다.** 네이티브 파일을 번들에서 뺐으므로 첫 실행에도 같은 기준을 건다.

### 7.3 오프라인

- 실행 중: Avalonia 런타임은 외부 통신을 하지 않는다. `NetworkPolicyTests`의 검사 범위(`src/`)에 새 프로젝트가 자동으로 들어가는지 확인한다.
- 빌드 중: Avalonia 빌드 도구에 익명 사용 정보 수집(빌드 시점)이 있으면 끈다(환경 변수·MSBuild 속성 중 문서가 정한 방법으로, 저장소 설정과 CI 양쪽에). 반입 심사 자료 `deploy/no-network.md`에 한 줄 적는다.

### 7.4 External Tools 설정

- GUI 항목: 명령 `pelly.exe`, 인수 `ui cs "$(ItemPath)" --line $(CurLine)`, Visual Studio는 **「출력 창 사용」 켬**(콘솔 창이 따로 뜨지 않게). `pelly.exe`는 콘솔 실행 파일이라 출력 창을 끄면 빈 콘솔 창이 함께 뜬다.
- Rider는 Run 도구 창으로 충분하다(표준 입력이 필요 없다).
- 기존 콘솔 항목은 그대로 둔다. GUI 항목은 추가다.
- 「실행 전에 저장」 안내는 그대로 유효하다.

## 8. 검증 방법

1. **`UiSession` 단위 테스트** (Avalonia 없이): 실행→승인=0, 실행→거부=2, 실행 중 취소=롤백 후 2, 질문 대기 중 닫기=2, 한 번도 실행 안 하고 닫기=2, 실패 후 다시 실행→성공=0(마지막 실행 코드), 롤백 대기 중 닫기 재요청 무시, 인수 오류=4로 「실행」 잠김. 실행은 가짜 `IRunner`로 대신한다.
2. **`GuiUserInteraction` 테스트**: `ConfirmAsync`가 사람의 답을 돌려줌, 취소 토큰으로 기다림이 끝남, `ShowStatus` 같은 단계 갱신이 마지막 줄을 바꿈, 외부 문자열이 마크업으로 해석되지 않음.
3. **헤드리스 창 테스트** (`Avalonia.Headless.XUnit`): 요청 입력→실행→가짜 실행이 diff를 보냄→「적용」 클릭→세션 종료 코드 0. 한글 문자열 입력(`KeyTextInput("배송 중인 주문")`)이 그대로 들어감. 헤드리스는 실제 IME를 거치지 않으므로 이것으로 IME를 확인했다고 보지 않는다.
4. **실제 FSM 연결 테스트**: 가짜 LLM 백엔드(기존 통합 테스트의 방식)로 `pelly ui`와 같은 조립에서 실제 파일을 고치고, 승인/거부/취소 뒤 파일 내용이 CLI와 같은지 확인한다.
5. **CI (Windows)**: 게시한 단일 파일 `pelly.exe`로 `pelly ui --selftest`(숨은 옵션, Claude 결정)를 실행한다. 실제 플랫폼으로 창을 만들고 한 번 그린 뒤 닫고 0으로 끝난다 — 단일 파일과 그 옆의 네이티브 DLL이 반입 zip 배치 그대로 적재되는지 확인한다. 그래픽 세션이 없는 CI라면 헤드리스 렌더링으로 Skia 적재까지만 확인하고, 그 사실을 문서에 적는다. `publish-check`·`package` 잡에 넣는다.
6. 기존 게이트: `dotnet build -warnaserror` 종료 0, `dotnet test` 실패 0.

## 9. 사람이 현장에서 확인할 것

CI와 헤드리스 테스트로는 확인할 수 없다.
- 한국어 Windows 11에서 요청 칸에 한글 IME로 입력(조합 중 글자 표시, 확정, 백스페이스).
- Visual Studio External Tools(「출력 창 사용」 켬)에서 창이 뜨고, 콘솔 창이 따로 뜨지 않고, 적용 후 파일 다시 불러오기가 되는지.
- 고해상도(125%·150% 배율)에서 글자·diff가 흐리지 않은지.
- 폐쇄망 PC에서 `pelly ui`가 뜨는지(백신·응용 프로그램 제어가 임시 폴더에 풀린 네이티브 DLL을 막지 않는지).

결과는 `deploy/field-results.md`에 칸을 더해 적게 한다.

## 10. 단계 (Claude 결정)

하나의 계획, 하나의 브랜치로 간다(1~2주 규모). 작업 순서의 큰 줄기:
1. Core로 옮기기(diff 줄 계산, 종료 코드 문구) — 동작 변화 없음.
2. `UiSession` + `GuiUserInteraction` + 단위 테스트.
3. Avalonia 프로젝트·창·헤드리스 테스트.
4. `ui` 명령(인수 검증 공유, 주 스레드 진입, 종료 코드), 실제 FSM 연결 테스트.
5. 단일 파일·`--selftest`·CI·라이선스·크기·시작 시간.
6. 문서: README, `deploy/usage.md`, `deploy/ide-external-tools.md`, `deploy/no-network.md`, `deploy/field-results.md`, PRD(§6.1 패키지, §11.1 크기, §12.2 구현 표시, 변경 이력).

- Avalonia 12의 정확한 패치 버전.
