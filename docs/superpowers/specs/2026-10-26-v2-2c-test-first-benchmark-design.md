## 1. 왜 하는가

V2-2a·V2-2b로 테스트 우선 검증은 동작한다. 그러나 이것이 모델의 실제 성공률을 올리는지는 아직 아무도 재지 않았다. PRD §12.6의 「수용 기준 충족률 ≥ 80%」와 「RED 확인 경고율(기록만)」도 셀 재료가 없다. PRD §12.6은 벤치마크에 「테스트가 연결된 작업 20건」을 더하라고 한다.

또 V2-2b 최종 검토에서 두 가드를 V2-2c로 미뤘다.
- 한 수용 기준의 RED와 GREEN이 서로 다른 작업에 있을 때, 그 사이에 테스트 파일이 바뀌었는지 보는 검사
- 그룹 안 테스트 파일 검사

V2-2a에서 미룬 한국어 스택 형식도 현장 측정 전에 필요하다.

## 4. `pelly-eval --test-first` (단독 실행 12건)

### 4.1 동작 (Claude 결정)
- 대상은 `judge.tests`가 있는 작업(지금 Modern 12건)뿐이다. 나머지는 「테스트 우선 대상 아님」으로 건너뛴다. `--tasks`로 고른 작업도 같은 규칙이다.
- 작업 복사본을 만든 뒤 그 작업의 판정 프로젝트를 **작업 공간 안**(`work/<id>/<root>/JudgeTests/<프로젝트>/`)으로 복사한다.
  - 이유: pelly의 `TestMethodIndex`·테스트 프로젝트 합집합은 작업 공간 안만 본다. 지금 판정 프로젝트는 작업 공간 밖(`work/<id>/judges/`)에 있다.
  - 판정 프로젝트의 `JudgeTargetRoot`는 복사본 안에서 작업 복사본 루트를 가리키게 고정한다. 방법(복사본에 `Directory.Build.props`를 쓸지 csproj의 기본값을 바꿀지)은 만드는 사람이 정한다.
  - 복사본을 복원한 뒤 실행한다.
- 요청은 `RunRequest.VerifyTests = judge.tests`, `ExpectBreaks = judge.failingTests`로 낸다. 그 밖은 v1 실행과 같다(`--yes`, 같은 재시도, 같은 설정).
- 독립 검증은 지금 방식 그대로다. 판정 프로젝트를 `work/<id>/judges/`에 따로 복사해 다시 빌드·실행하며, pelly가 실행 중에 만진 복사본과 섞이지 않는다.
  - (설계 검토 반영) 지금 `IndependentVerifier`는 작업 복사본 루트 아래 모든 `.csproj`를 코퍼스 프로젝트로 모은다. 작업 공간 안에 넣은 `JudgeTests/` 복사본은 명시적으로 빼고, 그것을 고정하는 테스트를 둔다. 지금처럼 순서에 기대지 않는다.
  - 판정 프로젝트가 코퍼스를 참조하는 방식은 둘이다. `Shop.Api.JudgeTests`는 `ProjectReference`, `Shop.Data.JudgeTests`는 코퍼스 소스를 `Compile Include`로 직접 컴파일한다. 뒤의 것은 pelly가 대상 참조로 찾지 못하고 「선언 프로젝트 합집합」(V2-2a §5.2a)으로만 들어온다. 두 방식 모두 테스트로 고정한다.
  - 복사본의 `JudgeTargetRoot` 기본값(`../../../../corpus/Modern`)은 복사 위치에서 틀린 곳을 가리키므로 반드시 덮어쓴다.
- `results.json` 행에 테스트 우선 결과(`red`, `green`, `regressions`, `breaksExcluded`, `firstAttemptGreen`)를 더한다. 실행 기록의 `summary.json`에서 읽는다. `firstAttemptGreen`은 §4.3을 위해 `TestFirstSummary`에 새로 더하는 값이다(첫 시도의 GREEN 판정: `Passed`·`Failed`·`NotChecked`, 첫 시도가 빌드에서 막혔으면 `NotChecked`).

### 4.2 대조 실험
- 같은 12건을 v1(`run`, `--test` 없음)과 `run --test-first`로 같은 모델·같은 `--repeat N`으로 돌린다. v1 기준선은 지금 사람들이 쓰는 방식이라 `--test`를 붙이지 않는다(설계 검토 반영, Claude 결정). 테스트 우선 방식에는 회귀 확인과 테스트 시간이 함께 들어가므로, 차이에 GREEN 피드백 효과와 회귀 관문 효과가 섞인다는 점을 요약에 적는다.
- `compare`에 `--metric test-first`(이름은 만드는 사람이 정함) 같은 별도 판정 모드를 둔다. 결과는 최종 작업 성공률의 차이, 시간 중위값의 비율, 검증 불변 조건 위반 수다.
- 기존 R4 채택 규칙(평균 +1.0건 등)은 프롬프트·설정 변경용이다. V2-2c 결과는 채택·거절이 아니라 **보고**로 낸다(Claude 결정). 테스트 우선 방식은 판정 장치라서, 성공률이 같아도 「요청을 하지 않은 패치」를 걸러낸 효과(§4.3)가 있다.

### 4.3 판정 테스트를 두 번 쓰는 문제
판정 테스트가 GREEN 판정에도, 독립 판정에도 쓰인다. 그래서 테스트 우선 방식에서는 「GREEN 통과 = 독립 판정 통과」가 거의 자동이다. 이를 요약에 밝히고, 효과를 다음 두 값으로 낸다.
- 두 값 모두 **테스트 우선 실행 안에서** 센다(설계 검토 반영, Claude 결정). 첫 시도의 프롬프트는 v1과 같고 v1은 테스트를 돌리지 않으므로, 「첫 시도가 빌드는 통과했는데 GREEN이 실패」면 v1이었다면 그 패치로 종료 0이 되었을 실행이다. 회차를 짝짓지 않는다.
- **막은 잘못된 패치 수** = `firstAttemptGreen == Failed`인 실행 수
- **피드백으로 고친 비율** = 그중 최종 종료 0이고 독립 판정까지 통과한 비율
- 함께 v1·테스트 우선 각각의 최종 작업 성공률도 낸다(같은 조건 대조).
- 하드코딩 확인: 테스트 우선 방식에서 성공한 diff 중 사람이 표본을 본다. 요약에 「사람 표본 검토 대상」 목록(작업 id·회차)을 낸다.

## 5. apply 테스트 연결 사례 8건

### 5.1 형식 (Claude 결정)
- `eval/benchmark/apply-test-first/<id>/` 폴더에 다음을 둔다.
  - `spec.md`: 기존 apply 사례와 같은 머리말. 수용 기준·`test:`·`breaks:`·작업을 담는다.
  - `files/`: 작업 복사본에 덮어 넣을 파일. RED 테스트 파일 등이며, `files/` 아래 상대 경로가 곧 `corpus/` 아래 경로다.
  - `expected.json`: 수용 기준별 기대 결과(`red`·`outcome`). 판정에 쓰지 않고, 사람 승인과 요약 표의 「기대」 칸에만 쓴다.
- `pelly-eval apply`가 `--cases`로 이 폴더도 고를 수 있게 한다. 기본 실행은 기존 12건만이다(수치 보존). `--set test-first`로 8건, `--set all`로 20건을 돈다.
- 승인: `eval/benchmark/apply-test-first/APPROVED.json`. 승인 전 결과의 요약 제목에 「예비(사람 승인 전)」를 붙인다.

### 5.2 구성 8건 (Claude 결정, 내용은 만드는 사람이 코퍼스에 맞춰 쓴다)
| id | 범위 | 다루는 것 |
| :--- | :--- | :--- |
| t1 | Modern | AC 하나를 서비스·컨트롤러 두 작업이 채움(첫 작업 RED, 마지막 작업 GREEN) |
| t2 | Modern | `breaks:`로 옛 동작 테스트(`*_CurrentlyCancels`)를 뺌 |
| t3 | Modern | 그룹 시그니처 변경 + 새 시그니처로 쓴 테스트(컴파일 RED, 엄격 회귀) |
| t4 | Modern | 이미 통과하는 테스트(RED 확인 경고, `--yes`로 계속) |
| t5 | Modern | 한 작업이 AC1의 마지막이자 AC2의 첫 작업 |
| t6 | Modern+Sql | C#+SQL을 함께 참조하는 AC(SQL 작업은 판정 안 함), 그리고 SQL만 참조하는 AC(미검증) |
| t7 | Modern | 수용 기준 테스트가 대상 프로젝트를 직접 참조하지 않는 테스트 프로젝트에 있음(선언 프로젝트 합집합으로만 찾음) |
| t8 | Legacy | 레거시 테스트 프로젝트 + `test.command`(`{trx}`), Windows 전용 |

- RED 테스트는 `files/`로 넣고 판정 프로젝트(`judges/`)는 쓰지 않는다.
- **독립 판정(설계 검토 반영, 상위 설계 §11을 따름):** apply가 종료 0이면 기존 독립 빌드에 더해, 사례의 `test:` 테스트를 pelly 밖에서 다시 빌드·실행한다(`TestRunner`를 그대로 써도 된다). pelly가 `Met`이라 했는데 독립 실행에서 그 테스트가 통과하지 않으면 **테스트 판정 불일치**로 센다. 검증 불변 조건 위반과 같은 급으로 요약에 따로 낸다. pelly가 스스로 채점한 충족률만 믿지 않기 위해서다.
- (설계 검토 반영) 지금 `ApplyBenchmark.LoadCases`는 평평한 `*.md`만 읽는다. 폴더 형식 사례는 새 로더로 읽는다. `--cases`는 지금처럼 id 글롭이고, `--set`이 어느 폴더를 볼지 정한다.
- (설계 검토 반영) 독립 빌드의 「바뀐 `.cs`」 비교 기준은 「원본 코퍼스 + 그 사례의 `files/`」다. 그래야 넣은 테스트 파일이 늘 「변경」으로 잡히지 않는다.
- t7은 원래 「테스트가 대상과 같은 파일」이었다. 그러면 테스트가 테스트 프로젝트 안의 대상 파일에 있어야 하고, 슬라이서가 테스트 원문을 프롬프트에 넣게 되어 비목표와 부딪힌다. 그래서 사례를 바꿨다(그 경우는 V2-2a 단위 테스트가 이미 고정한다).
- 사례의 RED 테스트가 원본 코퍼스에서 정말 RED(또는 t4는 이미 통과, t3은 컴파일 RED)인지를 확인하는 정의 검사를 `ApplyCasesTests`처럼 둔다. 실제 dotnet으로 돌며 macOS에서 되는 Modern 사례만 대상이다.

### 5.3 요약
`apply-summary.md`에 다음을 더한다. 계산은 `pelly report`(`ApplyReport.Build`)와 같다.

- 사례별 AC 표(기대 vs 실제)

## 6. 남은 가드 (V2-2b에서 미룬 것)

### 6.1 작업을 건너는 테스트 파일 검사 (Claude 결정)
- **무엇을 잡나(설계 검토 반영):** 대화형 apply는 작업마다 승인을 기다리므로, 그 사이에 사람이나 편집기가 테스트를 고칠 수 있다. 정상 흐름에서는 걸리지 않는다. 연결 작업마다 FSM이 자기 실행 안의 해시를 보고, `spec check`가 테스트 메서드를 대상으로 하는 작업을 막기 때문이다.
- AC의 RED와 GREEN이 다른 작업이면, SpecRunner가 **첫 연결 작업을 돌리기 직전** 그 AC 테스트 메서드의 선언 텍스트 해시를 잡는다(`TestMethodIndex` + 선언 텍스트, V2-2a `HashOf`의 「대상 파일일 때」 방식).
- 마지막 연결 작업 요청에 그 해시를 「기대 해시」로 싣는다.
- FSM은 기존 파일 단위 해시 확인을 그대로 두고, 기대 해시가 있으면 **추가로** 메서드 선언 해시를 비교한다(대체하지 않는다). 다르면 V2-2a와 같은 `TestFileChanged`로 마지막 작업이 롤백되고 종료 4다.
- 마지막 연결 작업이 그룹 안이면 기대 해시를 `GroupTester`에 넘겨 §6.2와 같은 자리에서 비교한다.
- 메서드 선언 텍스트만 비교한다. 같은 파일의 다른 멤버(도우미)를 다른 작업이 고치는 것은 정상 흐름이므로 오탐을 피한다. V2-2a 단독 실행의 파일 전체 해시는 그대로 둔다.
- `--resume`으로 첫 연결 작업이 이미 끝났으면 기대 해시가 없다. 이때는 단독 실행 규칙으로 돌아간다(그 실행 안에서만 본다). README 알려진 한계에 남긴다.

### 6.2 그룹 테스트 파일 검사
- `GroupTester.BaselineAsync`가 계획 테스트의 선언 텍스트 해시를 잡고, `VerifyAsync`가 통과 판정 직전에 다시 잰다.
- 다르면 그룹을 롤백하고 종료 4다. 새 실패 유형 `GroupTestFileChanged`를 쓰고 `FailureKinds`·`GroupFailureKinds`에 등록한다.
- 문구: `그룹 {id}: 지정한 테스트가 실행 중에 바뀌었습니다: {파일}`

## 7. 한국어 스택 형식
- 피드백의 스택 줄 정규식(`FeedbackBuilder`)이 영어 `at … in …:line N` 말고도 한국어 .NET Framework 형식 `위치: … 파일 …:줄 N`을 받게 한다.
- 정확한 형식은 픽스처로 고정한다. Windows 실기는 아직 확인하지 않았으므로 「Windows 미확인」으로 표시하고, 현장 반입 때 확인한다.
- README 알려진 한계의 「영어 스택만」 줄을 고친다.

## 8. GREEN 피드백 끝 문장 재생 실험 — 이번 단계에서 뺀다 (설계 검토 반영, Claude 결정)
- **빼는 이유:** 기록에는 시도별 프롬프트·출력·피드백만 있고, 그 시도 직전의 파일 상태는 없다. 「다음 시도가 GREEN이 되었나」를 실제로 판정하려면 작업 복사본을 그 시점으로 되돌려 패치하고 빌드·테스트해야 해서 이번 단계 범위를 넘는다. 끝 문장은 V2-2a 문장을 유지하고, 측정(§9)의 `firstAttemptGreen`·최종 성공률로 효과를 간접적으로 본다. 재생 실험은 시도별 파일 상태 기록을 먼저 만든 뒤 따로 계획한다.
- 아래는 원래 안이다(참고용).
- V2-2a는 끝 문장을 `The test cannot be changed. Make it pass by implementing the request.`로 고정했다. 상위 설계 §5.5는 「재생 실험으로 고른다」고 했다.
- `pelly-eval`에 GREEN 실패 피드백의 끝 문장만 바꿔 같은 프롬프트로 다시 생성해 보는 재생 명령을 둔다. 이름과 입력 형식은 만드는 사람이 정한다(Claude 결정). 입력은 기록된 `prompt.txt`, 출력은 후보별 「다음 시도가 GREEN이 되었는가」 비율이다.
- 후보는 지금 문장을 포함해 셋이다. 문구는 만드는 사람이 고르되 모두 영어, 한 줄, 비슷한 길이다.
- 결과는 문서(`docs/v2-2c-feedback-replay.md`)로 남긴다. 바꿀지는 사람이 정한다. 기본은 지금 문장 유지다.
- 로컬 모델이 없으면 도구와 문서 틀만 만들고 측정은 사람이 한다.

  - apply 독립 판정의 테스트 재실행과 「테스트 판정 불일치」 집계
