# `pelly asp` A2 — SP와 ASP를 한 명세로 함께 고치기 설계

작성 2026-11-09. 상태: 설계 초안, 빌더 확인 반영(질문 4건은 「Claude 결정, 빌더 확인 반영」으로 표시).

## 1. 왜 하는가

업무 로직을 고치는 요청(「주문 목록에 상태 조건 추가」)은 SP와 그 SP를 부르는 ASP 페이지를 함께 고쳐야 한다(사람 답). 지금도 `pelly sql`과 `pelly asp`를 차례로 돌리면 고칠 수는 있다. 하지만 이렇게 돌리면 세 가지가 빠진다.

1. **한 묶음이 아니다.** SP는 고쳤는데 ASP 수정이 실패하면, 사람이 SP 수정을 직접 되돌려야 한다.
2. **SP를 부르는 다른 페이지를 모른다.** 매개변수를 하나 더하면 그 SP를 부르는 다른 페이지가 깨지는데, 지금은 그 페이지들을 찾아 주지 않는다. 지금 SQL 영향 탐색은 DB의 다른 SP와 C# 문자열만 찾고 `.asp`·`.inc`는 보지 않는다.
3. **ASP 수정이 옛 SP를 기준으로 판정된다.** `pelly asp`의 SP 검사(존재·인수 개수)와 모델 입력은 **개발 DB의** SP 매개변수를 쓴다. 그런데 SP 파일은 고쳤어도 DB에는 아직 배포 전이다. 그래서 새 매개변수를 넘기는 ASP 수정이 「인수 개수가 다름」 경고를 받고, 모델은 옛 매개변수만 보고 코드를 쓴다.

A2는 이 셋을 명세(`pelly spec`·`pelly apply`)로 푼다. 명세에 `asp` 작업 종류를 더하고, SP 영향 탐색이 ASP 페이지까지 찾게 한다.

## 2. 목표 / 비목표 / 실패 조건

**목표**
1. 명세 작업 줄에 `asp` 종류를 더한다. 대상은 `.asp`·`.inc` 파일의 프로시저(`#이름`) 또는 줄 범위(`#L시작-끝`)다(§3).
2. `spec check`가 asp 작업을 검사한다. 파일 존재, `asp.extensions`, 프로시저 존재·모호함, 줄 범위가 파일 안인지를 본다.
3. `pelly apply`가 asp 작업을 A1 파이프라인으로 차례대로 실행한다. 그룹(`[G1]`)에 sql·asp를 넣을 수 있게 하고, 그룹 안 작업이 하나라도 실패하면 함께 되돌린다(§4.1 — V2-1 그룹 규칙을 넓힘).
4. **SP → ASP 영향 탐색:** `spec check --impact`와 `apply`의 사전 영향 탐색이, sql 작업이 바꾸는 SP를 부르는 `.asp`·`.inc` 파일·줄을 사이트 전체에서 찾는다. 그 호출이 명세의 asp 작업 대상 안에 없으면 「영향 대상이 명세에 없습니다」 경고를 낸다(§4.3). DB 연결 없이도 동작한다.
5. **바뀐 뒤의 SP로 판정:** 같은 apply의 앞선 sql 작업이 바꾼 SP를 asp 작업이 부르면, 모델 입력과 SP 검사가 DB가 아니라 **수정된 SQL 파일에서 읽은 매개변수**를 쓴다(§4.4).
6. **apply 뒤 확인:** sql 작업이 SP의 매개변수 목록을 실제로 바꿨는데, 그 SP를 부르는 페이지 중 같은 apply에서 고치지 않은 곳이 있으면 결과에 경고한다(§4.5).
7. `apply.json`·`summary.json`·`pelly report`·README·`deploy/usage.md`·PRD·`deploy/field-results.md`에 반영한다.

**비목표**
- 실행 검증(IIS·브라우저·DB 실행). A1과 같다.
- `spec draft`가 asp 작업을 제안하는 것. 초안 색인·프롬프트는 cs·sql 그대로다(A1 설계 §4.8의 결정). 다만 사람이 초안에 asp 줄을 직접 써 넣으면 검사·적용은 된다.
- `js`·`css` 작업 종류. W3에 남긴다. 이 문서의 줄 범위 문법(`#L`)은 W3도 쓸 수 있게 일반적으로 정한다.
- DB 배포. `pelly apply`는 지금처럼 파일만 고친다.
- SP의 결과 열(레코드셋 열) 변경 추적. 결과 열은 DB에서 실행해 봐야 알 수 있어 다루지 않는다(A1 설계 §4.8의 결정). 매개변수만 다룬다.
- ASP가 동적으로 만든 SP 이름(`"usp_" & kind`). 찾지 못한다(A1과 같음).

**실패 조건 (기술적으로 돌아가도 실패로 본다)**
- SP 수정은 남고 ASP 수정만 실패해서, 사람 모르게 둘이 어긋난 채로 끝난다. 그룹으로 묶으면 함께 되돌리고, 묶지 않았으면 결과에 「T1은 적용됨, T2는 실패」를 분명히 보여야 한다.
- 매개변수를 더한 SP를 부르는 ASP 수정이 옛 매개변수 기준으로 「인수 개수 다름」 판정을 받거나, 모델이 새 매개변수를 모른다.
- SP를 부르는 페이지가 수십 곳일 때 경고가 쏟아져 명세 검사를 읽을 수 없다. 기존 SQL 영향 경고와 같이 상한을 두고 전체 목록은 파일로 남긴다.
- 앞선 asp 작업이 같은 파일을 고친 뒤, 뒤 작업의 줄 범위가 엉뚱한 곳을 가리킨다(§3.2).

## 3. 명세 문법

### 3.1 작업 줄

```
- [ ] T1 sql db/proc/usp_OrderList.sql 상태(@status) 조건을 더한다 [G1]
- [ ] T2 asp admin/order/list.asp#Search T1의 @status를 넘기고 검색 폼에 상태 선택을 더한다 [G1]
- [ ] T3 asp admin/order/list.asp#L120-148 상태 선택 select를 검색 조건 줄에 넣는다 [G1]
```

- **종류 낱말 `asp`:** 기존 `cs`·`sql`처럼 종류 낱말로 정한다. 파일 확장자는 `asp.extensions`(기본 `.asp`·`.inc`)에 맞아야 한다(맞지 않으면 기존 `KindMismatch`). 이를 위해 파서의 `cs|sql` 세 곳(작업 줄, 작업 모양 줄, 체크박스 줄)에 `asp`를 더한다.
- **대상:**
  - `#이름` — `Function`·`Sub` 하나. `Class.이름`도 받는다(A1 `--proc`와 같음).
  - `#L시작-끝` — 줄 범위(A1 `--lines`와 같음). `L` 대문자이고, 줄 번호는 `spec check`를 할 때의 파일 기준이다(Claude 결정).
  - 대상이 없으면 `spec check` 오류다(`AspTargetRequired`). 파일 전체를 대상으로 하지 않는다. A1에서도 대상 없이 실행하면 프로시저를 고르게 하는데, 명세는 대화형이 아니기 때문이다.
- `#L…`는 `asp` 작업에서만 받는다. `cs`·`sql`에 쓰면 오류다. 이 문법은 W3(`js`·`css`)이 다시 쓸 수 있다.

### 3.2 같은 파일의 줄 범위 작업 (Claude 결정)

앞선 작업이 같은 파일을 고치면 줄 수가 바뀌어, 뒤 작업의 `#L` 범위가 어긋난다. 처리 규칙은 다음과 같다.
- `spec check`: 같은 asp 파일에 작업이 둘 이상이고, 그중 앞이 아닌 작업이 `#L` 대상이면 **오류**다(`AspLinesAfterEdit`). 문구: 「T3의 줄 범위는 같은 파일을 먼저 고치는 T2 뒤에 어긋날 수 있습니다. 프로시저 대상(#이름)으로 쓰거나 작업을 하나로 합치십시오」.
- 프로시저 대상(`#이름`)은 실행할 때 다시 찾으므로 순서와 상관없다.
- `#L` 작업이 그 파일의 첫 작업이면 허용한다.
- 이유: 줄을 옮겨 계산하는 방식은 앞 작업이 그 범위 안을 고친 경우를 판정할 수 없다. 틀리면 엉뚱한 곳을 고치므로 막는 쪽을 골랐다.

### 3.3 `spec check`가 asp 작업에 하는 검사

검사 순서는 기존 `CheckTask`와 같다. asp에서 더하는 것은 다음과 같다.

| 검사 | 문제 코드 | 수준 |
|---|---|---|
| 확장자가 `asp.extensions`가 아님 | `KindMismatch`(기존, 문구에 asp 추가) | 오류 |
| 대상 없음 | `AspTargetRequired` | 오류 |
| `#이름` 프로시저가 없음·여럿 | `SymbolNotFound`·`SymbolAmbiguous`(기존 코드 재사용) | 오류 |
| `#L` 범위가 파일 밖이거나 거꾸로 됨 | `LinesOutOfFile` | 오류 |
| `#L`이 `cs`·`sql` 작업에 쓰임 | `LinesNotSupported` | 오류 |
| §3.2 | `AspLinesAfterEdit` | 오류 |
| 파일을 읽을 수 없음(인코딩) | `AspEncoding`(기존 실패 유형과 같은 이름) | 오류 |

A1의 판정(구조·안전·컴파일 등)은 `spec check`에서 하지 않는다. 적용할 때 A1 파이프라인이 한다.

## 4. 설계

### 4.1 apply가 asp 작업을 실행하는 방식

- `FsmTaskExecutor`에 asp 갈래를 더한다. `RunRequest`의 `Kind = EditKind.Asp`, 프로시저 대상이면 A1 `--proc` 값, 줄 범위면 A1 `--lines` 값을 넣는다.
- 파이프라인은 `FsmOrchestratorFactory.CreateAsp`(A1과 W2가 더한 블록 판정 포함)를 그대로 쓴다. 고르는 곳은 `Composition`의 종류별 분기다.
- **테스트 우선(V2-2):** asp 작업에는 테스트가 없으므로 해당하지 않는다.
  - 그룹 안에 cs 작업이 있으면 그룹 테스트 우선 규칙은 cs 작업에만 적용된다(기존 동작).
  - asp만 있는 그룹은 테스트 우선을 건너뛴다.
- **그룹 규칙을 넓힌다 (Claude 결정, 빌더 확인 반영 — V2-1 결정 변경):** 지금 파서는 sql 작업을 그룹에 넣으면 `SqlInGroup` 오류를 낸다. V2-1 설계는 그룹을 「C# 빌드 검증 단위」로 정했고, `RunGroupAsync`는 작업마다 `.csproj`를 찾는다. A2는 이렇게 바꾼다.
  - `SqlInGroup`을 없앤다. 그룹에는 cs·sql·asp를 섞을 수 있다.
  - 그룹은 두 가지 일을 한다: ① **함께 되돌림**(작업 하나라도 실패하면 그룹 전체 파일을 백업으로 복원), ② **C# 빌드·테스트 검증**.
  - ②는 그룹 안 **cs 작업에만** 적용한다. 대상은 cs 작업이 속한 프로젝트들이고, 기준 빌드·그룹 빌드·오류 귀속·재실행·그룹 테스트 우선이 여기에 들어간다.
  - cs 작업이 없는 그룹(sql·asp만)은 ②를 건너뛰고 ①만 한다. 작업을 차례로 실행해서 모두 성공하면 확정한다.
  - sql·asp 작업은 그룹 빌드의 오류 귀속·재실행 대상이 아니다. 각자 자기 파이프라인 안에서 재시도한다.
  - V2-1 설계(§3·§4)의 「그룹에는 cs 작업만」 문장은 이 규칙으로 고친다. `spec draft` 예비 측정에서 `SqlInGroup` 때문에 실행되지 않던 초안이 이제 실행될 수 있다는 점을 PRD 변경 이력에 적는다.
- **되돌리기:** 그룹 실패 시 되돌림은 위 ①(백업으로 파일 복원)이다. ASP 파일 복원은 A1의 바이트 이어 붙이기 쓰기 덕분에 원본 바이트 그대로다.
- **결과 표시:** 작업마다 「적용됨·실패·건너뜀」을 보이는 기존 표시를 쓴다. 그룹이 없는 sql + asp 명세에서 asp가 실패하면, 끝에 경고 한 줄을 더한다: 「T1(sql)은 적용됐고 T2(asp)는 실패했습니다. SP와 페이지가 어긋나 있을 수 있습니다. 함께 되돌리려면 [G1]로 묶으십시오」(Claude 결정, §2 실패 조건).
- **실행 기록:** `apply.json`의 작업 항목에 `kind: "asp"`와 대상(`proc` 또는 `lines`)이 들어간다. 작업별 `summary.json`은 A1 형식 그대로다.

### 4.2 사이트의 SP 호출 색인

`.asp`·`.inc` 전체를 훑어 「어느 파일 어느 줄이 어떤 SP를 부르는가」를 만든다.

- **찾기:** A1의 `AspSpCallFinder.Find(page, asp.spCallFunctions)`로 한다. 래퍼 함수 설정도 그대로 쓴다.
- **범위:** `asp.siteRoot`(없으면 작업 공간 루트) 아래, 확장자는 `asp.extensions`이고, 파일 수 상한은 W2 색인과 같이 2000이다.
- **캐시:** W2 사이트 색인(`WebSiteIndex`, `.pelly/cache/`)에 SP 호출을 함께 담아 파일 해시로 재사용한다(Claude 결정). 색인을 따로 두면 같은 페이지를 두 번 해석하기 때문이다. 캐시 판을 올린다.
- **한 항목:** `(상대 경로, 줄, SP 이름(스키마 정규화), 인수 개수 또는 모름, 감싼 프로시저 이름 또는 없음)`.
- **include:** `.inc` 안의 호출은 그 `.inc` 줄로 남긴다. 경고에는 「(include: 그 파일을 쓰는 페이지 N곳)」을 덧붙인다. 개수는 W2 색인의 `IncludersOf`로 센다.

### 4.3 SP → ASP 영향 탐색

**연결 (Claude 결정, 빌더 확인 반영):** ASP 호출 찾기는 `SqlImpactFinder`와 **따로** 둔다. 지금 apply의 SQL 영향 탐색은 `sql.production`이 설정됐을 때만 돌고, 아니면 C# 문자열 찾기까지 통째로 건너뛴다. ASP 찾기는 파일만 보므로 그 조건에 묶지 않는다.
- **`spec check`:** 지금 SQL 탐색과 같이 `--impact`일 때 돈다.
- **`pelly apply`:** 명세에 완료되지 않은 sql 작업이 있으면 `sql.production`과 상관없이 돈다. 그 경고는 기존 영향 경고와 함께 「경고가 있습니다. 계속할까요?」 확인에 들어간다. `--yes`이면 묻지 않고, 비대화형은 기존 규칙을 따른다.
- **바뀌는 점:** production이 없는 개발 PC에서도, sql 작업이 바꾸는 SP를 명세 밖 ASP가 부르면 apply가 확인을 묻게 된다. 이것이 목표 4의 의도다. README에 한 줄 적는다.
- **전체 목록 파일:** SQL 탐색이 돌지 않은 경우에도 `asp` 배열만 담아 같은 경로에 쓴다.

- **씨앗:** 기존과 같이 완료되지 않은 sql 작업이 바꾸는 SP다.
- **찾는 것:** §4.2 색인에서 SP 이름이 같은 호출. 이름 비교는 기존 SQL 이름 규칙대로 한다(스키마 생략 = `dbo`, 대소문자 무시).
- **명세에 있는지 판정:** 호출이 아래 중 하나에 들어 있으면 「명세에 있음」으로 친다.
  - 같은 파일의 asp 작업 대상: 프로시저 대상이면 그 프로시저 안, 줄 범위면 그 범위 안.
  - 같은 파일 asp 작업이 프로시저 대상이고, 호출이 다른 프로시저나 프로시저 밖에 있으면 「명세에 없음」이다(Claude 결정 — 같은 파일이라도 그 줄은 아무도 고치지 않는다).
- **경고 문구:** 기존 영향 경고 형식을 따른다.
  - 「작업 T1의 영향 대상이 명세에 없습니다: admin/order/view.asp:88 (usp_OrderList 호출, 인수 5개)」
  - include면 「(include: 그 파일을 쓰는 페이지 3곳)」을 덧붙인다.
- **상한:** SP 하나당 ASP 경고는 10개까지다(기존 `MaxWarningsPerTable`과 같은 값). 넘으면 「외 N곳」을 한 줄로 보인다.
- **전체 목록:** 기존 SQL 목록 파일(`.pelly/impact/<명세>-sql.json`, apply는 `.pelly/runs/apply-…/impact-sql.json`)에 `asp` 배열로 넣는다. 각 항목은 `path`, `line`, `object`, `arguments`, `procedure`, `covered`다.
- **DB가 없을 때:** DB 쪽 찾기는 지금처럼 「연결 안 됨」 경고 후 건너뛰고, ASP 찾기는 그대로 한다.
- **`spec draft`:** 영향 탐색을 다시 돌리므로 ASP 경고도 보인다. 하지만 asp 작업 줄을 자동으로 더하지는 않는다(비목표).

### 4.4 asp 작업이 쓰는 SP 매개변수 — 「바뀐 뒤」

같은 apply에서 앞선 sql 작업이 끝난 SP는 DB와 파일이 다르다(배포 전). asp 작업은 그 SP에 대해 **파일 기준 매개변수**를 쓴다.

- **어떤 SP인가:** 이번 apply에서 「적용됨」이 된 sql 작업의 대상 SP와, **같은 명세에서 이미 완료(`[x]`)된 sql 작업의 대상 SP**다(Claude 결정, 빌더 확인 반영). 그룹 없는 sql+asp에서 asp가 실패한 뒤 `apply --resume`으로 이어 가면, SP는 이미 파일에만 바뀌어 있고 DB에는 배포 전이기 때문이다. 완료된 작업의 서명은 지금 SQL 파일에서 읽는다. 작업 결과로 바뀐 SQL 파일을 ScriptDom으로 해석한다. 초안 색인의 `PROCEDURE (…)` 만들기를 공용으로 옮겨 재사용하고, 매개변수 이름·형식·OUTPUT을 얻는다.
- **쓰는 곳:**
  1. **ASP 모델 입력 [READ-ONLY: sql]:** 그 SP 줄에 「(T1이 바꾼 뒤, 아직 DB에 배포 안 됨)」을 붙이고 파일 기준 매개변수를 보인다. 나머지 SP는 지금처럼 개발 DB 기준이다.
  2. **ASP SP 검사(`AspSpStep`):** 존재 확인과 인수 개수 비교를 파일 기준 매개변수로 한다. 그 SP가 새로 만든 SP라 DB에 없어도 「없음」으로 막지 않는다.
     - 개발 DB 연결이 없을 때 지금은 단계 전체를 건너뛴다. A2에서는 파일 기준 서명이 있는 SP만 검사하고, 나머지는 「건너뜀(DB 없음)」으로 남긴다(Claude 결정, 빌더 확인 반영).
- **전달 방법:** `TaskRunOptions`에 「이번 apply에서 바뀐 SP의 파일 기준 서명」 목록을 담아 asp 작업에 넘긴다(Claude 결정). 파이프라인은 그 목록을 DB 조회보다 먼저 본다.
- **`pelly asp` 단독 실행:** 이 목록이 없으므로 지금과 같다.
- **해석 실패:** SQL 파일을 해석하지 못하면 DB 기준으로 돌아가고, 경고 한 줄을 남긴다: 「T1의 SP 파일을 해석하지 못해 개발 DB의 매개변수를 씁니다」.

### 4.5 apply 뒤 확인 — 매개변수가 바뀐 SP

- **비교:** 각 sql 작업이 「적용됨」이 되면, 그 SP의 원래 파일과 바뀐 파일에서 매개변수 목록(이름·순서·OUTPUT·기본값 유무)을 비교한다.
  - 원래 파일은 그 작업 실행 전 백업이다.
  - 앞선 apply에서 이미 완료된 sql 작업(`--resume`)은 이 비교를 하지 않는다(Claude 결정). 그때의 원본을 믿고 쓸 수 없기 때문이다.
- **경고:** 다르면, §4.2 색인에서 그 SP를 부르는 호출 중 이번 apply에서 「적용됨」이 된 asp 작업 대상 안에 없는 것을 모아 경고로 보인다.
  - 문구: 「usp_OrderList의 매개변수가 바뀌었습니다(@status 추가). 고치지 않은 호출: admin/order/view.asp:88 외 2곳」
  - 기본값이 있는 매개변수가 끝에 더해진 경우에는 「기존 호출은 그대로 동작할 수 있음」을 덧붙인다. 막지는 않는다(Claude 결정 — Classic ADO는 기본값 매개변수를 빼고 불러도 되는 경우가 많다).
- **기록:** `apply.json`에 `aspCallersNotUpdated` 목록으로 남기고, `pelly report`가 「SP 매개변수 변경 뒤 고치지 않은 ASP 호출 N곳」을 센다.
- 이 경고는 종료 코드를 바꾸지 않는다.

### 4.6 결과와 기록

- `TaskKind`에 `Asp`를 더한다. 파서·검사·실행기·`apply.json`·`pelly report`(작업 종류별 수)에 반영한다.
- 새 문제 코드(spec check): `AspTargetRequired`, `LinesOutOfFile`, `LinesNotSupported`, `AspLinesAfterEdit`.
- `impact-sql.json`에 `asp` 배열(§4.3), `apply.json`에 `aspCallersNotUpdated`(§4.5).
- `pelly doctor`는 바꾸지 않는다.

## 6. 검증 (pelly 자체 테스트)

- **파서:** `asp` 줄, `#이름`·`Class.이름`·`#L10-20`, `#L`을 cs·sql에 쓰면 오류, 그룹·완료 표시·실패 주석과 함께.
- **spec check:** 표 §3.3의 각 줄, `asp.extensions` 설정 반영, §3.2(첫 작업 `#L`은 허용, 뒤 작업 `#L`은 오류, `#이름`은 허용).
- **영향 탐색:**
  - 직접 호출·`{call}`·래퍼 함수·`.inc` 안 호출.
  - 프로시저 대상 안/밖 판정, 줄 범위 안/밖 판정.
  - SP 하나당 상한 10과 「외 N곳」, 전체 목록 파일의 `asp` 배열.
  - DB 없이도 ASP 경고가 나옴.
  - 동적 SP 이름은 찾지 않음.
- **apply:**
  - sql→asp 순서 실행.
  - 그룹에서 asp 실패 → sql 파일도 원래 바이트로 복원.
  - 그룹 없는 sql+asp에서 asp 실패 → 어긋남 경고.
  - `--dry-run`.
- **바뀐 뒤 서명:**
  - T1이 `@status`를 더하고 T2가 그 SP를 새 인수 개수로 부른다 → `AspSpStep` 통과, 모델 입력에 「T1이 바꾼 뒤」 줄.
  - T1이 새 SP를 만들고 T2가 부른다 → 「없음」으로 막지 않음.
  - SQL 파일 해석 실패 → DB 기준으로 돌아가고 경고.
- **apply 뒤 확인:** 매개변수 변경 + 고치지 않은 호출 → 경고와 `apply.json` 목록. 기본값 매개변수를 끝에 더한 경우 덧붙임 문구. 매개변수가 그대로면 경고 없음.
- **A1 단독 실행:** `pelly asp` 결과가 바뀌지 않음(기존 테스트 그대로).
- **게이트:** `dotnet build -warnaserror` 종료 0, `dotnet test` 실패 0.

## 7. 사람이 확인할 것

**결정 (아직 없음 — 아래 Claude 결정 중 바꾸고 싶은 것)**
- **V2-1 그룹 규칙 변경:** sql을 그룹에 넣을 수 있게 하고, 그룹은 「함께 되돌림 + (cs가 있으면) C# 빌드 검증」이 된다(§4.1).
- production 연결이 없어도 apply가 ASP 영향 경고로 확인을 묻는다(§4.3).
- 줄 범위 문법 `#L시작-끝`, 같은 파일을 먼저 고치는 작업 뒤의 `#L`은 오류(§3.1·§3.2).
- 그룹 없는 sql+asp에서 asp가 실패해도 sql 수정은 남기고 경고만 한다(그룹으로 묶으면 함께 되돌림, §4.1).
- 매개변수가 바뀐 뒤 고치지 않은 호출은 경고만 하고 종료 코드는 바꾸지 않는다(§4.5).
- `spec draft`는 asp 작업을 제안하지 않는다(비목표).

**현장 (`deploy/field-results.md` §16에 더함)**
- 같은 SP를 여러 페이지가 부르는가, 공용 `.inc` 래퍼를 거치는가. 현장 A3 답이 있으면 `asp.spCallFunctions`를 채운 뒤 영향 경고 수를 본다.
- 실제 업무 로직 요청 1건을 sql + asp 명세로 돌린 결과와 화면 확인. 그룹 사용 여부, 영향 경고가 맞았는지를 본다.

## 8. 빌더에게 맡기는 것

- `SpecTask`에 줄 범위를 담는 방식(별도 필드 또는 `Symbol` 해석). 기존 `Symbol` 사용처가 깨지지 않게.
- SP 호출 색인 항목의 자료형과 W2 색인 안 위치, 캐시 판 번호.

- 「바뀐 SP 서명」을 `TaskRunOptions`로 넘기는 형태와 A1 파이프라인 안에서 쓰는 지점.
- 코퍼스 페이지 내용과 벤치마크 3건의 구성(§5 목록은 출발점).
