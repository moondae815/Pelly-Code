# V2-3 프로젝트 규칙 — 외부 사전 측정 (규칙 있음 / 없음)

* **날짜:** 2026-10-24
* **용도:** PRD §12.6 "규칙 도입 효과(성공률 +5%p 이상)"의 **외부 참고치**다. PRD §2.1에 따라 KPI 최종 판정은 폐쇄망에서 실제 코드베이스로 한다. 이 수치로 판정하지 않는다.
* **환경:** macOS arm64(Darwin 25.6.0), Ollama 0.40.0, 모델 `qwen3.6:35b`(GGUF `Q4_K_M`, digest `a7eb95c53bcf…` — [M4 기준선](m4-gguf-baseline.md)과 같은 파일), SQL Server 2022 컨테이너
* **코드:** `2bed072`(pelly 0.9.1, 규칙 기능 + forbid 코드 토큰 검사 포함). 프롬프트 `cs-v2`·`sql-v1`, `llm.thinkMode = retry`, `budget.think = 512`, `budget.system = 450`, `budget.rules = 150`, 샘플링 기본값.
* **요약 파일:** [baseline.summary.json](v2-3-rules-premeasure/baseline.summary.json), [rules.summary.json](v2-3-rules-premeasure/rules.summary.json)

## 1. 방법

* 같은 날, 같은 코드·모델로 내장 벤치마크(50건)를 **규칙 없이** 3회, **규칙을 넣고** 3회 돌렸다. 두 실행 모두 시작 전에 SQL 코퍼스를 다시 배포했다.
* 규칙은 코퍼스 사본의 루트마다 `pelly rules init --yes`로 만든 초안을 **손대지 않고** 썼다. "초안 그대로의 효과"를 잰 것이다. 초안: [Modern](v2-3-rules-premeasure/agents/Modern.AGENTS.md) · [Legacy](v2-3-rules-premeasure/agents/Legacy.AGENTS.md) · [Sql](v2-3-rules-premeasure/agents/Sql.AGENTS.md)

  | 루트 | 규칙 |
  | :--- | :--- |
  | Modern | `[*]` 주석은 한국어로 · `[async]` `.Result`/`.Wait()` 금지(forbid) · `[dapper]` Dapper 파라미터 |
  | Legacy | `[*]` 주석은 한국어로 · `[dapper]` Dapper 파라미터 |
  | Sql | `[procedure]` 프로시저 본문 처음에 `SET NOCOUNT ON` |
* 규칙 스위트는 내장 스위트를 복사해 루트 안에 `AGENTS.md`를 두었다. SQL 작업은 작업 폴더 최상위가 작업 공간이라 Sql 초안을 `supportFiles`로 최상위에 넣었다.

```bash
dotnet run --project eval/PellyCoder.Eval -- [--suite <규칙 스위트>] --config <pelly.json: llm.model=qwen3.6:35b, sql 허용 목록> --repeat 3 --out <폴더>
dotnet run --project eval/PellyCoder.Eval -- compare <규칙 없음 summary.json> <규칙 있음 summary.json>
```

### 2.1 성공 수가 바뀐 작업

| 작업 | 규칙 없음 | 규칙 있음 | 요청 |
| :--- | :--- | :--- | :--- |
| cs-modern-002 | 0/3 | 1/3 | 환불액을 10원 단위로 반올림 |
| cs-modern-003 | 0/3 | 1/3 | 사은품을 일반 상품 뒤로 정렬 |

* 두 작업 모두 규칙 내용(주석 언어·동기 대기·Dapper·`NOCOUNT`)과 관계가 없다. 프롬프트에 규칙 몇 줄이 더해져 경계에 있던 작업의 출력이 흔들린 것으로 본다. 두 작업은 M3b 기준선에서도 불안정했다(cs-modern-003 2/3, [m3b-baseline.md](m3b-baseline.md)).

### 2.2 규칙이 실제로 들어간 정도와 지켜진 정도

* **들어간 규칙:** C# 실행 90회 모두에 규칙이 들어갔다(cs-legacy 평균 1.28개, cs-modern 2.25개). SQL은 60회 중 48회(프로시저 작업만, 함수·뷰는 `procedure` 태그가 맞지 않음). 예산 초과로 빠진 규칙은 없다.
* **forbid 위반:** 0회(`RULE` 오류 코드 0건). 규칙이 없을 때도 모델이 `.Result`/`.Wait()`를 추가한 적이 없다.
* **추가된 주석(종료 코드 0 실행의 마지막 패치 기준):**

  | 범주 | 규칙 없음 | 규칙 있음 |
  | :--- | :--- | :--- |
  | cs-legacy | 3개 (한국어 100%) | 24개 (한국어 100%) |
  | cs-modern | 6개 (한국어 100%) | 13개 (한국어 100%) |
  | sql | 0개 | 0개 |

  규칙이 없어도 주석은 이미 모두 한국어였다(코드와 요청이 한국어라서). 대신 "주석은 한국어로" 규칙을 넣자 **주석 수가 2~8배 늘었다.** 규칙을 "주석을 달라"로 읽은 것으로 보인다. diff가 커지는 부수 효과다.

## 3. 해석

1. **외부 코퍼스에서는 규칙 효과를 성공률로 잴 수 없다.** 차이 +1.3%p는 규칙과 무관한 두 작업의 흔들림이다. 이 벤치마크 작업은 규칙을 지켜야 통과하는 판정이 없고, 초안 규칙(주석 언어·동기 대기 금지)은 모델이 규칙 없이도 이미 지키고 있었다.
2. **규칙은 해를 끼치지 않았다.** 불변 조건 위반 0건, 범주 감소 없음. 비용은 실행당 입력 약 21토큰과 작업 시간 중위값 +0.22초다.
3. **부수 효과:** `[*] 주석은 한국어로 작성한다`는 주석을 늘린다. 현장에서 주석이 늘어나는 것이 싫으면 문구를 "주석을 쓸 때는 한국어로 작성한다"로 바꾸는 것을 검토한다(이 측정에서는 시험하지 않았다).
4. **폐쇄망 측정에 필요한 것:** PRD §12.6의 "+5%p"를 의미 있게 판정하려면 실제 코드베이스의 관례 중 **모델이 기본으로는 지키지 않는 것**을 규칙으로 두고, 그 관례를 지켜야 통과하는 작업(`mustContain`·`mustNotContain` 판정)을 세트에 더해야 한다. 지금 세트로는 현장에서도 같은 결과가 나올 가능성이 크다.
