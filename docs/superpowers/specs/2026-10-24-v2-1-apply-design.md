# V2-1 작업 명세 파일과 순차 실행 (`pelly apply`) 설계

작성 2026-10-24. 상태: 사람 결정 반영(§9), 구현 시작 승인. 설계 검토(빌더 확인) 반영. 사람은 「질문 없이 바로 설계」를 골랐다. 아래에서 「Claude 결정」으로 표시한 것은 사람이 아직 확인하지 않은 판단이다.

근거 문서:

- [docs/s6-planning-probe.md](../../s6-planning-probe.md) — 모델의 작업 분해 측정
- [docs/s8-semantic-load.md](../../s8-semantic-load.md) — Roslyn 의미 분석 불러오기와 호출부 찾기

## 1. 왜 하는가

v1은 한 번에 파일 하나의 메서드 하나만 고친다. 실제 변경 요청은 여러 곳에 걸친다. 예를 들면 C#과 저장 프로시저를 함께 바꾸거나, 인터페이스의 반환 형식을 바꾸고 구현과 호출부를 따라 고치는 경우다. 지금 사람은 이것을 v1 명령 여러 번으로 쪼개 직접 순서를 지켜 돌린다. 시그니처 변경은 아예 할 수 없다. 멤버 모양 검사가 막고, 대상 프로젝트만 빌드하기 때문이다.

V2-1은 v1의 「한 작업 = 한 멤버」 단위를 그대로 두고, 사람이 쓴 작업 목록을 순서대로 실행한다. 시그니처 변경은 「작업 그룹」으로 묶어 그룹 끝에서 한 번에 빌드 검증한다. 실행 기록은 명세 파일 자체에 남아 폐쇄망의 감사 추적과 코드 리뷰 자료가 된다.

측정으로 정해진 것 둘:
- **작업 분해와 명세 작성은 사람이 한다.** S6에서 모델(생각 켬)은 다중 작업 분해 75%로 「부분」 판정이었다. 시그니처 변경 범주는 5/15였다. 대상이 맞아도 지시 문구가 틀리거나 모호한 것이 표본 10개 중 2~5개 있었다. PRD §12.7의 「모델이 스스로 작업을 분해하지 않는다」는 그대로 둔다.
- **호출부·구현체 찾기는 모델이 아니라 Roslyn 심볼로 한다.** S8에서 심볼 방식은 범주 A 3/3, 이름 방식은 2/3이었다. 이름 방식은 같은 이름의 다른 인터페이스에 속았다. 이것을 명세 검사(`spec check`)의 「빠진 영향 대상」 경고로 쓴다.

## 2. 목표 / 비목표 / 실패 조건

**목표**
- `changes/<id>.md` 명세를 문법대로 읽어, 작업을 위에서부터 하나씩 v1 FSM으로 실행한다.
- 작업 그룹으로 인터페이스·DTO·메서드 시그니처 변경과 그 구현·호출부 수정을 한 단위로 검증·롤백한다.
- `pelly spec check`로 실행 전에 명세 오류와 빠진 영향 대상을 알린다.
- 중단 뒤 이어서 하기(`--resume`), 실패해도 계속하기(`--continue`), 끝에 한 번에 승인하기(`--review-at-end`)를 지원한다.
- 명세 파일에 작업별 실행 기록을 남기고, 끝나면 보관 폴더로 옮긴다.

**비목표**
- **모델이 명세를 쓰거나 작업을 나누는 것**(`pelly spec draft`). S6 결과는 일부 범주(C#+SQL 동시 변경, 한 곳 변경)에서 가능성을 보였다. 그러나 PRD는 그대로 두었고 채택은 사람이 정할 일이라, 이 설계에 넣지 않는다(§9 미결).
- 탐색이 찾은 빠진 대상을 작업으로 자동 추가하는 것. 검사는 알리기만 하고, 추가는 사람이 한다. 탐색은 「영향받을 수 있는 곳」을 내고, 고칠 곳은 사람이 고른다(S8 §8 한계).
- 작업 병렬 실행, 작업 순서 자동 변경, 새 파일 생성, 여러 저장소에 걸친 명세.
- 수용 기준(AC)의 테스트 실행. AC의 `test:` 참조는 문법과 존재만 검사한다. 실행은 V2-2의 일이다.
- SQL 작업을 그룹에 넣는 것. SQL 객체 변경은 C# 빌드를 깨지 않는다. S6 범주 B(C#+SQL 동시 변경)는 그룹 없이 15/15였다.

**실패 조건** (돌아가도 실패인 경우)
- 그룹 검증이 실패했는데 일부 파일만 되돌아가 저장소가 빌드되지 않는 상태로 남는다.
- 명세 파일의 체크 표시가 실제 파일 상태와 어긋난다. 예를 들어 롤백된 작업이 `[x]`로 남는다.
- pelly 밖에서 바뀐 파일을 롤백이 덮어쓴다(v1의 「바깥 변경은 덮어쓰지 않음」 불변 조건).
- 검사가 영향 대상을 놓쳤는데, 의미 분석이 실패해 이름 기준으로 대신한 사실을 알리지 않는다.

## 3. 제약

- .NET 10. 기존 구조(`PellyCoder.Core`, `PellyCoder.Cli`, Spectre.Console.Cli)를 쓴다. 새 구성 요소는 PRD의 `Specs/ChangeSpecParser.cs`, `Specs/SpecRunner.cs`, `Specs/SpecArchiver.cs`, `Commands/ApplyCommand.cs`, `Commands/SpecCommand.cs`를 기본으로 한다.
- 작업 하나는 v1과 같은 FSM, 같은 컨텍스트 예산·재시도·규칙(V2-3)·검증 단계를 쓴다. 모델 호출 방식은 바꾸지 않는다.
- 프롬프트는 그룹 작업에서만 한 줄 바꾼다(§6). v1 단일 실행(`pelly cs`·`pelly sql`)의 프롬프트·동작·벤치마크 수치는 바뀌면 안 된다.
- 폐쇄망·완전 오프라인 동작과 self-contained 배포를 유지한다.
- 의미 분석(`MSBuildWorkspace`)을 쓰면 Roslyn 보조 프로세스 폴더 둘(`BuildHost-net472`, `BuildHost-netcore`)을 exe 옆에 함께 배포해야 한다. 단일 exe에 묶으면 동작하지 않는다(S8 실측). 반입 zip의 파일 목록이 바뀐다.
- Windows가 주 대상이다. 레거시 .NET Framework 프로젝트의 의미 분석은 Visual Studio MSBuild가 있어야 된다. macOS 개발 PC에서는 레거시 의미 분석이 「조용히 반쯤 실패」한다(S8: 해석률 2.8%).
- 작업 수 상한 20(PRD).

## 4. 명세 파일

형식은 PRD §12.3 그대로다. 정해진 문법만 파싱하고, 모델은 명세를 해석하지 않는다.

```
- [ ] <ID> <cs|sql> <파일>[#심볼] <요청> [(AC 참조)] [[G<n>]]
```

S6에서 쓴 파서·정답 형식과 같은 문법이다. S6 정답 12건이 이 문법으로 쓰여 있어 그대로 벤치마크 재료가 된다(§8).

추가로 정하는 규칙(Claude 결정):
- **작업 줄 모양인데 문법에 안 맞는 줄은 오류다.** 들여쓰기, `*`·번호 목록, 대소문자가 다른 `[X]` 같은 것이다. 조용히 건너뛰면 사람이 쓴 작업이 실행되지 않은 채 「완료」가 된다. S6 최종 리뷰에서 실제로 나온 결함이다.
- `[G<n>]` 표시 뒤에 구두점이 붙어도 그룹으로 읽는다(S6 미룬 결함 M1).
- 같은 그룹의 작업은 목록에서 연속해야 한다. 사이에 다른 작업이 끼면 오류다. 그룹 끝에 한 번 검증하므로, 그 사이에 실행된 다른 작업의 결과가 검증 범위에 섞이지 않게 한다.
- 그룹에는 `cs` 작업만 넣는다.
- 경로는 apply 작업 공간 루트 기준 상대 경로이고, `\`와 `/`를 모두 받는다.
- **apply 작업 공간 루트는 명세 파일 하나로 정한다(Claude 결정).** v1과 같은 규칙(가장 가까운 상위의 `.git`·`.svn`·`*.sln`)을 명세 파일 위치에 적용한다.
  - v1은 파일마다 루트를 따로 찾는다. 그러면 한 명세의 작업이 서로 다른 `.pelly`·잠금·규칙 파일에 흩어질 수 있다. 실제로 코퍼스의 Legacy·Modern·Sql은 루트가 다르다.
  - apply는 모든 작업에 이 루트 하나를 쓴다. `.pelly`, 잠금, `AGENTS.md` 규칙, 백업, 실행 기록이 모두 여기 매인다.
  - 작업 대상이 이 루트 밖이면 오류다.
  - FSM이 받은 루트를 그대로 쓰도록 바꾼다. 빌드 대상 프로젝트는 지금처럼 파일마다 가장 가까운 `.csproj`다.
- 실행 기록 주석 `<!-- run: <run-id> -->`는 pelly만 쓴다. 사람이 지워도 체크 표시가 있으면 완료로 본다.

## 5. `pelly spec` 명령

- `pelly spec new <id>`: 빈 템플릿을 `changes/<id>.md`로 만든다. 이미 있으면 거부한다.
- `pelly spec check <파일> [--impact]`: 다음을 검사한다.
  1. **문법:** 작업 줄 모양인데 틀린 줄, 중복 ID, 그룹 연속성, 그룹 안의 `sql` 작업, 작업 수 상한.
  2. **대상 존재:**
     - 파일이 있는지 본다.
     - `cs`는 심볼이 있는지 v1 LOCATE와 같은 규칙(`MemberLocator`)으로 확인한다. 후보가 여럿이면 오류다.
     - `sql`은 파일 안 객체를 확인한다.
  3. **AC 참조:** `(AC1)`이 목표 절에 정의된 AC인지 본다. `test:` 참조의 테스트 메서드가 있는지는 구문으로만 확인한다.
  4. **지시 문구 안 이름(경고):**
     - 요청 문구에 나온 식별자 꼴의 낱말을 대상 파일과 같은 프로젝트의 선언 이름과 대조한다. 백틱으로 감싼 것, `PascalCase`, `_camel`, `dbo.이름`이 대상이다.
     - 없으면 경고한다. S6 사람 확인에서 없는 컬럼 이름(`CancelTime`) 같은 지시가 기계 판정을 통과했다.
     - 사람이 쓰는 명세라 오류가 아니라 경고다.
  5. **빠진 영향 대상(경고):** 그룹이 있으면, 또는 `--impact`면 모든 `cs` 작업에 대해 한다.
     - 대상 멤버의 구현·재정의와 그것을 부르는 멤버를 심볼로 찾는다.
     - 명세의 작업에 없는 곳을 목록으로 경고한다.
     - 찾는 방법은 S8 `SemanticCallerFinder`를 바탕으로 한다. 제품 코드로 옮기며 테스트한다.
     - S8 탐색은 아래쪽(구현·재정의·호출부)만 찾는다. 제품에서는 위쪽도 찾는다. 대상이 인터페이스·기반 멤버를 구현하거나 재정의하면 그 멤버와, 그 멤버의 다른 구현·호출부까지 포함한다(Claude 결정). 클래스 메서드의 시그니처를 바꾸면 인터페이스도 따라 바뀌어야 하기 때문이다.
     - 의미 분석이 안 되는 환경이면 이름 기준 탐색으로 대신한다. 이때 결과에 「이름 기준(부정확): 의미 분석 실패 — <유형>」을 반드시 표시한다. 「안 되는 환경」은 S8 판정 기준을 쓴다: 호출 해석률 99% 미만, 복원된 프로젝트의 컴파일 오류, 빌드 도구 없음.
- 종료 코드: 오류가 하나라도 있으면 4, 경고만 있으면 0. 경고는 화면과 실행 기록에 남는다.

## 6. `pelly apply` 실행

`pelly apply changes/<id>.md [--continue] [--resume] [--review-at-end] [--yes] [--dry-run] [--verbose]`

**시작**
1. `spec check`를 먼저 돈다. 오류면 아무것도 바꾸지 않고 종료 코드 4로 끝난다. 경고가 있으면 대화형에서는 보여 주고 계속할지 묻는다. `--yes`면 기록만 하고 계속한다.
2. 작업 공간 잠금을 apply 전체 동안 한 번만 잡는다. 지금은 v1 실행마다 잠금을 잡는다. 이 설계는 FSM이 이미 잡힌 잠금을 받아 쓰도록 바꾼다(Claude 결정). 작업 사이에 다른 pelly가 끼어들지 못하게 하기 위해서다.
3. 명세 `status`를 `in-progress`로 바꾼다. apply 실행 ID(`apply-<run-id 형식>`)를 만든다.

**작업 하나**
- v1 FSM으로 실행한다. 앞 작업의 결과는 이미 파일에 있으므로 SLICE는 바뀐 코드로 컨텍스트를 만든다.
- 성공하면 체크 표시를 `[x]`로 바꾸고 작업의 run-id를 붙인다.
- 명세 파일은 다음과 같이 고친다.
  - 쓰기 전에 읽었던 내용의 해시와 비교한다. 다르면 쓰지 않고 멈춘다(종료 4, 「명세 파일이 실행 중에 바뀌었습니다」).
  - 임시 파일에 쓴 뒤 바꿔 끼운다.
  - 원래 인코딩·줄 끝·BOM을 유지한다.

**작업 그룹** (시그니처 변경)

그룹에서 허용하는 변경(Claude 결정):
- 대상 멤버 자신의 반환 형식·매개변수·제한자·특성 변경
- 대상 멤버의 **이름 변경**. S6 a3(`GetOrder` → `FindOrder`)가 벤치마크에 있다.
- 그 밖의 멤버 변경·삭제, `using` 삭제는 그대로 막는다.
- **타입에 새 public 멤버를 더하는 것은 V2-1 범위 밖이다.** 예를 들어 DTO에 속성을 추가하는 것이다. 그것은 「멤버 수정」이 아니라 「멤버 생성」이라 대상 지정·멤버 모양 검사·LOCATE를 새로 설계해야 한다. V2-1의 DTO 변경은 기존 멤버의 형식 변경만이다.

실행 순서:
1. **기준 빌드.** 그룹 첫 작업 전에 영향 범위의 기준 빌드를 잡는다(Claude 결정).
   - 영향 범위는 그룹 파일이 속한 프로젝트들과, 작업 공간 안에서 그 프로젝트를 (간접 포함) 참조하는 프로젝트들이다. 참조 관계는 `.csproj`의 `ProjectReference`를 읽어 구한다.
   - 솔루션 전체가 아닌 이유는 그룹과 무관하게 깨지거나 복원되지 않은 프로젝트 하나 때문에 검증이 막히지 않게 하려는 것이다. 그룹 밖 호출부가 깨지는 것은 참조 프로젝트까지 빌드해서 잡는다. v1은 대상 프로젝트 하나만 빌드한다.
   - 프로젝트마다 형식에 맞는 빌드 도구를 쓴다(v1 `BuildToolResolver`).
2. **그룹 안 작업 실행.**
   - 검증은 구문 검사와 규칙 검사(V2-3)까지만 하고 빌드는 미룬다.
   - 멤버 모양 검사는 위의 허용 변경만 받는다. 이름 변경은 「대상 멤버가 사라지고 같은 자리에 같은 종류의 멤버 하나가 생긴 것」으로 짝짓는다.
     - (2026-10-25 구현 보정) 후보는 새로 생긴 같은 종류·같은 형식의 멤버 중 대상과 접근 수준이 같은 것을 먼저 본다. 그래서 public 대상 옆에 새로 생긴 private 도우미는 대상이 될 수 없다. 그중 이름이 같은 하나, 없으면 같은 자리의 하나를 고른다. 자리는 수정 앞뒤에 모두 있는 멤버만 세므로 끼워 넣은 도우미가 자리를 밀지 않는다.
     - private 대상 옆에 private 도우미가 생겨 자리로 가를 수 없으면 시그니처가 그대로인 쪽(순수한 이름 변경)을 고른다. 그래도 가를 수 없으면 거절한다. 도우미를 대상으로 잘못 짝지으면 대상 표시가 틀어져 그룹 빌드 뒤 귀속이 엉뚱한 멤버를 가리키기 때문이다.
   - 대상 추적은 이름이 아니라 위치(파일 안 멤버 순서)로 한다. 이름이 바뀐 뒤 재시도나 그룹 재실행에서도 대상을 다시 찾아야 하기 때문이다. 지금 v1 FSM은 이름으로 다시 찾아, 이름을 바꾼 패치 뒤에 대상을 잃는다.
   - 본문 없는 멤버(인터페이스·추상 멤버)는 지금 LOCATE·SLICE·모양 검사가 이미 다룬다(설계 검토 확인). E2E 테스트가 없으므로 구현에서 더한다.
   - 그룹 작업의 시스템 프롬프트는 v1 규칙 5(「멤버의 시그니처·특성·접근 제한자를 바꾸지 마라」)만 그룹용 문장으로 바꾼다(Claude 결정): 「요청이 정한 만큼만 이 멤버의 시그니처를 바꾸고, 다른 멤버는 바꾸지 마라」. 길이는 v1과 비슷하게 두어 시스템 예산(450)을 지킨다. 그룹용 프롬프트는 별도 캐시 접두가 된다. 정확한 문구는 구현 때 재생 실험으로 고른다.
3. **그룹 빌드.** 그룹의 마지막 작업 뒤 영향 범위를 한 번 빌드한다. 기준 빌드에 없던 새 오류가 없으면 통과다.
4. **새 오류의 귀속(Claude 결정).** 새 오류는 줄 번호로 그 오류를 감싼 멤버를 찾는다.
   - 그 멤버가 그룹 작업의 대상이면, 그 작업에 v1과 같은 자가 교정 피드백을 주고 그 작업만 다시 실행한다. 재시도는 그룹 전체에 `retry.max`번이다. 그 뒤 다시 그룹 빌드를 한다.
   - 그 멤버가 어떤 작업의 대상도 아니면 고치려 하지 않는다. 그룹 작업의 대상 파일 안이어도 마찬가지다. 그룹 전체를 롤백하고 실패로 끝낸다. 메시지에 그 파일·멤버를 「명세에 빠진 영향 대상」으로 적는다. 다시 실행해도 모양 검사가 그 멤버를 못 건드리게 하므로 재시도는 소용없다. `spec check`의 영향 경고를 무시했을 때의 결말이다.
   - 멤버 밖(필드 초기화 등)의 오류도 같은 처리다.
5. **빌드로 검증할 수 없을 때(Claude 결정).** 그룹을 실패로 끝낸다(종료 4, 「그룹 빌드 검증 불가」). 구문 검사만으로 통과시키지 않는다. 예는 다음과 같다.
   - Windows가 아닌데 레거시 프로젝트가 영향 범위에 있다.
   - 기준 빌드에 컴파일러 오류가 아닌 오류(NETSDK·MSB·NU)가 있다.
   - 빌드 도구가 없다.
   - (2026-10-25 추가) 영향 범위를 확정할 수 없다. 모두 편집 전에 종료 4로 끝나고 메시지에 원인을 적는다.
     - 목록을 읽을 수 없거나 속성을 읽을 수 없는 폴더가 있다.
     - 링크·정션 폴더가 작업 공간 밖을 가리키거나 대상을 알 수 없다. 작업 공간 안을 가리키는 링크는 건너뛴다.
     - 범위 안 프로젝트의 `ProjectReference`가 없는 `.csproj`를 가리킨다. 범위 밖 프로젝트의 깨진 참조는 변경된 프로젝트를 참조할 수 없으므로 보지 않는다.

   그룹 범위 탐색은 `packages` 폴더를, 하위 폴더가 하나 이상이고 모든 하위 폴더에 `.nupkg`가 있을 때(packages.config 복원 폴더)만 건너뛴다. 틀린 짐작이 범위를 넓힐 뿐 좁히지 않게 하려는 것이다. v1 탐색(DTO, 테스트 프로젝트 찾기)은 계속 `packages`를 늘 건너뛴다.

   그룹 메시지는 `그룹 빌드 검증 불가 (<프로젝트>): <원인>` 꼴이다. 시간 초과는 `build.timeoutSeconds`의 초를 적고, 비컴파일러 오류는 「빌드 검증을 할 수 없습니다」를 되풀이하지 않고 `<코드> <메시지>. <조치>`로 적는다. v1 문구(v1 설계 §8.9)는 그대로다. 그룹 빌드의 상대 경로 진단은 그 프로젝트 폴더 기준으로 푼다.

   시그니처 변경은 빌드가 유일한 판정이라, 판정 없이 통과시키면 §2 실패 조건이 된다. 따라서 레거시 그룹의 E2E 측정은 Windows에서만 한다.
6. **그룹 롤백.** 그룹이 바꾼 모든 파일을 그룹 시작 전 바이트로 되돌린다.
   - pelly 밖에서 바뀐 파일은 덮어쓰지 않는다. 그런 파일이 있으면 되돌리지 못한 파일 목록을 남기고 종료 4로 끝난다(v1 불변 조건과 같음).
   - v1 롤백은 FSM 안에서 한 실행의 파일 하나만 다룬다. 그래서 그룹 롤백은 apply 수준에서 만든다. 파일별 시작 전 바이트와 「pelly가 마지막으로 쓴 내용」을 apply가 보관한다.
7. **체크 표시.** 그룹의 체크 표시는 그룹이 통과한 뒤에 한꺼번에 `[x]`로 바꾼다.

FSM에 필요한 변경(설계 검토 확인):
- 이미 잡힌 잠금과 정해진 작업 공간 루트를 받는다.
- 빌드를 미루는 검증 모드가 필요하다.
- REVIEW를 미루는 모드가 필요하다.
- 그룹 재실행 때 처음부터 줄 자가 교정 피드백 입력이 필요하다.
- 실행 결과에 바꾼 파일과 그 마지막 내용을 돌려준다. 지금 `RunAsync`는 종료 코드만 돌려준다.
- v1 단일 실행의 동작과 기존 테스트는 그대로여야 한다.

**승인(REVIEW)**
- 기본은 작업마다 diff를 승인받는다. 그룹은 그룹 빌드 통과 뒤 그룹 전체 diff를 한 번에 승인받는다(Claude 결정). 그룹 중간 상태는 빌드가 안 되는 상태라 하나씩 승인하는 것이 의미가 없다.
- `--review-at-end`: 모든 작업이 끝난 뒤 전체 diff를 한 번 승인받는다. 거부하면 apply가 바꾼 모든 파일을 시작 전으로 되돌리고, 명세의 체크 표시도 되돌린다.
- `--yes`: 승인을 묻지 않는다(v1과 같음).

**실패와 이어서 하기**
- 실패하면 그 작업(또는 그룹)은 롤백되고 apply는 멈춘다. 종료 코드는 실패한 작업의 v1 종료 코드다.
- `--continue`: 실패한 작업은 `[ ]`로 두고 실패 표시 주석(`<!-- failed: <run-id> <실패 종류> -->`)을 붙인 뒤 다음 작업으로 간다. 다음과 같은 경우는 계속해도 소용없으므로 멈춘다(Claude 결정).
  - 실패한 작업이 그룹이면, 그 뒤 작업 중 그룹 파일을 대상으로 하는 것이 있을 때
  - 서버 연결이나 환경 오류(종료 4)일 때
  - 끝의 종료 코드는 실패가 하나라도 있으면 1이다.
- `--resume`: `[ ]`인 첫 작업부터 다시 시작한다. 그룹 중간에서 멈춘 경우는 그룹 첫 작업부터 다시 한다. 그룹은 롤백되어 있기 때문이다.
- 취소(Ctrl+C): 진행 중인 작업(또는 그룹)을 롤백하고, 완료된 작업의 체크 표시는 유지한다.

**끝**
- 모든 작업이 `[x]`면 `status: done`으로 바꾸고 `changes/archive/<yyyy-MM-dd>-<id>.md`로 옮긴다. 같은 이름이 있으면 `-2`, `-3`을 붙인다.
- `--dry-run`: 검사와 첫 작업의 EDIT까지만 하고 파일을 바꾸지 않는다(v1 `--dry-run`과 같은 뜻). 명세 파일도 바꾸지 않는다.

**기록**
- `.pelly/runs/<apply-id>/`에 apply 요약을 둔다. 요약에는 작업별 run-id·결과·시간, 그룹 빌드 결과, `spec check` 경고가 들어간다.
- 작업별 기록은 v1처럼 각 run-id 폴더에 둔다.
- `pelly report`는 apply 요약을 읽어 명세 완료율(§12.6 KPI)을 셀 수 있어야 한다.

## 7. 종료 코드

v1 코드를 그대로 쓴다(0 성공, 1 검증 실패, 2 사용자 취소·거부, 3 대상 특정 실패, 4 환경·입력 오류, 5 안전장치 거부). 명세 오류와 명세 파일 바깥 변경은 4다. `--continue`로 끝까지 갔는데 실패가 있으면 1이다.

## 8. 검증 방법

- **단위·통합 테스트:**
  - 명세 파서(S6 파서·Review Focus의 틀린 줄 사례 포함)
  - 그룹 연속성
  - 명세 파일 원자적 갱신과 바깥 변경 감지
  - 그룹 롤백(바깥 변경 파일 포함)
  - `--resume`·`--continue`·`--review-at-end` 상태 전이
  - 영향 탐색: S8의 a3 이름 혼동 사례 회귀, 의미 분석 실패 시 「이름 기준」 표시
- **E2E 벤치마크:**
  - S6 정답 12건을 그대로 명세 파일로 쓴다. 필요하면 머리말 형식만 맞춘다.
  - 코퍼스의 명세는 `eval/corpus` 루트를 apply 작업 공간으로 쓴다. 그래야 Legacy·Modern·Sql을 잇는 사례(b1, b3)가 한 루트에 든다. 그 루트를 표시하는 방법(빈 `.sln` 또는 표시 파일)은 구현에서 정한다.
  - 레거시 그룹 사례(a3)는 Windows에서만 잰다(§6 그룹 5).
  - 코퍼스(`eval/corpus`)에서 현장 모델 파일(qwen3.6:35b GGUF)로 `pelly apply --yes`를 반복한다.
  - 명세 완료율(PRD §12.6 목표 ≥ 70%)과 그룹 빌드 통과율을 잰다.
  - 작업 1~2개짜리 사례가 섞여 있다. 그래서 「작업 3~8개 규모」 KPI 분모와는 따로 보고한다.
- **의미 분석 배포:** 반입 zip에 보조 프로세스 폴더가 들어갔는지와 `pelly doctor`가 의미 분석 가능 여부를 보고하는지 확인한다. 현장 측정은 S8 현장 측정과 함께 한다.

## 9. 사람 결정 (2026-10-24)

- **`pelly spec draft`(모델 명세 초안 + 검사 + 사람 승인)는 V2-1 뒤에 둔다.** V2-1에는 넣지 않는다. S6 근거: C#+SQL 동시 변경·한 곳 변경 15/15, 시그니처 변경 5/15, 지시 문구 실패 표본 2~5/10.
- **v2 진입 조건(M4 현장 결과) 전에 V2-1 구현을 시작한다.** 현장 검증은 V2-1 구현 뒤 반입 때 함께 한다(PRD §12.2 「각 단계가 끝날 때마다 폐쇄망으로 반입해 검증」).

## 10. 만드는 사람에게 맡기는 것

- FSM이 이미 잡힌 잠금을 받는 방식과 「빌드를 미루는 검증 모드」의 구현 방식. v1 단일 실행의 동작과 기존 테스트는 바뀌면 안 된다.
- 지시 문구 안 이름 대조의 낱말 추출 규칙. 경고만 하므로 보수적으로 잡되, 규칙은 한 곳에 두고 테스트한다.
- 영향 탐색의 의미 분석 결과를 한 apply 안에서 재사용할지(S8: 처음 열기 약 5초).
- 화면 표시(진행률, 그룹 단위 표시)의 세부 모양.
