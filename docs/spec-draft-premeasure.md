## 1. 요약

- 제품 경로(arm P: `DraftModel` + `SpecDrafter`, 의미 기반 영향 탐색 켬, SQL 영향 탐색 끔)의 「초안으로 쓸 만함」은 **45/60 (75%)** 로 S6 arm B(45/60)와 같다. 판정 표(S6 §7)로는 「부분(Partial)」이다.
- **범주 A(전파)는 9/15 (60%)** 로 S6 arm B 5/15 (33%)보다 높다. 범주 A 평균 재현율은 P 0.92(같은 실행의 모델 답만 채점하면 0.85), S6 arm B 0.81이다. 오른 몫은 Modern 사례(a1·a2)에서 영향 탐색이 더한 줄이다. Legacy 사례 a3는 이 맥에서 의미 분석이 불가해(`MsBuildNotFound`) 한 줄도 더하지 못했고 0/5다.
- **범주 D(한 곳 변경)는 12/15 (80%)** 로 S6 arm B 15/15보다 낮다. 모델 답만으로는 15/15였는데, d1에서 모델이 한 줄짜리 동작 변경에 `[G1]`을 달아 영향 탐색이 인터페이스·컨트롤러·테스트를 더했다(3회 모두 범위 밖 작업으로 탈락).
- 버린 줄 0, 제품 파서는 받고 S6 파서는 거부한 줄 0 — 파서 차이는 이번 채점에 영향이 없었다(5절).
- 기계 판정 「쓸 만함」 45회 중 12회는 제품 검사기(`SpecChecker`)에 오류가 있다(`SqlInGroup` 9회, 영향 줄을 더해 상한 20을 넘은 `TooManyTasks` 3회). 이 초안은 그대로는 `pelly apply`가 실행하지 않는다(6절).

## 5. 버린 줄과 파서 차이

| 항목 | 값 |
| :--- | ---: |
| 버린 줄(작업 줄 모양인데 제품 문법 밖) | **0** (60회 전체) |
| 제품 파서가 받았지만 S6 파서가 거부한 최종 줄 | **0** |
| 모델 답에 작업 줄이 하나도 없어 실패(종료 1) | 0 |
| 영향 탐색이 더한 줄 | **82** (60회 중 21회에서) |

영향 탐색이 더한 줄은 사례별로 a1 4, a2 17, b3 9, c1 45, d1 7이다(3절 표).

**파서 관대함(설계 §4.3):** 제품은 문법 밖 줄을 버리고 나머지를 받는다. S6 채점기는 한 줄이라도 틀리면 그 반복을 파싱 실패로 친다. 그래서 제품 경로는 S6가 실패로 칠 반복을 초안으로 받아들일 수 있다. 이번 60회는 버린 줄이 0이고, 최종 줄 중 S6 파서가 거부한 줄도 0이라 **이 차이가 채점에 준 영향은 없다**(파싱 실패 0). 영향 탐색이 더한 줄(`… (영향 탐색으로 추가) [G1]`)도 S6 파서가 그룹까지 읽었다.

## 6. 기계 판정이 보지 않는 것: 제품 검사 오류

S6 채점기는 대상만 본다. 같은 초안을 제품 검사기로 보면 60회 중 15회에 오류가 있고, 그중 12회는 기계 판정 「쓸 만함」이다.

| 오류 | 사례(반복) | 내용 |
| :--- | :--- | :--- |
| `SqlInGroup` | b1(2회), b2(5회), d3(3회) | 모델이 sql 작업에 `[G1]`을 달았다. 제품 문법은 sql 작업의 그룹을 금한다. 오류가 있으면 영향 탐색도 건너뛴다 |
| `TooManyTasks` | c1 #2·#3·#5 | 모델 6줄 + 영향 탐색 15줄 = 21줄로 작업 수 상한 20을 넘었다. 영향 줄을 더한 뒤의 재검사에서 난 오류다 |
| `SymbolRequired` | c1(2회) | `cs` 작업에 `#멤버`가 없다(S6 채점에서도 지어낸 대상) |
| `SymbolNotFound` | b2 #1 | 없는 속성 `OrderDto#ProductName` |

「쓸 만함」이면서 오류가 있는 12회: b1 #1·#4, b2 #2~#5, d3 #1·#3·#5(`SqlInGroup`), c1 #2·#3·#5(`TooManyTasks`). 오류 코드는 원문의 최종 줄을 `pelly spec check`로 다시 검사해 확인했다. 오류가 있는 초안도 사람 승인 후 쓰이지만 `pelly apply`는 실행하지 않는다(설계 §4.3 6단계).

## 7. 읽는 법과 한계

- **표본이 작다.** 사례 12개 × 5회, 로컬 맥 1대. S6 재측정에서도 같은 조건의 쓸 만함이 A 33/60 → 29/60으로 흔들렸다(S6 §7.1). 범주별 몇 회 차이는 모델 편차 안일 수 있다. 「답만」 열이 같은 실행의 기준선이다: 영향 줄은 범주 A를 6/15 → 9/15로 올리고 범주 D를 15/15 → 12/15로 내렸다.
- **영향 탐색의 출발점이 그룹이다(설계 §4.4).** 모델은 시그니처를 바꾸지 않는 한 줄 변경(d1)에도, sql 작업(b1·b2·d3)에도 `[G1]`을 단다. 앞의 경우는 과분해(d1 3회 탈락), 뒤의 경우는 검사 오류로 영향 탐색이 건너뛰어진다. 동작만 바꾸는 그룹 작업의 호출부를 더하는 것도 과하다: c1(연결 시간 제한)에서 영향 탐색이 호출부·인터페이스·테스트 15줄을 더해 작업 수 상한 20을 넘겼다(S6 쓸 만함 판정은 그대로, 정밀도 0.29, 제품 검사는 `TooManyTasks` 오류).
- **Legacy 의미 분석은 재지 못했다.** a3·c2·c3·d2와 b1·b2의 Legacy 쪽은 이름 기준으로 떨어져 줄을 더하지 않았다. 현장 Windows에서는 결과가 다를 수 있다.
- **지시 문구 품질은 채점하지 않았다**(S6 §6.2와 같다). 사람 표본 확인은 하지 않았다.
- **생성자 미색인**(S6 §6.1)은 그대로다. c1의 지어낸 대상 2회는 생성자가 아니라 `#멤버` 누락이다.

## 8. 재현

```
cd spikes/S6-planning/S6Planning
dotnet run -- run --arm P --repeat 5 [--workspace <복사본 경로>]   # eval/corpus를 복사하고 .git 표시·Modern 복원
dotnet run -- score && dotnet run -- report                         # S6 채점기 그대로
dotnet run -- run --arm P --stats                                   # 영향 추가·버린 줄·답만 채점 (results/premeasure-stats.md)
```

원문(`raw/P/…`)과 결과(`results/`)는 S6와 같이 gitignore 대상이라 저장소에 없다.
