# 현장 스위트와 작업 작성

현장 코드로 pelly를 재려면 스위트 폴더를 만듭니다. 절차 전체는 [field-guide.md](field-guide.md)입니다.
템플릿: `field-kit\templates\suite.json`, `field-kit\templates\tasks\*.yaml`. 복사해서 고치십시오.

```text
D:\pelly-field\suite\
  suite.json
  tasks\
    cs-modern-001.yaml
    cs-legacy-001.yaml
    sql-001.yaml
  judges\<루트 이름>\      (선택: 동작 판정 테스트 프로젝트)
```

## 구성 권장

외부 측정(PRD §2.1)과 같은 규모를 권장합니다. 그래야 결과를 외부 기준과 비교할 수 있습니다.

| 범주 | 건수 |
| :--- | ---: |
| C# 레거시 (`cs-legacy`) | 18 |
| C# 모던 (`cs-modern`) | 12 |
| SQL (`sql`) | 20 |
| 합계 | 50 |

현장 코드에서 이 비율이 어렵다면 실제 건수로 만들고, 범주별 건수를 `field-results.md`에 적으십시오.
한 범주가 0건이면 `validate`가 경고합니다.

## suite.json

```json
{
  "formatVersion": 1,
  "name": "field",
  "roots": [
    { "name": "Modern", "path": "D:\\src\\<현대 SDK 저장소>" }
  ],
  "supportFiles": [],
  "resultsDir": "D:\\pelly-field\\results"
}
```

JSON 안의 `\`는 두 번 씁니다(`\\`). 모르는 키는 오류입니다(오타가 조용히 무시되지 않게 하기 위해서입니다).

| 키 | 설명 |
| :--- | :--- |
| `formatVersion` | `1`만 읽습니다 |
| `name` | 필수. 빈 문자열 불가 |
| `roots` | 하나 이상. 작업마다 `work\<id>\<이름>\`으로 복사되는 원본 폴더 |
| `roots[].name` | 영문·숫자·`_`·`-`만. 서로 달라야 함(대소문자 무시). `judges`는 쓸 수 없음 |
| `roots[].path` | 존재하는 폴더. 두 루트가 같은 폴더이거나 한쪽이 다른 쪽 안에 있으면 오류 |
| `roots[].exclude` | (선택) 복사에서 뺄 폴더 **이름**. 경로가 아니고 어느 깊이에서든, 대소문자 무시. `bin`·`obj`·`.pelly`·`TestResults`·`.git`·`.vs`는 항상 뺍니다 |
| `supportFiles` | (선택) 작업 폴더 맨 위(`work\<id>\`)에 파일 이름 그대로 복사할 파일. 존재해야 하고 파일 이름이 서로 달라야 함 |
| `resultsDir` | (선택) 기본 출력 폴더의 부모. 기본 `results` |

* 경로는 `suite.json`이 있는 폴더 기준 상대 경로 또는 절대 경로입니다. 공백·한글 경로도 됩니다.
* Windows 드라이브 문자 경로(`D:\\…`)는 Windows 미확인입니다.
* 스위트 오류가 있으면 실행기는 오류를 모두 출력하고 종료 4로 끝납니다.
* Legacy 여부는 루트 이름이 아니라 대상 파일에서 가장 가까운 csproj가 SDK 형식이 아닌지로 정합니다.

### supportFiles 경고

작업 복사본은 루트 폴더만 담습니다. 루트 위 폴더에 있는 빌드 입력(`Directory.Build.props`, `Directory.Packages.props`, `global.json` 등)은 복사되지 않습니다.
`validate`가 `루트 밖 빌드 입력: <파일> — supportFiles에 넣지 않으면 작업 복사본에 없습니다`라고 경고하면, 그 파일이 빌드에 필요한지 봅니다.
필요하면 `supportFiles`에 경로를 넣습니다. 필요 없으면 경고를 무시해도 됩니다(경고는 종료 코드에 영향이 없습니다).
빌드가 복사본에서만 실패하는 작업이 있으면 이 경고부터 보십시오.

## 작업 YAML

`tasks\<id>.yaml` 한 파일이 작업 한 건입니다.

| 필드 | 설명 |
| :--- | :--- |
| `id` | 파일 이름(확장자 제외)과 같아야 합니다. 형식은 아래 「id 규칙」 |
| `kind` | `cs` 또는 `sql` |
| `category` | (선택) Legacy 작업의 앱 종류: `mvc`, `adonet`, `dapper` |
| `file` | `<루트 이름>/<루트 안 경로>`. 구분자는 `/`만 씁니다 (예: `Modern/Api/Services/OrderService.cs`) |
| `method` | `cs`: 대상 메서드 이름 |
| `line` | `cs`: 대상 멤버 안의 줄 번호(1부터). `method`와 `line` 중 **정확히 하나** |
| `object` | `sql`: 대상 객체 이름. 파일에 객체가 여러 개면 필수 |
| `request` | 한국어 요청문. 사용자가 입력하는 그대로 |
| `judge` | 판정 기준 (아래) |

* `cs` 작업: `judge.build: true` 필수, `object`·`sqlCompile` 금지.
* `sql` 작업: `judge.sqlCompile: true` 필수, `method`·`build` 금지. 대상 객체 배치는 정확히 1개여야 합니다.
* `file`을 해석하지 못하면(알 수 없는 루트, 루트 밖을 가리키는 `..`, 없는 파일, `\` 구분자) 그 작업은 실행되지 않고 실패(`Definition`)로 기록됩니다. `validate`가 미리 알려 줍니다.
* 시그니처를 바꾸는 요청(async 전환 등)은 넣지 않습니다. pelly가 막는 것이 의도된 동작입니다.

### id 규칙

형식은 `cs-modern-NNN`, `cs-legacy-NNN`, `sql-NNN`(NNN은 숫자 세 자리)입니다. 다른 형식은 `validate`가 오류로 거절합니다.
**id에 업무 이름이나 시스템 이름을 넣지 마십시오.** 형식이 강제되므로 반출한 결과에는 업무 정보가 남지 않습니다.
요청문과 파일 경로가 반출본에 남는지는 반출 전에 직접 열어 확인하십시오(field-guide.md 9절).

## 판정 선택 지침

판정은 `judge` 아래에 둡니다. **판정이 하나도 없으면 아무 수정이나 통과하므로** `validate`가 오류로 거절합니다(빌드·컴파일만으로는 부족합니다).

| 필드 | 뜻 | 원본에서는 |
| :--- | :--- | :--- |
| `tests` | 수정 뒤 통과해야 하는 테스트 전체 이름 | 실패해야 함 |
| `failingTests` | 수정 뒤 **실패해야** 하는 테스트(수정 전 동작을 고정한 것) | 통과해야 함 |
| `mustContain` | 수정된 대상에 있어야 하는 문자열 | 없어야 함 |
| `mustAdd` | 수정된 대상에서 원본보다 **더 많이** 나와야 하는 문자열 | |
| `mustNotContain` | 수정된 대상에 없어야 하는 문자열 | 있어야 함 |

* **Modern은 동작 판정을 우선합니다.** 현장 테스트 프로젝트의 테스트, 또는 `judges\<루트 이름>\`에 둔 판정 테스트로 `tests`·`failingTests`를 씁니다.
  * 판정 테스트는 원본에서 실패해야 해서 현장 CI에 넣지 않고 `judges\`에 따로 둡니다.
  * 현장 테스트 프로젝트에 이미 있는 테스트만으로도 됩니다. 그 테스트가 원본에서 실패하는지 `validate --deep`이 확인합니다.
* **Legacy와 SQL은 문자열 판정입니다.** 동작 판정은 쓸 수 없습니다(Legacy는 오류로 거절).
* **다른 올바른 수정을 떨어뜨리는 문자열 판정은 쓰지 마십시오.** 올바른 수정이 여러 가지 모양일 수 있기 때문입니다. M3b에서 실제로 겪은 예가 둘 있습니다.
  * 배송 중 주문의 취소를 막는 수정에 `mustAdd: OrderStatus.Shipped`를 걸었더니, 죽은 조건의 `|| Shipped`를 지우고 새 예외 조건을 쓴 올바른 수정이 떨어졌습니다.
  * 반올림 수정에 `mustAdd: Math.Round`를 걸었더니, `Math.Floor(값 / 10m + 0.5m) * 10m`처럼 올바른 다른 반올림이 떨어졌습니다.
* 문자열 판정은 테스트가 못 보는 것을 확인할 때만 남깁니다. 문자열은 가능한 한 짧고, 원본에 없는 이름이나 값을 고릅니다.
* 공백·줄바꿈만 바뀐 수정과 대상이 원본과 같은 수정은 항상 실패입니다.
* `mustContain`은 원본 대상에 **없어야** 하고 `mustNotContain`은 **있어야** 합니다. 어기면 `validate`가 오류로 거절합니다.

## `validate`가 확인하는 것

```cmd
pelly-eval validate --suite <폴더> --config <pelly.json>
```

LLM과 SQL에 접속하지 않고, 실행 전에 이것을 점검합니다.

* 스위트: 키 이름, 루트와 `supportFiles`, 루트 밖 빌드 입력(경고)
* 작업 정의: id 형식, id와 파일 이름 일치, id 중복, `request`, `kind`별 필드 조합
* 대상: 파일과 csproj 존재, `cs-legacy`/`cs-modern`이 실제 프로젝트 형식과 맞는지, `method`가 하나로 정해지는지, `line` 범위, SQL 객체 배치가 하나이고 구문 오류가 없는지
* 판정: 판정이 하나도 없는지, 위의 원본 대상 조건

종료 0은 오류 없음(경고는 있어도 됨), 종료 4는 오류 있음입니다.

### `--deep`

```cmd
pelly-eval validate --suite <폴더> --config <pelly.json> --deep
```

정적 검사에 오류가 없을 때만 돕니다. 동작 판정이 있는 모던 C# 작업마다 원본 복사본을 만들어 복원하고, 판정 테스트를 실제로 실행합니다.

* `tests`가 원본에서 이미 통과하면 오류입니다(빈 판정: 아무 수정이나 통과합니다).
* `failingTests`가 원본에서 실패하면 오류입니다.
* 테스트 이름이 결과에 없으면 오류입니다.
* 복원 실패나 테스트 호스트 문제 같은 도구 문제는 경고입니다.

복원과 빌드가 필요해서 느립니다. 스위트를 고칠 때마다 돌리지 말고 마지막에 한 번 돌리십시오.
작업 복사본은 확인 뒤 지워집니다.

## 작업 쓰는 순서

1. 대상 코드를 고릅니다. 한 메서드나 한 SQL 객체 안에서 끝나는 수정이 좋습니다.
2. 요청문을 사용자가 말하듯 한국어로 씁니다.
3. 올바른 수정이 어떤 모양일지 여러 가지 떠올리고, 모두 통과하는 판정을 고릅니다.
4. 템플릿을 복사해 값을 채웁니다. `<…>`가 남아 있으면 안 됩니다.
5. `validate`가 깨끗해질 때까지 고칩니다. 마지막에 `--deep`을 한 번 돌립니다.
