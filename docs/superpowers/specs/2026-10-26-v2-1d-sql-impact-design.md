# V2-1d 운영 정의 읽기·`pelly sql pull`·SQL 영향 탐색 설계

- 작성일: 2026-10-26
- 상태: 초안 (사람 승인 전)
- 선행: V2-1c(영향 탐색, main `845a412` 이후). 확장 지점 `ImpactSeed.Kind`, `ImpactCheck.Covers`를 쓴다.
- 표기: **(사람 결정)**은 사용자가 대화에서 정한 것, **(Claude 결정)**은 설계자가 정한 것이다. Claude 결정은 만드는 사람이 더 나은 근거가 있으면 바꿔도 되지만, 바꾸면 이 문서를 고친다.

## 1. 왜 하는가

현장 사용 흐름 **(사람 결정, 현재 상태)**:

1. SSMS에서 SP를 스크립트로 뽑아 파일로 저장한다. **저장소에 `.sql` 파일을 두지 않는다.**
2. 그 파일을 `pelly sql`로 고친다. 검증은 **개발 DB**에서 한다.
3. 고친 파일을 SSMS에서 **운영 DB**에 직접 실행해 반영한다.

이 흐름의 문제:

- **1단계가 번거롭다.** SP를 하나 고칠 때마다 SSMS에서 스크립트를 뽑아 저장해야 `pelly sql`을 쓸 수 있다.
- **운영 변경이 조용히 사라질 수 있다.** 운영에서 누군가 SP를 직접 고쳤는데 개발 DB에는 그 변경이 없다고 하자. 개발 DB에서 뽑은 옛 버전을 고치면 개발 DB 검증은 통과하고, SSMS에서 운영에 실행하면 운영의 변경이 덮어써진다. 개발 DB만 보는 pelly는 이 차이를 알 수 없다. 받아 온 뒤 반영하기 전 사이에 운영이 바뀌어도 마찬가지다.
- **SQL 쪽 영향 대상을 알 수 없다.** V2-1c는 C# 작업의 빠진 영향 대상만 알린다. SP를 고칠 때 그 SP를 부르는 다른 SP, 그 SP를 이름으로 부르는 C# 코드, 같은 데이터를 읽는 다른 SP는 알리지 않는다.

## 2. 목표 / 비목표 / 실패 조건

### 목표

1. **운영 DB 읽기 전용 연결 (사람 결정):** pelly가 운영 DB에 `VIEW DEFINITION` 권한만으로 접속해 정의와 의존성 정보를 읽는다.
2. **`pelly sql pull`:** 서버의 SP·함수·뷰 정의를 SSMS 「ALTER로 스크립트」와 같은 모양의 `.sql` 파일로 받는다. 기본 출처는 운영이다.
3. **운영과의 차이 알림:** 다음 세 시점에 운영 정의와 비교해 다르면 알린다.
   - `pull` 때: 운영과 개발 DB의 정의가 다르면 알린다(개발 DB 검증을 그만큼 덜 믿어야 하므로).
   - `pelly sql`로 고칠 때: 받아 온 뒤 운영이 바뀌었으면 멈춘다(받은 기록이 없는 파일은 다르면 경고).
   - SSMS에서 반영하기 직전: 사람이 `pelly sql check <파일>`을 돌려 확인한다.
4. **SQL 영향 탐색 (사람 결정, 세 가지 모두):** `sql` 작업을 시작점으로 다음을 찾아 명세에 빠졌으면 경고한다.
   - 이 SP를 `EXEC`하거나 참조하는 다른 SP·함수·뷰
   - 이 SP 이름을 문자열로 쓰는 C# 코드
   - 이 SP가 쓰기(INSERT/UPDATE/MERGE)하는 **컬럼**을 읽는 다른 SP·함수·뷰

### 비목표

- 운영 DB에 쓰기. pelly는 운영에 정의·메타데이터를 읽는 조회만 보낸다. `SET NOEXEC` 컴파일 검증도 운영에서는 하지 않는다.
- 반영(배포) 자동화. 반영은 지금처럼 사람이 SSMS에서 한다. pelly는 SSMS 실행을 막을 수 없다.
- 찾은 영향 대상을 명세 작업으로 자동 추가하기(V2-1c와 같음). 알리기만 하고, 추가는 사람이 한다. 다만 메시지에 `pull` 명령을 함께 보여 준다.
- C# 작업에서 SP 쪽으로 가는 영향(C# 변경이 SP를 깨는 경우).
- 동적 SQL 안의 참조, 다른 DB·연결된 서버(3·4부 이름) 참조, 동의어(synonym)를 거친 참조. 서버 의존성 정보에 잡히지 않으므로 놓친다. 이 한계는 README에 적는다.
- 테이블·트리거 정의 받기. `pull`은 `pelly sql`이 고칠 수 있는 PROCEDURE·FUNCTION·VIEW만 받는다.

### 실패 조건 (기술적으로 동작해도 실패로 본다)

- pelly가 운영 DB에 정의·메타데이터 조회 이외의 문장을 보낸다.
- 운영 정의와 다른데 아무 표시 없이 지나간다(비교하지 못했을 때도 "비교하지 못함"을 표시해야 한다).
- 같은 테이블을 쓰는 SP가 많은 환경(사용자 답: 주요 테이블 하나에 약 50개)에서 경고가 쏟아져 사람이 읽지 않게 된다.
- 기존 `pelly sql`·`spec check`·`apply`의 동작·종료 코드가 운영 연결을 설정하지 않은 사용자에게 바뀐다.

## 3. 제약

- 폐쇄망. 외부 통신 없음(`deploy/no-network.md`).
- 운영 연결도 기존 개발 연결 규칙을 따른다: 허용 목록(호스트·DB) 필수, 비어 있으면 접속하지 않음(fail closed), 비밀번호가 있는 연결은 환경 변수로만.
- 운영 연결과 개발 연결은 서로 바꿔 쓸 수 없어야 한다. 컴파일 검증 경로가 운영 연결을 받을 수 없도록 타입으로 나눈다 **(Claude 결정)**: 운영 연결은 정의·의존성 읽기만 가진 별도 인터페이스(예: `ISqlDefinitionReader`)로만 쓴다.
- 기존 v1·V2-1a~c·V2-2·V2-3 동작과 테스트는 바뀌지 않는다. 운영 연결이 없으면 새 기능은 꺼져 있거나 개발 DB 기준으로 동작하며 그 사실을 표시한다.
- 게이트: `dotnet build -warnaserror` 경고 0, `dotnet test` 실패 0. SQL 통합 테스트는 기존 Linux SQL 컨테이너(`localhost,14333`, `PellyCorpus`)를 쓰고, 운영 역할은 같은 서버의 두 번째 DB로 흉내 낸다 **(Claude 결정)**.
- SQL 경로는 Windows에서 확인하지 않았다는 기존 한계가 그대로다.

## 4. 운영 연결 설정

**(Claude 결정)** 기존 `sql` 섹션 아래에 `production` 하위 섹션을 둔다.

```json
{
  "sql": {
    "allowedHosts": ["devdb01"], "allowedDatabases": ["Shop"],
    "connectionString": "Server=devdb01;Database=Shop;Integrated Security=true",
    "production": {
      "allowedHosts": ["proddb01"], "allowedDatabases": ["Shop"],
      "connectionString": "Server=proddb01;Database=Shop;Integrated Security=true;ApplicationIntent=ReadOnly"
    }
  }
}
```

- 비밀번호가 있는 운영 연결은 환경 변수 `PELLY_SQL_PROD_CONNECTION`으로만 지정한다. 규칙은 `PELLY_SQL_CONNECTION`과 같다(설정 파일의 비밀번호는 설정 오류, 환경 변수가 우선, 허용 목록은 그대로 적용).
- 허용 목록·연결 문자열 검사(`SqlTargetPolicy`, 서버·DB 키 중복, `Failover Partner` 거부 등)는 개발 연결과 같은 규칙을 운영 허용 목록으로 적용한다.
- 운영 연결 문자열이 개발 연결과 같은 서버·DB를 가리키면 설정 오류(종료 코드 4)다. 비교가 의미 없어지기 때문이다 **(Claude 결정)**.
- 필요한 권한: 운영 DB 수준 `VIEW DEFINITION` 하나. 없으면 운영을 쓰는 기능은 "운영 권한 없음"으로 처리한다(아래 각 절).
- `pelly doctor`에 운영 연결 행을 더한다: 설정 여부, 허용 목록, 접속, `VIEW DEFINITION`, 개발과 같은 대상인지. 운영이 설정되지 않았으면 "운영 연결 없음(선택)"으로 표시하고 실패로 세지 않는다.

## 5. `pelly sql pull`

```bash
pelly sql pull <객체> [<객체> ...] [--from prod|dev] [--out <폴더>] [--force] [--config <경로>] [--pause-on-exit]
```

- `<객체>`: `dbo.usp_X`, `usp_X`(스키마 생략 시 `dbo`), `[dbo].[usp_X]`. PROCEDURE·FUNCTION(스칼라·인라인·다중 문장 테이블)·VIEW만 받는다. 그 밖의 종류나 없는 객체는 그 객체만 실패로 알리고 나머지는 계속 받는다. 하나라도 실패하면 종료 코드 4다.
- **출처 (사람 결정):** 기본은 운영(`--from prod`). 운영 연결이 설정되지 않았으면 종료 코드 4와 설정 안내로 멈춘다. `--from dev`를 명시해야 개발 DB에서 받는다 **(Claude 결정: 조용히 개발 DB로 대신하지 않는다)**.
- **파일 위치 (사람 결정, 2026-10-26):** 저장소(작업 공간) 안의 정해진 폴더에 받고, 그 폴더는 `.gitignore`로 커밋에서 뺀다. 그래야 명세의 `sql` 작업이 받은 파일을 가리킬 수 있다(`SpecChecker`는 작업 공간 밖 파일을 `OutsideWorkspace` 오류로 처리한다). 팀은 저장소에 `.sql`을 커밋하지 않는다.
  - 기본 폴더는 `<작업 공간 루트>/db/pulled/`이고, 설정 `sql.pullDirectory`(작업 공간 루트 기준 상대 경로)와 `--out`으로 바꾼다 **(Claude 결정: 이름)**. 폴더가 없으면 만든다. 작업 공간 루트는 기존 `pelly sql`·`apply`와 같은 방법으로 찾는다.
  - pelly는 `.gitignore`를 고치지 않는다. 받은 폴더가 git 저장소 안에 있고 무시되지 않으면(`git check-ignore`로 확인, git이 없으면 건너뜀) `db/pulled/가 .gitignore에 없습니다 — 받은 파일이 커밋될 수 있습니다`를 알림으로 보여 준다. README에 `.gitignore` 줄을 안내한다.
- **파일 이름 (Claude 결정):** `<스키마>.<이름>.sql`. 같은 이름의 파일이 있으면 그 객체는 쓰지 않고 실패로 알린다. `--force`면 덮어쓴다.
- **파일 모양:** SSMS 「ALTER로 스크립트」와 같게 한다. `pelly sql`과 SSMS 실행에 그대로 쓸 수 있어야 한다.

  ```sql
  -- pelly pull: source=prod server=proddb01 database=Shop object=dbo.usp_X sha256=<정의 해시> at=2026-10-26T09:12:33Z
  SET ANSI_NULLS ON
  GO
  SET QUOTED_IDENTIFIER ON
  GO
  ALTER PROCEDURE [dbo].[usp_X] ...
  GO
  ```

  - 정의 본문은 `OBJECT_DEFINITION`(또는 `sys.sql_modules.definition`)을 그대로 쓰되, 정의의 첫 `CREATE` 키워드만 `ALTER`로 바꾼다. 주석·공백·대소문자는 건드리지 않는다. 키워드 위치는 ScriptDom 토큰으로 찾는다(주석 안의 `CREATE`를 바꾸지 않도록). `CREATE OR ALTER`는 그대로 둔다.
  - `SET ANSI_NULLS`/`SET QUOTED_IDENTIFIER` 값은 `sys.sql_modules.uses_ansi_nulls`·`uses_quoted_identifier`에서 가져온다.
  - 첫 줄 주석(**받은 기록**)은 출처·서버·DB·객체·정의 해시·받은 시각(UTC)이다. 해시는 정의 본문을 정규화한 뒤 계산한다(§6.1). 이 주석은 첫 배치(`SET ANSI_NULLS`) 앞에 있어 `pelly sql`의 대상 밖 배치 보호가 그대로 지킨다. 예외는 §6.2의 받은 기록 갱신 하나다(그 줄만, 갱신한 값으로만 허용).
  - 줄바꿈은 정의 원문을 따른다. 인코딩은 UTF-8(BOM 포함)으로 쓴다 **(Claude 결정: SSMS가 한글 주석을 깨지 않고 여는 형태)**.
- **암호화된 객체**(`definition`이 NULL)는 "암호화된 객체는 받을 수 없습니다"로 그 객체만 실패한다. 권한이 없어 NULL인 경우와 메시지를 구분한다(`VIEW DEFINITION` 확인 결과로 판단).
- **운영에서 받을 때 개발 DB와 비교:** 개발 연결이 설정되어 있으면 같은 객체의 개발 정의와 비교한다(§6.1 정규화). 다르면 경고를 보여 주고 받은 기록 주석 다음 줄에 `-- pelly pull: dev differs (sha256=<개발 해시>)`를 남긴다. 개발 DB에 객체가 없으면 "개발 DB에 없음 — pelly sql 검증이 실패할 수 있습니다"로 경고한다. 개발 DB에 접속할 수 없으면 "개발 DB와 비교하지 못함"을 표시한다. 어느 경우든 파일은 쓴다.

## 6. 운영과의 차이 확인

### 6.1 비교 규칙

- 비교 대상은 **정의 본문**(대상 객체의 `CREATE`/`ALTER` 배치 한 개)이다.
- 정규화 **(Claude 결정)**: 줄바꿈을 `\n`으로 통일, 각 줄 끝 공백 제거, 앞뒤 빈 줄 제거, 첫 `CREATE`/`ALTER`/`CREATE OR ALTER` 키워드를 하나로 통일. 그 밖(주석·대소문자·식별자 대괄호)은 바꾸지 않는다. 즉 주석만 바뀌어도 "다름"이다. 운영에서 누가 무엇이든 바꿨다면 알아야 하기 때문이다.
- 해시는 정규화한 본문의 SHA-256이다.

### 6.2 받은 기록이 유효한 경우 (Claude 결정)

받은 기록은 `source=prod`이고 기록의 `server`·`database`가 지금 설정된 운영 연결의 서버·DB와 같을 때만 유효하다. `--from dev`로 받은 파일이나 다른 운영 서버에서 받은 파일은 **받은 기록이 없는 파일**로 다룬다(아래 규칙대로 파일과 운영을 직접 비교한다). 받은 기록은 다시 `pull`할 때, 그리고 아래 **받은 기록 갱신** 때 바뀐다.

**파일과 운영이 같으면 그것이 우선한다 (Claude 결정):** 파일의 대상 배치가 운영의 현재 정의와 같으면(§6.1 정규화) "운영과 같음"이다. 받은 기록의 해시와 달라도 운영 변경 경고를 내지 않는다. 고친 파일을 이미 SSMS로 운영에 반영한 뒤 같은 파일을 다시 고치거나 확인하는 경우다. 이 경우에 거짓 경고를 내면 사람이 경고를 무시하게 된다(§2 실패 조건).

**받은 기록 갱신 (사람 결정, 2026-10-27):** 파일과 운영이 같은데 유효한 받은 기록의 해시가 운영 해시와 다르면(고친 파일을 이미 SSMS로 반영함) 받은 기록이 운영보다 오래된 것이다. 그대로 두면 다음 수정 뒤 `pelly sql`이 "받은 뒤 운영이 바뀜"으로 잘못 멈춘다. 그래서 `pelly sql`(과 `apply`의 `sql` 작업)은 이번 실행이 쓰는 파일의 받은 기록 줄을 갱신한다: 출처·서버·DB·객체는 그대로, `sha256=`는 방금 읽은 운영 해시, `at=`는 지금(UTC). 파일의 나머지(`dev differs` 줄 포함)는 바뀌지 않고, 줄바꿈·BOM도 그대로다.
- 갱신한 줄은 수정의 바탕 텍스트에 미리 들어간다. 대상 밖 배치 보호는 그 줄을 원본으로 보므로, 대상 밖에서 바뀌어도 되는 것은 정확히 그 한 줄뿐이다. 다른 변경(옛 받은 기록 그대로 쓰기 포함)은 전처럼 거부한다.
- 받은 기록이 대상 배치 안에 있으면(첫 배치가 대상) 갱신하지 않는다 **(Claude 결정: 모델이 고치는 배치를 pelly가 따로 고치지 않는다)**.
- 파일을 쓸 때만 갱신된다: `--dry-run`은 아무것도 쓰지 않고(diff에는 보인다), 검증 실패·사용자 거절이면 원래 파일(옛 기록)로 되돌린다. 다음 실행이 다시 갱신한다.
- 받은 기록이 지금 운영 해시와 같거나, 유효하지 않거나(§6.2), 없으면 갱신하지 않는다.

### 6.3 `pelly sql`로 고칠 때

기존 PREFLIGHT 뒤, 모델을 부르기 전에 확인한다. 운영 연결이 없으면 아무것도 하지 않는다(기존 동작 그대로).

- **파일의 대상 배치가 운영과 같으면:** 표시 없음(§6.2). 다만 받은 기록이 운영보다 오래되었으면 `받은 기록을 운영 정의로 갱신합니다 (이 파일은 이미 운영에 반영되어 있습니다)`를 알리고, 쓰는 파일의 받은 기록을 갱신한다(§6.2 받은 기록 갱신). 실행 기록(`summary.json`의 `sqlProd.recordRefreshed`)에 갱신한 기록이 실제로 파일에 남았는지 적는다.
- **받은 기록이 유효한 파일:** 운영의 현재 정의 해시를 받은 기록의 해시와 비교한다.
  - 같으면 표시 없음.
  - 다르면 **멈춘다 (사람 결정, 2026-10-26)**: 모델을 부르지 않고 파일도 바꾸지 않은 채 종료 코드 4(실패 종류 `SqlProdChanged`)로 끝난다. 메시지: `받은 뒤 운영에서 dbo.usp_X가 바뀌었습니다 (받은 시각 …). 운영 변경을 덮어쓰지 않도록 다시 받으십시오: pelly sql pull dbo.usp_X --force`. 이미 고친 내용이 있으면 다시 받기 전에 따로 보관하라는 안내도 붙인다. 넘기는 옵션은 두지 않는다 **(Claude 결정: 다시 받는 비용이 작다)**.
- **받은 기록이 없거나 유효하지 않은 파일(SSMS에서 직접 뽑은 파일 등):** 파일의 대상 배치를 운영의 현재 정의와 직접 비교한다. 다르면 `파일의 dbo.usp_X가 운영 정의와 다릅니다`를 경고한다. 어느 쪽이 최신인지는 알 수 없으므로 그렇게 적는다.
- 운영에 객체가 없으면(새 SP) `운영에 dbo.usp_X가 없습니다 (새 객체)`를 알림으로 남긴다.
- 운영에 접속할 수 없거나 권한이 없으면 `운영 정의와 비교하지 못했습니다: <원인>`을 경고하고 진행한다.
- 결과는 실행 기록(`summary.json`/`events.jsonl`)에 남긴다(비교 여부, 결과, 해시).
- 받은 기록이 없거나 유효하지 않은 파일이 운영과 다를 때는 어느 쪽이 최신인지 알 수 없으므로 멈추지 않고 경고만 한다.
- `pelly apply`의 `sql` 작업도 같은 확인을 거친다(작업마다). 멈춤은 그 작업의 실패(`SqlProdChanged`)이며, 이후는 기존 apply 실패 규칙(`--continue` 등)을 따른다. `--yes`여도 경고는 기록에 남는다.

### 6.4 `pelly sql check <파일>` — 반영 직전 확인

```bash
pelly sql check <파일.sql> [--object <이름>] [--config <경로>] [--pause-on-exit]
```

- 사람이 SSMS에서 운영에 실행하기 직전에 돌리는 명령이다. 모델을 부르지 않고 파일을 바꾸지 않는다.
- 대상 지정은 `pelly sql`과 같다(객체가 하나면 자동, 여럿이면 `--object`).
- 검사 순서와 종료 코드 **(Claude 결정)**:
  1. 운영 연결 없음·접속 실패·권한 없음·파일 오류 → 4 (확인할 수 없음).
  2. 파일의 대상 배치가 운영의 현재 정의와 같다 → 0, "운영과 같음 (이미 반영됨 또는 아직 고치지 않음)" (§6.2: 이 결과가 받은 기록보다 우선). 유효한 받은 기록이 운영보다 오래되었으면 "받은 기록이 운영보다 오래되었습니다 — 다음 pelly sql 실행 때 갱신합니다"를 덧붙인다. `check`는 파일을 바꾸지 않으므로 갱신하지 않는다 (사람 결정, 2026-10-27).
  3. 받은 기록이 유효하고(§6.2) 운영의 현재 해시가 기록과 같다 → 0, "받은 뒤 운영이 바뀌지 않음".
  4. 받은 기록이 유효하고 운영의 현재 해시가 기록과 다르다 → 1, "받은 뒤 운영이 바뀜 — 반영하면 그 변경을 덮어씁니다".
  5. 받은 기록이 없거나 유효하지 않다 → 4, "받은 기록 없음 — 운영 변경 여부를 확인할 수 없습니다. 파일이 운영과 다릅니다".
  6. 운영에 객체가 없다(새 객체) → 0, "운영에 없음 (새 객체)".

## 7. SQL 영향 탐색

### 7.1 언제 돈다

**(Claude 결정)** V2-1c와 같은 경고 체계에 붙인다. 오류(종료 코드 4)를 새로 만들지 않는다.

- **운영 연결이 설정된 경우에만 자동으로 돈다 (Claude 결정):** 운영 연결이 없는 사용자의 `apply`에 새 경고·질문·DB 조회가 생기지 않게 한다(§2 실패 조건). 운영 연결이 없으면 `spec check --impact`를 명시했을 때만 개발 DB 기준으로 돈다.
- `pelly spec check --impact`: 미완료 `sql` 작업 모두를 시작점으로 돈다. `--impact`가 없으면 SQL 영향 탐색은 돌지 않는다(지금 `spec check`는 DB에 접속하지 않으므로 그 성질을 지킨다).
- `pelly apply` 시작 검사: 운영 연결이 설정되어 있고 명세에 미완료 `sql` 작업이 있으면 돈다. 경고는 V2-1c와 같이 대화형이면 보여 주고 계속할지 묻고, `--yes`면 기록만 한다.
- 완료(`[x]`) 작업은 시작점에서 뺀다. 「명세에 있음」 판정에는 모든 작업을 쓴다(V2-1c와 같음).

### 7.2 어느 DB를 보나

- 운영 연결이 있으면 **운영 DB의 의존성 정보**를 쓴다. 실제로 반영될 곳의 관계이기 때문이다.
- 운영 연결이 설정되어 있는데 접속할 수 없거나 권한이 없으면 **개발 DB로 대신하지 않는다 (Claude 결정)**. 경고 `ImpactSqlUnavailable`: `영향 탐색(SQL): 운영 DB에 접속하지 못해 SP 쪽 영향을 찾지 못했습니다: <원인>`을 남기고 C# 문자열 탐색(§7.3 ②)만 한다. 운영 관계가 조용히 개발 관계로 바뀌지 않게 하기 위해서다.
- 운영 연결이 설정되지 않았으면(`spec check --impact`를 명시한 경우만, §7.1) 개발 DB를 쓰고 경고 `ImpactSqlDevBased`: `영향 탐색: 운영 연결이 설정되지 않아 개발 DB 기준으로 찾았습니다`를 한 번 남긴다. 개발 DB에도 접속할 수 없으면 `ImpactSqlUnavailable`(원인: 개발 DB)을 남기고 C# 문자열 탐색만 한다.

### 7.3 무엇을 찾나

시작점 객체 이름은 작업의 `#객체`, 없으면 파일에 정의가 하나뿐일 때 그 객체다(`SqlLocatePhase`와 같은 규칙). 정의가 여럿인데 `#객체`가 없으면 그 작업은 `ImpactSeedNotFound`로 경고하고 건너뛴다.

① **이 객체를 참조하는 모듈 — 이유 `EXEC`/`참조`**
- `sys.sql_expression_dependencies`에서 이 객체를 참조하는 같은 DB의 모듈(PROCEDURE·FUNCTION·VIEW·TRIGGER)을 찾는다. 참조하는 쪽이 PROCEDURE이고 본문에서 `EXEC`로 부르면 이유는 `EXEC`, 그 밖은 `참조`다. 이유를 가르기 어려우면 `참조`로 둔다 **(Claude 결정: 이유 구분은 표시용이다)**.
- 개수 상한 없이 하나씩 경고한다. 직접 호출자는 같은 테이블 독자보다 훨씬 적고, 모두 깨질 수 있는 곳이기 때문이다.

② **이 이름을 문자열로 쓰는 C# 코드 — 이유 `이름 호출(문자열)`**
- 작업 공간의 `.cs` 파일에서 문자열 리터럴(일반·축자·원시·보간 문자열의 텍스트 부분)을 구문 트리로 훑는다. 빌드·의미 분석 없이 동작한다.
- 다음 중 하나면 찾은 것으로 본다(대소문자 무시, SQL 식별자 경계 기준):
  - 리터럴 전체가 객체 이름과 같다: `"dbo.usp_X"`, `"usp_X"`, `"[dbo].[usp_X]"`, `"[usp_X]"`
  - 리터럴 안에 `EXEC`/`EXECUTE` 다음 그 이름이 있다: `"EXEC dbo.usp_X @Id"`
- 사용자 코드는 `"dbo.usp_X"`를 문자열로 직접 쓴다 **(사람 답)**. 상수 클래스를 거친 이름은 상수 정의 위치가 찾히고, 그 상수를 쓰는 곳은 찾지 않는다(한계로 README에 적는다).
- 찾은 곳은 V2-1c와 같은 `(경로, 멤버)`로 낸다. 멤버 이름 규칙은 V2-1c(`MemberLocator` 규칙, 멤버 밖이면 감싼 타입 이름과 이유 `멤버 밖`)를 따른다.
- 폴더 탐색은 V2-1c의 제한·건너뛰기 규칙(`BoundedWalker`, 2000 폴더 등)을 그대로 쓰고, 잘리면 `ImpactIncomplete`를 남긴다.
- 이 결과는 이름 기준이므로 V2-1c의 「이름 기준(부정확)」과 같은 성격이다. 다만 C# 의미 분석 실패가 원인이 아니므로 `ImpactNameBased`를 남기지 않고, 이유 칸의 `(문자열)`로 표시한다 **(Claude 결정)**.

③ **같은 컬럼을 읽는 모듈 — 이유 `같은 컬럼 읽음`** (사용자 환경: 주요 테이블 하나에 SP 약 50개)
1. 시작점 객체의 **현재 서버 정의**(§7.2의 DB)를 ScriptDom으로 파싱해 쓰기 대상 `(테이블, 컬럼)`을 모은다.
   - `INSERT INTO T (a, b)` → T.a, T.b. 컬럼 목록이 없으면 T의 모든 컬럼.
   - `UPDATE T SET a = …` → T.a. 별칭(`UPDATE x SET … FROM T x`)은 풀어서 T로.
   - `MERGE`의 UPDATE·INSERT 절 → 같은 규칙.
   - `DELETE`는 컬럼이 없으므로 개별 경고 대상이 아니다. 테이블 요약(아래 4)에만 센다.
   - `#임시테이블`·테이블 변수·다른 DB 테이블은 뺀다.
   - 서버 정의는 고치기 **전** 것이다. 이번 수정이 새로 쓰기 시작할 컬럼은 알 수 없다(명세 검사가 수정 전에 돌기 때문). 이 한계는 경고 문구와 README에 적는다.
2. 그 테이블을 참조하는 모듈 후보를 `sys.sql_expression_dependencies`로 모은다(시작점 자신 제외).
3. 후보마다 `sys.dm_sql_referenced_entities(<후보>, 'OBJECT')`로 컬럼 단위 참조를 읽는다. `is_selected = 1`인 컬럼, 또는 `is_select_all = 1`(SELECT *)이면 그 테이블의 모든 컬럼을 읽는 것으로 본다. 쓰기 컬럼과 하나라도 겹치면 개별 경고 대상이다.
   - 후보가 지금 컴파일되지 않아 이 함수가 실패하면(기존 `GetReferencedEntitiesAsync`와 같은 경우) 그 후보는 개별 경고 대상에서 빼고 요약에 "컬럼 확인 불가 n개"로 센다.
4. **개별 경고 상한 (사람 결정: 좁히고 요약)**: 테이블마다 개별 경고는 최대 10개다 **(Claude 결정: 숫자)**. 정렬은 겹치는 컬럼 수 내림차순, 같으면 이름순.
5. **테이블 요약 한 줄**: 시작점이 쓰는 테이블마다 한 줄. 예: `작업 T2: dbo.Orders를 함께 쓰는 모듈 50개 — 쓰는 컬럼(Status, UpdatedAt)을 읽는 모듈 7개 경고, 외 0개 생략, 컬럼 확인 불가 2개. 전체 목록: <경로>`.
6. **전체 목록**은 파일로 남긴다 **(Claude 결정)**: `apply`는 `.pelly/runs/<apply-id>/impact-sql.json`, `spec check --impact`는 `.pelly/impact/<명세 id>-sql.json`(실행마다 덮어씀). 내용은 시작점·테이블·쓰는 컬럼·후보 모듈 전체와 각자의 겹치는 컬럼·확인 불가 여부다.

### 7.4 「명세에 있음」 판정

`ImpactCheck.Covers`에 `sql` 규칙을 더한다(V2-1c가 이 자리를 열어 두었다).

- **SP 쪽 대상(①·③):** 대상에는 파일이 없다. 어떤 `sql` 작업의 대상 객체(작업의 `#객체`, 없으면 그 파일의 유일한 정의)가 대상 객체와 같으면(스키마 포함, 대소문자 무시, 스키마 생략은 `dbo`) 「있음」이다. 파일을 읽어야 하는 경우가 있으므로 `Covers`가 순수 함수로 남지 못하면, 명세의 `sql` 작업 → 대상 객체 이름 표를 먼저 만들어 넘기는 식으로 바꿔도 된다(만드는 사람 몫).
- **C# 쪽 대상(②):** 기존 `cs` 규칙 그대로(경로 + 멤버).

### 7.5 경고 문구

V2-1c 코드를 그대로 쓰고 이유만 더한다.

- `ImpactMissing`(SP 대상): `작업 {ids}의 영향 대상이 명세에 없습니다: {스키마.이름} ({이유}) — pelly sql pull {스키마.이름} 로 받아 작업 줄에 추가할 수 있습니다 ({받는 폴더}/{스키마.이름}.sql)`
- `ImpactMissing`(C# 대상): 기존 형식, 이유 `이름 호출(문자열)`
- `ImpactTableShared`(새 코드, 작업 줄): §7.3 ③-5의 요약 한 줄
- `ImpactSqlDevBased`(새 코드, 줄 0): §7.2의 개발 DB 기준 경고
- `ImpactSqlUnavailable`(새 코드, 줄 0): §7.2의 DB 접속 불가 경고(운영·개발 중 어느 쪽인지와 원인을 적는다)
- `ImpactSeedNotFound`: 기존 코드. 시작점 객체가 서버에 없거나(새 SP) 특정할 수 없을 때. 새 SP면 문구를 `작업 {id}: dbo.usp_X가 서버에 없어(새 객체) SP 쪽 영향을 찾지 않았습니다`로 한다.

## 8. 실행 기록과 report

- `pelly sql`·`apply`의 실행 기록에 운영 비교 결과(§6.3)를 남긴다.
- `apply.json`에 SQL 영향 탐색 요약(시작점 수, 경고 수, 기준 DB, 전체 목록 경로)을 더한다.
- `pelly report`는 이번 단계에서 바꾸지 않는다 **(Claude 결정)**. 운영 비교 결과 집계는 현장 사용을 본 뒤 정한다.

## 9. 검증 방법

- **단위 테스트:** 설정 검사(운영 섹션, 환경 변수, 개발과 같은 대상 거부), pull 파일 모양(`CREATE`→`ALTER`, 주석 안 `CREATE` 보존, `CREATE OR ALTER`, SET 값, 받은 기록 주석, BOM), 정규화·해시, 받은 기록 파싱, 쓰기 컬럼 추출(INSERT 목록 유무, UPDATE 별칭, MERGE, DELETE, 임시 테이블 제외), C# 문자열 매칭(각 리터럴 종류, 경계, 대소문자, `EXEC` 포함, 오탐 예: `"usp_XY"`), `Covers`의 sql 규칙, 개별 경고 상한과 정렬.
- **SQL 통합 테스트 (Linux 컨테이너):** 같은 서버에 개발 역할 DB와 운영 역할 DB를 두고 다음을 확인한다.
  - pull 결과 파일을 다시 실행하면 오류 없이 같은 정의가 된다(왕복).
  - 운영에서 정의를 바꾼 뒤 `pelly sql`은 경고하고 `pelly sql check`는 종료 코드 1이다.
  - 운영과 개발이 다를 때 pull이 경고하고 `dev differs` 줄을 남긴다.
  - 영향 탐색 ①·③이 기대한 모듈을 찾고, 컴파일되지 않는 후보를 "확인 불가"로 센다.
  - **운영 역할 DB에 보낸 문장이 모두 읽기 조회뿐임**을 확인한다(예: 운영 역할 로그인을 `VIEW DEFINITION`만 가진 계정으로 만들어 쓰기 시도가 있으면 실패하게 한다).
- **회귀:** 운영 연결을 설정하지 않은 상태에서 기존 `pelly sql`·`spec check`·`apply` 테스트가 모두 그대로 통과한다.
- **현장 확인(사람 몫):** 실제 운영 DB에서 주요 테이블 하나를 쓰는 SP로 `spec check --impact`를 돌려 개별 경고 수가 읽을 만한지 본다. 사용자 답(약 50개 중)과 비교해 상한 10을 조정할지 정한다.
