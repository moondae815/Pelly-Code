## 1. 결론 (현장 전 잠정)

**Visual Studio MSBuild가 있는 Windows에서는 레거시·SDK 형식 코퍼스 모두 의미 분석용으로 깨끗하게 읽혔다.**
- 판정 항목이 모두 통과했다: 호출 해석률 100%, 컴파일 오류 0, 처음 열기 약 5초, 참조 찾기 메서드당 최대 0.7초.
- S6에서 이름만 보는 탐색이 헷갈렸던 a3도 정답과 같았다. 빠짐 0, 금지 대상 0이다.

**배포:** 보조 프로세스 폴더(`BuildHost-net472`, `BuildHost-netcore`)를 exe 옆에 두는 형태(설계 5.2의 3)만 된다. 단일 파일 exe 하나만으로는 macOS와 Windows 모두 「빌드 도구를 찾을 수 없음」(종료 3)으로 실패했다. 제품에 넣는다면 반입 묶음에 폴더 둘이 더 생긴다.

**개발 PC(macOS)에서는 레거시를 의미 분석할 수 없다.** 예외 없이 「열렸지만」 호출 해석률은 2.8%, 컴파일 오류는 830이었다. 도구는 이 조용한 반쯤 실패를 잡아 미달·종료 3으로 알린다. 제품에 넣는다면 「의미 분석 실패 → 지금의 구문 방식」으로 돌아가는 경로가 꼭 필요하다는 근거다.

**설계 §7 「다음 행동」 표에서의 자리(현장 전 잠정):** 「현장에서 모두 통과」 줄에 해당할 것으로 보인다. 단 현장 측정 전까지는 확정하지 않는다. 확정되면 2단계(S6 arm C를 의미 탐색으로 재측정)로 간다.

## 4. 확인한 것과 못 한 것

- **a3 대조:** 의미 기반 참조·구현 찾기 결과가 S6 정답 5곳과 같고, 금지 대상(`IOrderService.GetOrder`와 그 호출부 `OrderController.Detail`)은 하나도 잡지 않았다.
  - 같은 코드에 이름만 보는 탐색을 돌리면 금지 대상을 잡는다. 테스트 `A3_reports_forbidden_when_name_matching_is_used`가 이것을 고정한다.
  - macOS에서 해석률 2.8%인데도 a3가 맞은 것은 프로젝트 소스 안의 심볼만으로 찾을 수 있는 사례이기 때문이다. 바깥 라이브러리 타입이 걸린 탐색은 해석률이 낮으면 틀릴 수 있다.
- **복원 안 된 솔루션:** Modern 사본에서 `obj/`를 지우고 쟀다. 결과는 「타입 정보: 판정 안 함(측정 프로젝트 0/3)」, 「불러오기: 미달(참조 해석 실패)」, 종료 0이다. 「통과」로 나오지 않는다.
- **MSBuild 없음(설계 5.3):**
  - macOS에서는 실제로 Visual Studio MSBuild가 없어 확인되었다(종료 3).
  - Windows 러너에서 `MSBUILD_EXE_PATH`를 없는 경로로 준 흉내는 **효과가 없었다**. 보조 프로세스가 MSBuild를 스스로 다시 찾아 정상으로 읽었다(종료 0, 모두 통과).
  - 따라서 Windows에서 MSBuild가 없을 때의 동작은 측정되지 않았다.

## 5. 측정 중에 고친 것 (최종 리뷰와 실측)

- **메시지 언어:** 이 Mac에서 Roslyn 예외가 한국어로 번역되어 나왔다(「빌드 호스트를 찾을 수 없습니다」). 분류 규칙은 영어 낱말이라, 도구 시작 시 UI 언어와 `VSLANG=1033`·`DOTNET_CLI_UI_LANGUAGE=en`을 고정했다.
- **잘못된 「빌드 도구 없음」:** 빌드 오류에 MSBuild가 붙이는 머리말과 오류 안내 링크(`aka.ms/msbuild/...`) 속 `msbuild` 때문에 잘못 분류되고 있었다. 머리말을 벗기고 규칙을 구 단위로 좁혔다.
- **조용한 거짓 통과 막기:** 잰 것이 없으면(측정 프로젝트 0 또는 호출 0, 참조 탐침 메서드 0) 「통과」 대신 「판정 안 함」이다.
- **멀쩡한 솔루션이 떨어지지 않게:**
  - 작업 공간 경고는 실패로 세지 않는다.
  - 불러온 프로젝트는 개수가 아니라 경로로 대조한다. 솔루션 밖 참조는 「추가」로 따로 센다.
  - `dynamic` 인자로 늦게 바인딩되는 호출(`ViewBag` 등)은 해석률 분모에서 뺀다.
  - 웹 사이트 프로젝트 항목(폴더 경로·URL)이 모든 진단을 「C# 아님」으로 삼키지 않게 했다.

## 6. 한계

- 처음 열기(콜드)에서 OS 파일 캐시를 통제하지 않았다. 「첫 회」를 콜드로 부른 것이다.
- 언어 고정(`VSLANG`)이 Visual Studio MSBuild 메시지까지 영어로 바꾸는지는 현장에서만 확인된다. 바뀌지 않으면 분류가 「기타」로 빠진다. 그래도 실패 여부 판정은 유지된다.
- 「빌드 도구를 찾을 수 없음」에는 MSBuild가 없는 경우와 .NET SDK가 없는 경우가 같이 들어간다.
- 「없는 참조 DLL」 수는 항상 0으로 나온다. Roslyn이 해석하지 못한 참조를 프로젝트에서 지우고 경고만 남기기 때문이다. 대신 경고 수(기타)를 본다.
- 최대 메모리에는 보조 프로세스(BuildHost)가 빠져 있다. macOS 값은 최댓값이 아니라 끝 시점 값이다.
- 공백·한글이 든 경로를 실제 보조 프로세스로 여는 것은 Windows에서 재지 않았다. 인구 조사 단계만 테스트했다.

## 8. 2단계: S6 범주 A 코드 비교군을 심볼로 다시 재기

S6 arm C(이름만 보는 호출부 탐색)를 같은 출력 형식의 의미 기반 탐색으로 바꿨다. 두 결과를 S6 채점기와 승인된 정답(커밋 `c2344a6`)으로 나란히 채점했다.
- 명령: `s8 arm-c`
- 측정 환경: Windows 러너 실행 `40097215069`(커밋 `c557797`).
- macOS에서는 Modern 두 사례만 쟀다. 레거시는 해석률 2.8%라 채점하지 않았다(「측정 불가」). Modern 두 사례의 결과는 Windows와 같았다.

| 사례 | 범주 A 내용 | 이름(구문) | 심볼(의미) |
| :--- | :--- | :--- | :--- |
| a1-cancel-returns-refund | 반환 형식 변경 → 구현·호출부 | 재현율 1.00, 정밀도 0.75, 쓸 만함 | 재현율 1.00, 정밀도 0.75, 쓸 만함 |
| a2-update-status-returns-rows | 반환 형식 변경 → 테스트의 숨은 구현체 | 재현율 1.00, 정밀도 1.00, 쓸 만함 | 재현율 1.00, 정밀도 1.00, 쓸 만함 |
| a3-rename-getorder | 이름 변경, 같은 이름의 다른 인터페이스 있음 | 재현율 1.00, **금지 1**(`OrderController.Detail`), 쓸 만하지 않음 | 재현율 1.00, 정밀도 1.00, 금지 0, **쓸 만함** |
| 합계 | | 2/3 | **3/3** |

**판정(S6 설계 §7 별도 판정의 갱신):** 호출부·구현체 찾기는 코드로 하고, 이름이 아니라 심볼로 한다. 심볼 방식은 정답을 모두 찾았고 금지 대상을 하나도 잡지 않았다. 모델(S6 arm B)의 범주 A 쓸 만함은 5/15였다.

**한계**
- a1의 정밀도 0.75는 두 방식이 같다. 탐색은 기존 테스트 `CancelAsync_WhenShipped_CurrentlyCancels`를 호출부로 냈다. 그러나 반환 형식이 `Task`에서 `Task<decimal>`로 바뀌어도 `await` 호출은 고칠 필요가 없어서 정답에는 없다. 탐색은 「영향받을 수 있는 곳」을 내고, 고칠 곳은 아직 사람(또는 빌드 오류)이 고른다.
- 범주 A는 사례가 3개뿐이다. 현장 코드에서의 효과는 현장 측정(7절) 뒤에 판단한다.
- 생성자 안의 호출은 S6 색인과 맞추려고 대상에서 뺐다.
